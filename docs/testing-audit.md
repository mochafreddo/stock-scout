## 감사 원문

2026-11-14의 `3714f59e0ef1edef20c9b63b833d8114f5ef755a`를 대상으로 한 감사 기록이다. 실행 대상 테스트 18개, 보조 파일 3개를 모두 읽고 관련 제품 코드와 대조했다. 제품·테스트 수정, 커밋·푸시·이슈 등록, 실제 토스 및 계좌 조회는 범위에 포함하지 않았다.

전체 252개 테스트는 통과했지만 보강이 필요한 발견 13건을 남겼다. 높음 4건, 중간 7건, 낮음 2건이다. 선택한 고유 변이 17개 중 13개가 생존했고, 이를 12개 검증 공백으로 묶었다. 별도로 테스트 도우미의 timeout 정리 실패 1건을 실행으로 재현했다. 추가 보강점 5개는 정적 검토 결과로 구분했다. 이 표본은 의도적으로 의심 경로를 골랐으므로 전체 테스트의 변이 점수로 해석하지 않는다.

## 판단 기준과 증거 수준

현재 요구사항은 [#278 통합 명세](https://github.com/mochafreddo/stock-scout/issues/278), [#283 계약 결정](https://github.com/mochafreddo/stock-scout/issues/283#issuecomment-6686267791), [CLI 계약](toss-cli.md), [용어집](../GLOSSARY.md), [ADR 0019](adr/0019-toss-query-tools-transition.md) 및 [전환 기록](toss-transition.md)을 따른다. 개발 도구는 [개발 안내](development.md)와 [ADR 0004](adr/0004-staged-commit-validation.md)를 따른다. 과거 KIS·추천 제품의 인수 조건을 현재 조회 도구에 적용하지 않았다.

감사 기준은 요구사항 대응, 결함 검출력, 구현과 독립적인 기대값, 목의 범위, 경계·오류·재실행·상태 격리, 불안정성·중복·폐기된 검사, 주요 경로의 검증 공백이다. 공개 경계는 CLI 인자·stdout JSON·stderr·종료 코드·HTTP 요청, 소비자 예제와 개발 도구의 외부 동작이다.

이 문서에서 **실행 확인**은 실제 코드와 기존 테스트를 실행한 결과이며, **정적 확인**은 소스의 입력·제어 흐름·단언을 추적한 결과다. **변이 생존**은 임시 복제본의 제품 코드에 결함을 넣어도 지정한 기존 테스트가 전부 통과했다는 뜻이다. 현재 제품에 그 결함이 있다는 뜻은 아니다. 우선순위의 높음·중간·낮음은 테스트 보강 순서를 나타내며 현재 제품의 취약점 등급이 아니다.

## 발견 사항

### F01. 저장소 안 인증 상태를 거부하는 검사가 빠져 있다

**우선순위: 높음.** [저장소 검사](../scripts/toss-client.ts#L258)는 상태 디렉터리의 상위 `.git`를 확인해 저장소 안 자격 증명·토큰 저장을 거부한다. [기존 저장소 안전성 테스트](../tests/toss.test.mjs#L509)는 권한, 심볼릭 링크, FIFO를 다루지만 Git 작업 트리 안 상태를 만들지 않는다. 이 방어를 제거하는 변이는 M12다.

임시 상위 디렉터리에 `.git`를 만들고 그 아래의 보호된 합성 상태를 사용해 `AUTH_STORAGE`, HTTP 0건, 새 `state.json` 부재를 확인하는 검사가 필요하다. 일반 디렉터리의 유효 조회도 함께 유지해야 한다.

### F02. HTTP 본문 상한을 청크별 상한으로 잘못 바꾸어도 구별하지 못한다

**우선순위: 높음.** [크기 초과 사례](../tests/toss.test.mjs#L666)와 [목](../tests/toss-http-mock.mjs#L137)은 1,048,577바이트를 한 청크로 반환한다. [누적 바이트 계산](../scripts/toss-client.ts#L637)을 마지막 청크 크기의 대입으로 바꾸는 M01이 생존했다. 기존 검사는 단일 청크의 초과만 입증한다.

유효 JSON과 뒤따르는 공백을 둘 이상의 청크로 나누어, 총 1,048,576바이트는 허용하고 1바이트 초과는 `RESPONSE_INVALID`로 거부하는 기대값을 둔다. 초과 뒤 추가 GET이 없다는 사실도 대조한다. 현재 테스트 이름의 스트림 취소 오류 가림은 별도로 입증되지 않는다. 목의 `cancel()`은 요청의 `AbortSignal`에 연결되지 않았고 제품 코드는 `reader.releaseLock()`을 호출하므로, 현재 단언은 크기 거부와 출력 가림만 확인한다.

### F03. 일반 주문 권한이 조건 주문까지 허용되는 회귀를 구별하지 못한다

**우선순위: 높음.** [주문 테스트](../tests/toss-orders.test.mjs#L5)는 성공 계좌에 두 권한을 함께 부여하고 [거부 사례](../tests/toss-orders.test.mjs#L384)는 둘 다 주지 않는다. [에이전트 픽스처](../tests/toss-agent-cli.mjs#L328)는 명령 하나의 정상 권한만 확인한다. [권한 확인](../scripts/toss-client.ts#L362)에 `orders` 권한으로 `conditional-orders`를 허용하는 예외를 넣는 M04를 검사한다.

`orders`만 허용한 계좌로 `conditional-orders`를 요청하고, 역방향 조합도 각각 요청해 `ACCOUNT_SCOPE_DENIED`와 HTTP 0건을 확인한다. 자기 권한으로 정상 조회하는 사례를 함께 유지한다.

### F04. 묶음 조회의 종목별 봉 데이터 귀속을 판별할 수 없는 표본을 쓴다

**우선순위: 높음.** [다종목 정상 사례](../tests/toss-candles-batch.test.mjs#L834)는 종목마다 같은 `page()`를 사용한다. [소비자용 합성 응답](../tests/toss-agent-cli.mjs#L307)도 정상 종목에 같은 봉을 사용한다. 요청 심볼과 출력 행의 심볼·순서를 대조해도 두 성공 행의 `data`가 바뀌면 내용은 같다. [묶음 결과 조립](../scripts/toss-candles.ts#L122) 이후 비어 있지 않은 성공 행 둘의 `data`만 교환하는 M15를 검사한다.

서로 다른 종가·거래량·시각을 가진 두 종목으로 각 행의 `symbol`, `source`, `data`, `summary`를 함께 대조한다. 심볼 라벨만 맞는 결과가 통과하지 않아야 한다.

### F05. 캐시 토큰의 자체 만료를 검사하지 않는다

**우선순위: 중간.** [캐시 재사용](../tests/toss.test.mjs#L379), 공급자 401, 동시 교체는 검사하지만, [캐시 만료 판단](../scripts/toss-client.ts#L676)의 `expiresAt` 비교를 제거한 M02도 통과했다. 공급자가 만료를 통지하기 전에 로컬 만료 판단으로 재발급하는 경로가 구별되지 않는다.

짧은 수명의 합성 토큰 A를 발급한 다음 시계를 만료 이후로 옮겨 새 자식을 실행한다. 두 번째 실행이 새 토큰 B를 한 번 발급한 뒤 B로 GET을 보내는지 확인한다. 아직 유효한 A를 재사용하는 기존 검사는 유지한다.

### F06. 최근 체결의 순서 표본이 회문이다

**우선순위: 중간.** [순서·중복 보존 테스트](../tests/toss-market.test.mjs#L58)의 입력 `[A, B, A]`는 역순이어도 같다. 다른 정상 표본은 빈 배열·한 건·모두 같은 체결이다. [체결 파싱](../scripts/toss-market.ts#L51) 후 유효한 `data`만 뒤집는 M17로 순서 검출력을 확인한다. 파싱 전 입력을 뒤집는 M09는 잘못된 행의 누락 인덱스도 바꾸므로 순서만의 대조로 사용하지 않는다.

서로 다른 시각·가격을 가진 `[A, A, B]` 또는 `[A, B, A, C]`를 사용해 공급자 순서와 중복 보존을 함께 확인한다. 매수 호가도 유효 단계가 하나뿐이므로 여러 서로 다른 단계의 순서를 별도로 고정한다.

### F07. 거래 제약의 일부 미확인 값과 누락 사유를 확인하지 않는다

**우선순위: 중간.** [거래 제약 테스트](../tests/toss-sessions.test.mjs#L55)는 `availability`와 소수점 최소 금액 등을 확인하지만 일반·조건 주문 접수 시간, 수량 상하한, 소수점 최대 금액은 대조하지 않는다. [소수점 최대 금액](../scripts/toss-sessions.ts#L135)을 `unknown`에서 `100`으로 바꾸는 M07을 검사한다. 두 [필수 누락 사유](../scripts/toss-sessions.ts#L141) 중 하나가 사라져도 다른 하나 때문에 종료 코드 2는 유지된다.

계약상 미확인으로 남겨야 하는 각 필드와 두 필수 누락 사유를 독립적인 기대값으로 확인한다. 전체 객체의 구현 결과를 복사한 스냅샷 대신 합의한 미확인·공식 규칙의 경계를 검사한다.

### F08. 요청 심볼과 다른 보유·주문 응답을 섞는 회귀가 구별되지 않는다

**우선순위: 중간.** [보유 필터 사례](../tests/toss-account.test.mjs#L87)는 요청 심볼과 같은 행만 반환한다. [주문 필터 사례](../tests/toss-orders.test.mjs#L208)는 빈 페이지와 커서 재사용을 주로 확인한다. [보유 심볼 대조](../scripts/toss-account.ts#L45)와 [주문 심볼 대조](../scripts/toss-orders.ts#L191)를 각각 제거한 M05·M06으로 확인한다.

AAPL 요청에 AAPL·MSFT를 함께 반환하고 AAPL만 남는지, MSFT의 `invalid_item` 인덱스와 부분 종료 코드 2가 맞는지 검사한다. 일반·조건 주문의 경로도 각각 포함한다. 이는 공급자 요청 인자 확인과 응답 의미 확인이 다른 책임임을 드러내는 사례다.

### F09. 거래내역의 비어 있지 않은 체결단가·환율 표본이 없다

**우선순위: 중간.** [거래내역 픽스처](../tests/toss-transactions.test.mjs#L7)와 [소비자 픽스처](../tests/toss-agent-cli.mjs#L83)의 `filledPrice`·`exchangeRate`는 모두 null이다. [출력 보존](../scripts/toss-transactions.ts#L102)에서 `filledPrice`를 항상 null로 바꾸는 M13을 검사한다.

각각 다른 유효 소수 문자열의 체결단가·환율을 그대로 보존하는 매매 사례와, `amount`·`netAmount`가 null인 증권 입출고 사례를 둔다. 금액 재계산을 막는 기존 정산 금액 기대값과 함께 null·실제 값의 양쪽을 확인한다.

### F10. 인접 영업일이 요청일과 같은 경우를 검사하지 않는다

**우선순위: 중간.** [인접 객체 오류](../tests/toss-sessions.test.mjs#L250)와 [today 불일치](../tests/toss-sessions.test.mjs#L315)는 확인하지만 이전·다음 영업일이 요청일과 같거나 날짜 방향이 뒤집힌 표본이 없다. [이전 날짜 비교](../scripts/toss-sessions.ts#L25)의 `>=`를 `>`로 바꾸는 M08을 검사한다.

잘못된 인접 날짜만 제외하고 `invalid_day`와 부분 종료 코드 2를 반환하는지 확인한다. 같은 날과 반대 방향을 이전·다음 양쪽에 넣고, 유효한 휴장일 주변 사례도 유지한다.

### F11. 거래 가능 목록의 기본 ACTIVE 필터를 확인하지 않는다

**우선순위: 낮음.** [목록의 요청 인자 검사](../tests/toss-discovery.test.mjs#L50)는 `status=SCHEDULED`를 명시한다. 상태를 생략한 사례는 행·빈 결과만 확인한다. [기본값 설정](../scripts/toss-discovery.ts#L84)을 제거한 M03이 생존했다.

`tradable NASDAQ`의 실제 요청 쿼리와 `source.status` 양쪽이 `ACTIVE`인지 확인한다. 명시적으로 다른 상태를 선택하는 기존 사례와 분리한다.

### F13. 계좌 헤더가 계좌 목록 요청에도 붙는 회귀를 확인하지 않는다

**우선순위: 낮음.** [계좌 헤더 검사](../tests/toss-account.test.mjs#L97)는 최종 금융 요청을 본다. [HTTP 목](../tests/toss-http-mock.mjs#L97)은 헤더를 기록하지만 계좌 목록에 없어야 한다는 단언은 없다. [계좌 목록 조회](../scripts/toss-client.ts#L320)에 선택 계좌를 전달하는 M14를 검사한다.

토큰 발급·계좌 목록에는 계좌 헤더가 없고 금융 요청·재시도에는 선택 계좌가 있는지, 경로·메서드·헤더의 쌍을 대조한다. 이 발견은 새 계좌로의 정보 유출이 재현됐다는 뜻이 아니라 문서화한 헤더 범위의 회귀 방지 공백이다.

### F14. 테스트 도우미가 타임아웃 뒤 종료 처리를 마치기 전에 거부된다

**우선순위: 중간, 실행 재현.** [watchdog](../tests/toss-cli-helper.mjs#L53)은 `SIGKILL` 직후 Promise를 거부한다. 호출자의 `finally`에서 fixture가 지워진 뒤 [close 처리](../tests/toss-cli-helper.mjs#L58)가 trace를 읽으면 두 번째 오류가 발생한다.

기존 `runCli`에 합성 `{ hang: true }`, `TEST_REAL_CLOCK=1`을 전달하고, 거부를 받은 호출자가 `finally`에서 `f.close()`하는 작은 외부 재현을 실행했다. stdout에는 `EXPECTED_TIMEOUT: CLI test timed out`, stderr에는 `readRequests`에서 발생한 처리되지 않은 `ENOENT`가 남고 종료 코드 1이었다. 정상 응답을 같은 도우미로 실행한 대조는 종료 코드 0이었다. 이 결과는 재현한 실패 경로 한 번의 관찰이며 평상시 테스트의 간헐 실패율을 측정한 결과는 아니다.

타임아웃 사실은 기록하되 자식의 `close`와 필요한 trace 처리를 마친 후 Promise를 거부하도록 수명을 정리한다. 게이트를 소유한 테스트도 실패 시 게이트를 열고 자식을 회수해야 한다. [동시 교체 테스트](../tests/toss.test.mjs#L465)는 peer 실패 때 첫 자식의 정리를 별도로 보장하지 않는 반면 [다른 peer 사례](../tests/toss.test.mjs#L657)는 이를 처리한다. 실제 수정과 회귀 테스트는 이번 감사에서 수행하지 않았다.

## 유지할 검사와 제외한 주장

명령마다 반복되는 권한·HTTP·진단 검사는 각 명령이 공통 처리에 연결되는지 확인하므로 중복이라는 이유만으로 삭제할 근거가 없다. 일봉·분봉의 경계, 가격 경과 시간과 임계값 판정, 상태 파일 읽기·쓰기 한도, 같은 프로세스와 다른 프로세스의 호출 간격도 다른 계약이다. 기본 전체 검사와 pre-push 전체 검사의 중복은 [이미 기록된 결정](development.md#단일-전체-검사-실험-2026-11-14)이므로 감사에서 제거를 권하지 않는다.

초기 후보 F12는 제외했다. CLI 경과 시간 표본만 보면 정수 반올림을 놓치지만, 같은 `priceAge` 함수를 실행하는 [소비자의 소수초 기대값](../tests/price-consumer.test.mjs#L59)이 M16을 검출했다. 실제 실패는 `seconds`의 기대값 `900.000000001`과 관측값 `900`의 불일치였다. 테스트 파일 하나의 공백을 제품 전체의 검증 공백으로 확대하지 않았다. 발견 ID는 이 판단 이력을 보존하기 위해 다시 매기지 않았다.

폐기한 KIS·내장 추천 제품의 관문을 요구하는 활성 테스트는 검토한 범위에서 찾지 못했다. 테스트 파일의 줄 수·개수나 통과 개수를 완전성 지표로 해석하지 않았고, 커버리지 백분율·전체 변이 점수·간헐 실패율·성능 향상 수치를 산출하지 않았다.

실제 토스 응답의 최신 스키마, 공급자 자료 전달 허용, 조회 전용 권한, 실제 계좌·시장 및 Codex·Dot 연결은 실행하지 않았다. 과거 실연동 기록을 이번 합성 감사의 새 실행 증거로 계산하지 않았다.

## 재현과 원본 보존

실행 로그·명령 argv·작업 디렉터리·종료 코드, GitHub 본문·댓글 원본, 선택 소스 41개의 SHA-256, 변이 명세와 변이별 stdout·stderr·상태는 저장소 밖의 접근 제한 임시 증거 디렉터리에 보관한다. 증거 경로는 이 감사의 전달 메시지에 연결한다. 이 문서에 개인 상태 경로나 실제 자격 증명을 포함하지 않았다. 실행 전후 선택 소스 41개의 SHA-256이 모두 같았고 HEAD도 유지됐다. 테스트·보조 파일 21개의 전독 범위는 총 7,805줄이다. 이 비교를 선택하지 않은 파일·설치 의존성 전체의 불변 증명으로 확대하지 않는다.

변이는 공용 `mutation-probe.py --batch`로 실행했다. 원본의 명시된 일반 파일만 복사하고 설치된 `node_modules`는 읽기 용도로 연결했다. 각 배치는 무변이 기준 실행을 통과한 뒤 나머지 변이에서 그 기준 실행만 재사용하며, 변이별 제품·소비자 테스트는 다시 실행한다. 변이 대상은 제품 코드뿐이고 기존 테스트는 수정하지 않았다. 변이가 끝난 뒤 복제본은 제거하고 로그는 보존한다. 개발 도구 테스트 42개는 제품 코드 변이 대상에 포함하지 않았으며 기존 전체 실행에서 확인했다.

세 읽기 전용 `reviewer`가 전송·시장·계좌 영역을 분담하고 주 세션이 소비자·개발 도구와 실행·최종 판단을 담당했다. 세 역할의 선택은 세션 헤더에서 확인했다. 요청한 reasoning effort는 모두 `high`이며 실제 모델·effort·별도 권한 강제는 독립적으로 확인하지 않았다. 탐색용 `file_scout`는 읽기 전용 인벤토리만 반환했고 역할 선택도 세션 헤더에서 확인했다. `file_scout`의 요청 effort는 파일 간 관계 추적 때문에 기본 `low`에서 `medium`으로 높였다. 위임받은 검토·탐색 에이전트는 파일 변경·제품 코드 실행·네트워크 명령을 수행하지 않았다.

## 후속 작업 순서

1. 인증 저장 경계·누적 본문 상한·형제 권한 분리·종목별 데이터 귀속의 독립 표본을 보강한다.
2. 도우미의 자식 종료 수명을 바로잡고 timeout 재현을 회귀 검사로 남긴다.
3. 만료 토큰·체결 순서·미확인 제약·응답 심볼·유효 체결단가·인접 날짜·기본 필터·헤더 범위를 보강한다.
4. peer 준비 신호와 순차성 검사를 결정적인 관찰로 바꾸고, 순환 오류 기대값과 실제 중복만 정리한다.

이 순서는 수정 제안이며 이번 감사에서는 제품·테스트 수정을 수행하지 않았다. 보고서만으로 실제 서비스 인수나 출시 가능 여부를 판정하지 않는다.
