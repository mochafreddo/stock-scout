[#297](https://github.com/mochafreddo/stock-scout/issues/297)의 2026-11-10 KST 검증 기록이다. [#278의 전환 명세](https://github.com/mochafreddo/stock-scout/issues/278)와 [#283의 확정 계약](https://github.com/mochafreddo/stock-scout/issues/283#issuecomment-6686267791)을 적용한다. 계획 당시 코드 기준 `ef64daa3d663e13af8e34001609aa5da4990dcc4`에서 착수 시 기준은 `d2359555132132a52a64290632ecbf953a8fca96`으로 바뀌었고, 갱신한 `origin/main`과 같았으며 작업 트리는 깨끗했다. 제품 코드 변경 없이 기존 CLI의 실제 응답을 대조했다.

## 승인과 실행 범위

선행 [시장 검증 #296](toss-market-validation.md)은 완료됐다. [접근 준비 #294](toss-access-readiness.md)의 기존 승인은 `holdings`·`buying-power`에 한정돼 있어, 사용자가 이번 실행 전에 다음 범위를 추가 승인했다.

- 기존 기본 계좌 `primary`와 보호 위치·자격 증명을 재사용하고, 공통 인증 모듈의 필요시 토큰 갱신을 허용한다.
- 로컬 허용 범위에 `transactions`·`orders`·`conditional-orders`를 추가한다. 선택 파일을 같은 보호 위치에 먼저 백업한 뒤 기존 `TossClient.selectAccount`로 범위를 저장했다. 보호 디렉터리는 0700, 선택 파일과 백업은 0600을 확인했다. 실제 경로와 식별자는 공유 기록에 포함하지 않는다.
- 보유·USD/KRW 매수 가능 금액, 2026-10-11~2026-11-10 거래내역, 일반·조건 주문의 OPEN/CLOSED를 조회한다. 각 목록은 첫 페이지와 실제 다음 페이지까지, 전체 CLI 실행은 최대 12회로 제한한다.
- 금융 응답은 메모리에서만 대조하고 대화·파일·로그에는 통과 여부와 미관측 항목을 남긴다. 공급자가 강제하는 조회 전용 권한과 자료별 처리·보관 조건의 남은 미확인은 기존 사용자 재결정의 범위로 유지한다.

공개 검증 경계는 CLI 인수·stdout JSON·stderr·종료 코드·외부 HTTP다. 계좌 원문·키·토큰·금융 원자료를 이 문서에 포함하지 않는다. 주문 제출·정정·취소, 다른 계좌 선택, 신규 키 발급은 수행하지 않았다.

## 실제 관측

2026-11-10 20:28:57~20:29:20 KST에 CLI 10회를 순차 실행했다. 아래 인수는 `node scripts/toss.ts` 뒤에 붙인다. 페이지가 있는 명령에는 `limit=1`을 사용해 실제 다음 페이지의 관측 가능성을 높였다. 일반 주문에는 `from=2026-10-11 to=2026-11-10`을 적용했다. 조건 주문은 날짜 필터를 지원하지 않으므로 전체 제공 범위를 조회했다.

모든 실행에서 계좌 목록과 금융 조회의 HTTP 200, `source.accountAlias=primary`, 선택 계좌와 조회 헤더의 일치, 한 줄 stdout JSON과 빈 stderr를 확인했다. CLI가 반환하는 문서상 필드 전체를 원응답에서 직접 선택해 대조했으며 제품의 응답 변환 함수를 대조기에 재사용하지 않았다. 추가 공급자 필드는 대조 대상에서 제외했다. 소수 문자열·null·선택 필드의 생략을 보존했는지 확인했으며 금액을 재계산하지 않았다.

거래내역과 일반 종료 주문은 첫 응답의 `nextCursor`·`context`를 메모리에서 다음 CLI 인수로 전달했다. 실제 HTTP에 같은 커서가 전달되고 응답의 `hasNext`·`nextCursor`가 출력에 보존됨을 확인했다. 두 번째 페이지에도 `hasNext=true`와 `partial`·종료 코드 2를 확인했다. `next_page` 사유는 제품 코드 경로에서 확인했으며 실행 요약에는 누락 사유 배열을 저장하지 않았다. 각 페이지는 최대 한 항목이므로 복수 행의 실제 정렬은 검증하지 않았고 페이지 사이의 연결만 확인했다. 승인된 두 페이지까지만 확인했으며 기간 전체를 조회한 결과로 표시하지 않는다. 조건 주문은 두 그룹 모두 다음 페이지가 없어 페이지 연결을 입증하지 못했다.

## 대조 방법과 증거의 한계

실제 `fetch`를 호출하는 관측 모듈이 GET 응답의 복사본을 메모리 파이프로 부모 프로세스에 전달했다. 부모 프로세스는 변경하지 않은 CLI stdout·stderr·종료 코드를 수집해 대조했다. 인증 응답과 인증 헤더는 관측 출력에 포함하지 않았다. 이 방식은 실제 HTTP와 CLI 출력의 보존을 확인한 것이며, 별도 공급자나 앱의 독립 잔고·거래 원장과 대조한 결과는 아니다.

대조기의 합성 음성 대조 7개는 수량·정산 금액·결제일·결제 상태·처리 시각 변경, 항목 수 변경, 주문 순서 변경을 각각 거부했다. 이는 대조기의 검출 확인이며 실제 금융값이나 모든 상태 조합을 검증한 결과가 아니다. 제품 결함은 발견하지 않아 제품 코드·회귀 테스트를 수정하지 않았다.

stdout에서 계좌 식별자·자격 증명 키가 없고 조회한 계좌번호 문자열이 포함되지 않음을 확인했다. 원응답의 복사본·stdout·페이지 커서는 메모리에만 두었으며 실행 결과 파일에는 비식별 관측 요약만 저장했다. 기존 CLI의 저장 경로도 확인했으며 공통 모듈은 인증·호출 간격 상태와 선택 정보를 저장하고 금융 응답을 저장하지 않는다. 이는 실행기와 코드 경로에 대한 확인이며 운영체제 전체의 임시 저장·외부 제품 보관 정책을 감사한 결과는 아니다.

의미 해석은 [CLI의 계좌·거래내역·주문 계약](toss-cli.md#기본-계좌와-보유매수-가능-금액)을 따른다. 거래내역의 기간은 KST 결제일 기준이며 `settled`와 결제 처리 시각은 주문 생성·체결 시각과 다르다. 일반 주문의 날짜 필터는 `orderedAt`, 조건 주문의 등록 시각은 `createdAt`이다. 거래내역의 정산 금액 `netAmount`와 일반 주문의 `currency`·체결 금액 `execution.filledAmount`는 각각 원문을 보존하고, 통화 필드가 없는 조건 주문에는 통화를 추가하지 않았다. 각 필드가 실제로 가리키는 업무 사건을 앱·독립 원장으로 확인하거나 모든 결제·주문 상태를 관측한 것은 아니다.

## 2026-11-10 첫 인수 조건 재결정

사용자는 조건 주문의 실제 다음 페이지 표본을 첫 인수의 필수 조건에서 제외하고, 미관측 한계를 남긴 채 #297을 인수하는 방향에 동의했다. 거래내역·일반 종료 주문의 실제 다음 페이지와 종료 조건 주문의 실제 항목은 관측했지만, 조건 주문은 다음 페이지가 없어 관측하지 못했다. 표본을 만들기 위한 주문 등록 없이 첫 인수를 판단하기 위한 조건 변경이며, 합성 검사를 실제 페이지 관측으로 인정한 결정은 아니다.

조건 주문의 페이지 기능과 기존 합성 CLI 검사는 유지한다. 조건 주문의 실제 다음 페이지와 진행 중 일반·조건 주문의 항목·세부 상태는 미관측으로 남기고, 향후 승인된 조회에서 표본을 확보하면 추가 대조한다. 추가 실계좌 조회나 인증 변경을 승인한 결정은 아니다.

개정한 인수 조건 3은 거래내역·일반 종료 주문의 실제 다음 페이지 연결과 의미 대조를 요구하되, 조건 주문의 실제 다음 페이지 표본 부재는 첫 인수의 차단에서 제외한다. 기존 관측 근거에 따라 개정한 조건 3을 충족한 것으로 평가하며, #297은 이 미관측 한계를 포함해 첫 인수 대상으로 수용한다. 이슈의 게시·종료 상태는 #297에서 확인한다. 공급자 허용·권한의 남은 미확인과 Codex·Dot의 실제 자료 사용, 최종 전환 및 기존 KIS·내장 모델 제거의 별도 관문은 유지한다.
