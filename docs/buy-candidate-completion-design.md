# 실제 매수 후보 보고서 완료를 위한 실행 개선 설계

2026-10-31 #240의 설계 인터뷰에서 Q1~Q9의 권고안을 확정했다. 후속 `implement` 요청은 이 설계의 로컬 구현·검증·최대 6회 실제 검증·코드 리뷰·현재 브랜치 커밋을 승인했다. 푸시·원격 이슈 변경·종료는 포함하지 않는다. 실행 결과와 한계는 [보고서 실행 안내](buy-candidates.md)에 별도로 남긴다.

## 목표와 근거

기존 보고서 계약을 충족하는 실제 실행을 먼저 확보한다. 추천 전략 변경, 추천 유용성 평가와 제품 인수는 별도다. 정상적인 후보 없음 보고서는 완료로 인정하지만 유형 판단의 분석 불충분은 최종 보고서 완료로 인정하지 않는다. 정상 빈 후보군도 기존 후보 선정·의미 검토 경로를 거쳐 보고서를 만든다. 이 경로가 완료되어도 적격 종목의 실제 일봉 조회와 그 자료를 사용한 추천까지 확인한 것으로 확대하지 않는다.

검토 기준은 `33a1b316dd743e3d826056b52471596a491b454b`와 이번에 읽은 [#237](https://github.com/mochafreddo/stock-scout/issues/237)·[#240](https://github.com/mochafreddo/stock-scout/issues/240)의 본문이다. 두 이슈에는 조회 시 댓글이 없었다. [기존 실행 기록](buy-candidates.md#2026-10-31-시간예산-관측-보강-후-분리-검증)의 고정 6종목 유형 실행은 모델 요청 5개 구간의 합이 179,358ms, KIS HTTP 6개의 합이 543ms였으며 유형 단계 제한으로 끝났다. 전체 통합 실행은 수집 18,083ms 뒤 일정 모델 요청이 179,993ms에 취소됐다. 서로 다른 입력·경로의 실패이며 공급자 내부 검색·추론·대기 원인은 확인하지 못했다.

응답 반복과 필요한 정보 조회의 모델 왕복을 줄이는 변경은 개선 가설이다. 처리 시간·완료율 개선을 측정한 결과가 아니며, KIS 선조회나 한도 확대가 해결책이라고 가정하지 않는다.

## 일정 판단의 내부 응답

수집 범위와 공지 본문 전체, 부모·자식 관계, 공지마다 한 번의 판단, 모든 자식의 근거, 공지 사이의 정정·철회 처리를 유지한다. 제목 기반 제외, 본문 요약·누락, 분할 판단과 실행 사이의 판단 캐시는 추가하지 않는다. 일정 모델 요청 상한은 한 번이다.

내부 응답은 루트 객체를 유지하고 그 안의 상태별 항목 구조를 바꿔 적용하지 않는 변경 목록과 적용일의 반복을 없앤다. 모든 판단에는 식별자·상태·짧은 이유·근거 구간 ID·대체하는 공지 참조 목록이 필요하다. 대체 참조가 없으면 빈 목록이다. 일정 변경에는 구체적인 변경 목록, 미래 적용에는 적용일을 추가하며 다른 상태에는 해당 필드를 두지 않는다. 구조화 출력이 허용하는 분기 스키마를 사용하고 각 분기 안의 필드는 모두 필수로 선언한다. 코드는 허용한 상태별 필드만 검증하고 기존 공개 결과의 빈 배열·`null`과 원본 식별자·인용을 복원한다. 철회는 기존처럼 일정 영향 없음과 대체 참조로 표현할 수 있다. 필요한 필드의 누락, 잘못된 상태 조합, 미등록·중복 참조와 자신 또는 명시적으로 대체하는 공지에 속하지 않는 근거 참조를 복원 과정으로 숨기지 않는다. 공급자가 변경한 분기 스키마를 실제로 수용하는지는 다음 실제 검증에서 확인한다.

기존 구간 ID처럼 공지 ID와 정정 참조도 요청 안에서만 유효한 짧은 ID로 전달하고 코드가 원래 ID로 복원한다. 근거 구간은 원문과 연결된 기존 방식을 재사용한다. 공개 일정 결과와 근거 검증의 의미는 유지하며 구간 소속과 정정 관계를 복원한 뒤 검사한다. 결과가 간결해져도 선택한 근거의 의미적 타당성은 별도 확인 대상이다.

## 필요한 종목 정보의 묶음 조회

모델이 필요한 입력 종목들을 한 번에 요청하는 `get_infos`로 내부의 단일 종목 `get_info` 도구를 교체한다. 모든 종목을 미리 조회하지 않는다. 모델이 유형과 필요한 자료를 판단하고 코드는 조회·제한·출처 등록을 맡는다. 기존 `queryKis('info', ...)`와 인증·제한 재시도 정책을 재사용한다.

요청은 비어 있지 않은 중복 없는 거래소·종목 코드 목록이다. 각 종목이 현재 입력에 속하는지와 정보 조회 32회 한도에 들어가는지를 첫 HTTP 요청 전에 검사한다. 묶음 하나를 종목 수와 관계없이 한 번으로 계산하지 않는다. 기존 `infoToolCalls`는 스키마에 맞는 도구 호출에서 요청한 종목 수를 누적하며 사전 거부와 중간 실패 뒤 아직 시작하지 않은 항목도 포함한다. 이는 실제 전송 횟수가 아니며 기존 단건 도구의 한도 초과 시도도 통계에 포함하던 의미를 유지한다. 정보 조회 32회 한도는 실제로 시작하는 종목별 논리 조회에 적용하고, KIS 90회는 인증·허용된 재조회까지 실제 전송마다 센다. 모델 요청·웹 이벤트 상한은 그대로다.

묶음 안에서는 순차 조회한다. 각 조회 전에 남은 시간과 전송 예산을 검사하고 같은 취소 신호를 전달한다. 결과는 요청 순서대로 종목별 자료 또는 기존 개별 조회 실패를 반환하며 성공한 자료마다 기존 출처 ID를 부여한다. 개별 404는 해당 종목의 조회 실패로 남기고 다른 종목을 계속 처리한다. 인증·공통 조회 장애·취소·한도 도달은 묶음과 전체 분석을 실패로 종료한다. 이를 개별 자료 부족으로 바꾸지 않는다. 반복 도구 요청은 기존 한도에 계속 포함하며 별도 캐시를 만들지 않는다.

기존 `list_sources`와 실제 열람한 웹 출처 연결을 유지한다. KIS 코드 `01`·이름·검색 요약·모델 기억만으로 보통주를 확정하지 않는다. 개별 증권 연결, ADR 기초 권리, 현재 적용 여부와 알려진 반대 근거를 확인하는 기준도 유지한다. 폐기한 내부 단일 종목 도구를 호환 경로로 남기지 않는다.

## 단계별 모델 선택

후보군·보고서 공용 CLI는 필수 `--model`을 모든 단계의 기본값으로 유지하고 선택 인수 `--calendar-model`, `--type-model`로 해당 단계만 명시적으로 덮어쓴다. 인수의 누락 값·중복·형식상 잘못된 모델 식별자는 외부 요청 전에 거부한다. 독립 일정·유형 CLI는 기존 `--model`을 사용한다. 후보 선정과 별도 의미 검토는 같은 `--model`을 사용한다.

첫 검증 후보는 일정·후보 선정·의미 검토에 `gpt-6.1-sol`, 유형 판단에 `gpt-6-luna`다. 보고서 경로에서는 `--model gpt-6.1-sol --type-model gpt-6-luna`를 명시한다. 명시적 선택을 런타임 자동 모델 교체로 확대하지 않는다.

[공식 모델 조회 절차](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference)에 따라 기존 인증의 현재 계정 목록을 확인한다. 목록 조회는 추론·검색·도구·구조화 출력의 호환성 증거가 아니다. 변경한 단계의 실제 검증을 통과해야 해당 조합을 채택하며 사용할 수 없으면 중단하고 선택을 다시 결정한다. 실제 사용한 모델은 기존 일정 `noticeAssessment.model`, 유형 `typeAssessment.model.id`, 보고서 `model.id`에 각각 기록한다. 전역 모델 하나로 모든 단계를 표현하지 않는다.

과거 Luna의 작은 일정 표본 통과를 전체 입력 품질로 확대하지 않는다. 전체 입력에서 자식 근거 누락과 실제 운영 변경 오판이 있었으므로 일정의 첫 후보는 Sol로 유지한다. 유형의 기존 AAPL·BBD·BBDO 점검 결과도 변경된 묶음 조회 경로의 검증을 대신하지 않는다. 새 로그인·인증 경로·유료 API 전환은 추가하지 않는다.

## 시간과 요청 예산

전체 실행 600초와 판단 대상 개장 중 이른 마감을 유지한다. 첫 검증에서는 일정 전체 300초·수집 120초·일정 모델 최대 180초, 유형 180초, 추천·의미 검토 합계 180초를 유지한다. 독립 CLI에 통합 실행의 600초를 새로 적용하지 않는다. 단계별 상한은 최악 시간을 모두 보장하는 예약 시간이 아니며 전체 잔여 시간과 함께 적용한다.

첫 변경에서 단계별 180초도 유지하는 것은 구조·모델 변경의 결과를 기존 제한과 비교하기 위한 선택이다. 전체 잔여 시간을 소진하지 않은 단계 마감 실패가 다시 발생하면 실제 소요·입력·요청 수·뒤 단계에 필요한 시간을 근거로 배분을 재결정한다. 자동 한도 확대와 다른 단계의 요청 예산 차용은 하지 않는다. 일정 1회·유형 12회·추천 4회, KIS 90회·발급 2회, 일정 HTTP 100회·SIWC 갱신 2회와 기존 웹 이벤트 상한은 유지한다.

## 공개 경계와 검증

검증 경계는 CLI 인수·stdout·stderr·종료 코드와 외부 HTTP 요청이다. 기존 테스트 파일에서 영향받는 사례를 수정·추가하며 내부 함수 배치를 고정하는 새 평가 프레임워크는 만들지 않는다. 문서의 문구를 고정하는 검사는 만들지 않는다.

- 일정: 상태별 간결한 응답을 기존 공개 결과로 복원하고 모든 공지·자식 근거와 정정·철회 관계를 보존한다. 누락·중복·잘못된 참조·상태별 필수 값 누락과 정상 JSON 뒤 오류·완료 없는 EOF를 거부한다.
- 묶음 조회: 요청 종목만 순서대로 전송하고 개별 출처와 실패를 보존한다. 입력 밖 종목·중복·빈 목록은 조회 전에 거부한다. 종목별 정보 한도, 실제 KIS 전송 한도, 중간 취소·공통 실패 뒤 추가 전송 금지를 확인한다. 모델이 정보를 요청하지 않는 경로에서 선조회가 생기지 않아야 한다.
- 모델 전달: 외부 Responses 요청의 모델이 단계별 선택과 일치하고 생략한 선택 인수는 기존 `--model`을 사용한다. 잘못된 인수는 외부 요청 없이 실패한다. 공개 출력의 단계별 모델 출처도 확인한다.
- 보고서: 기존 정상 추천·후보 없음·분석 불충분·최대 후보 수·일봉 날짜와 필드·별도 의미 검토·개장 경계·명시적 완료와 빈 실패 stdout 계약을 유지한다.

영향받는 검사를 개발 중 수행하고 최종 검토·수정 후 형식·린트·타입·전체 모의 검사를 수행한다. 새 회귀의 수정 전 실패와 위험 경계의 음성 대조는 기존 mutation-probe 절차로 확인한다. 실제 실행은 고정한 소스에서 수행하고, 수정 후에는 영향받는 검사와 최종 검증 결과를 갱신한다. 모의 검사와 실제 서비스 결과를 구분한다.

## 다음 구현의 실제 검증 계획

추가 실제 호출은 이번 문서 작성에 포함하지 않는다. 다음 구현 요청에서 기존 승인 보관소의 인증과 위 모델·시간·요청 한도로 다음 계획을 적용한다. 최대 6회는 최상위 검증 실행 수이며 한 실행 안의 모델 전송 수는 기존 단계별 상한으로 별도 제한한다. 현재 계정 모델 목록 확인은 별도 인증 확인이며 검증 실행 6회와 구분해 기록한다. 과거 승인분의 남은 횟수를 이번 계획에 더하지 않는다.

모든 최상위 검증 실행은 실패·중단도 횟수에 포함한다. 실패하면 원인을 확인하기 전까지 후속 실행을 멈춘다. 계획한 필수 검증이 완료되면 남은 예비 재확인을 소비하지 않는다. 한 번의 추가 재확인으로 영향받은 범위를 확인할 수 없으면 부분 검증으로 남기고 다음 실행 범위를 다시 결정한다. 근거 없는 동일 실행 반복이나 모델 후보 전수 탐색은 하지 않는다.

각 실행의 소스 지문·모델·설정·명령·시각·종료 코드·안전한 진단·단계별 시간과 호출 수를 저장소 밖 소유자 전용 기록에 보존한다. 실패와 근거 심사 결과를 숨기지 않는다. 유형 실행에서는 실제로 다종목 `get_infos`를 요청했는지 관측한다. 모델이 요청하지 않았으면 해당 경로는 모의 검증만 완료한 것으로 남기며 횟수를 채우기 위해 추가 실행하지 않는다. 정상 빈 후보군과 적격 종목의 일봉을 사용한 보고서를 구분하고 후보 선정·의미 검토의 실제 요청·완료를 각각 확인한다. 전체 보고서 완료를 확인하기 전에는 #240의 남은 조건을 완료로 바꾸지 않으며 이슈 종료와 추천 유용성·제품 인수는 별도다.

## 확정한 변경 범위

구현 대상은 일정 판단의 내부 응답·검증, 공용 유형 정보 도구, 공용 후보군·보고서 CLI의 모델 전달, 해당 공개 경계 테스트와 사용 문서다. 공통 관측은 묶음의 실제 종목 수와 기존 한도 의미를 보존하는 데 필요한 범위만 수정한다. 인증·시세 공급자·탐색 N·일봉 기간·주문 기능은 이번 변경 대상에 추가하지 않는다.

이번 설계에는 새 도메인 개념이 없어 기존 용어집을 유지한다. 내부 프로토콜·명시적 모델 인수·첫 검증값은 되돌릴 수 있는 실행 설계이므로 별도 ADR을 추가하지 않는다. 기존 ADR의 도메인·출처·실패 계약은 유지하며 실제 검증 뒤 장기 구조 결정이 생기면 ADR 필요성을 다시 판단한다.

설계 확정 뒤의 구현 범위는 위 공용 경로와 공개 경계 검증·사용 문서·현재 브랜치 커밋이다. 실제 호출은 위 계획의 최대 6회와 기존 인증·한도를 따른다. 푸시·원격 이슈 반영·종료는 별도 요청 범위다.
