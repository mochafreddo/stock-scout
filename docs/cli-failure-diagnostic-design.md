# 모든 CLI 실패의 기본 진단 계약

[#262](https://github.com/mochafreddo/stock-scout/issues/262)의 2026-10-21 설계 인터뷰 기록이다. 상위 [#258](https://github.com/mochafreddo/stock-scout/issues/258)과 [기존 진단 설계](security-type-diagnostics-design.md)를 구체화한다. 사용자는 Q7에서 Q1~Q6과 작업 범위·공개 검증 경계·리뷰 기준을 확정하고 `to-spec`으로 #262 명세 게시와 `ready-for-agent` 라벨 적용을 요청했다. 구현·실연동·커밋·푸시·이슈 종료 승인은 포함하지 않는다.

## 확정 사항

Q1에서 실패의 `diagnostic` 객체는 `stage`, `reason`, `location` 세 필드를 항상 제공하기로 합의했다. 단계는 `input`, `authentication`, `ranking`, `retrieval`, `judgment`, `output`으로 구분한다. 단계 자체를 특정하지 못하면 `stage`는 `unknown`이다. `location`은 확인된 안전한 경로 또는 `null`이다. 시간·호출 통계는 후속 티켓에서 추가한다.

```json
{
  "diagnostic": {
    "stage": "retrieval",
    "reason": "unknown",
    "location": null
  }
}
```

Q2에서 기존 오류 코드가 원인을 명확하게 나타내면 코드가 정한 고정 식별자로 전달하기로 합의했다. `MODEL_OUTPUT`처럼 여러 거부 조건을 묶는 코드만으로 세부 원인을 추정하지 않으며 이 경우 `reason`은 `unknown`이다. 실패 단계는 원인과 별도로 전달하여 자료 조회와 최종 판단을 구분한다. 필드 누락·근거 ID 오류 등의 세분화는 후속 범위로 유지한다. 식별자의 신뢰 기준과 기존 철자의 재사용은 Q6을 따른다.

Q3에서 기본 진단의 보장 범위는 CLI 애플리케이션이 처리할 수 있는 실패와 예상하지 못한 예외로 정했다. 실행 전 런타임·모듈 로딩 실패, 프로세스 강제 종료, 진단 출력 자체의 실패는 보장 범위에서 제외한다. 이를 포괄하기 위한 별도 실행기는 추가하지 않는다.

Q4에서 `stage`는 실패 당시 실행하던 단계로 정했다. 초기 인증 준비 실패는 `authentication`, 자료 조회 중 KIS 인증 실패는 `retrieval`로 표시하며 후자의 `reason`에는 확인된 인증 실패 식별자를 사용한다. 오류 코드만 보고 실행 단계를 바꾸지 않는다.

Q5에서 단계의 경계를 다음과 같이 확정했다. 근거 검증을 마쳐야 `judgment`로, 판단 결과 검증을 마쳐야 `output`으로 넘어간다. 예상하지 못한 예외도 실행 단계가 확인되면 해당 단계를 유지하며 확인되지 않을 때만 `unknown`으로 표시한다.

| 단계 | 포함하는 작업 |
| --- | --- |
| `input` | 인수·평가 파일 읽기와 검사 |
| `authentication` | 초기 인증 준비 |
| `ranking` | 순위 수집·검사와 입력 종목 구성 |
| `retrieval` | 조회 준비·실행과 근거 검증 |
| `judgment` | 최종 판단 준비·실행과 판단 결과 검증 |
| `output` | 최종 출력 객체 구성·민감값 검사·직렬화 |

Q6에서 코드 내부에서 확인한 실패 조건에만 고정 원인 식별자를 부여하기로 합의했다. 기존 식별자를 재사용할 때는 철자도 유지한다. 여러 원인을 묶은 오류나 미등록 예외는 `reason: "unknown"`으로 표시한다. 외부 메시지의 내용이나 접두사로 원인을 추측하지 않는다. 기존 오류 출력의 호환 동작과 진단 원인의 확실성은 구분하며 미등록 예외의 기존 `error: "MODEL_FAILED"`만으로 진단 원인을 확정하지 않는다.

## 유지하는 상위 계약

기존 stderr 필드·오류 코드·종료 코드·성공 출력·실패 stdout 계약과 인증 실패의 재시도 시각·로그인 안내를 유지한다. 정상적인 분석 불충분을 새 실패로 바꾸지 않는다. 기존 검증 순서에서 최초로 발견한 거부 조건 하나만 보고하며 추가 오류를 찾기 위한 검증은 하지 않는다.

`location`은 오류가 발생한 응답 배열·필드의 경로다. 배열 번호는 0부터 시작하며 입력 종목 순번과 구분한다. 코드가 아는 필드명과 숫자만 사용하며 모델이 보낸 필드명·값·URL·원문은 포함하지 않는다. 위치를 특정할 수 없으면 `null`이다. 진단에 모델 응답 원문·외부 오류 메시지·인증 값·개인 경로를 넣지 않는다.

진단을 위한 모델 호출·조회·재시도를 추가하거나 기존 호출·시간 한도를 변경하지 않는다. 상세 거부 사유와 단계별 시간·호출 통계는 후속 범위다. 실제 실패 진단·고정 표본 평가·#250 완료 선언은 이번 범위가 아니다.

## 최종 확정과 게시 범위

Q7에서 Q1~Q6과 이 로컬 설계 문서의 확정을 수락했다. 이어 요청한 `to-spec`의 게시 범위는 #262 본문과 `ready-for-agent` 라벨이다. 구현·실연동·커밋·푸시·이슈 종료는 포함하지 않는다. 게시 요청과 원격 반영 성공은 구분하며 실제 게시 결과는 별도로 확인한다.

2026-10-21 #262 명세를 게시하고 원격 본문과 제안 본문의 정확한 일치를 확인했다. 기존 `ready-for-agent` 라벨과 OPEN 상태를 유지했다. 기존 완료 조건 일곱 개의 문구·순서·미완료 상태를 보존하고 이번 합의를 구체화한 네 조건을 추가했으며 열한 조건 모두 미완료다. 이번 작업은 설계·명세 게시에 한정하여 코드 테스트·실연동·커밋·푸시는 수행하지 않았다.

향후 #262 구현의 공개 검증 경계는 CLI 입력·stdout·stderr·종료 코드와 외부 HTTP 요청이다. 여섯 단계의 대표 실패·미등록 예외·원인과 단계의 구분·민감정보 비노출·기존 성공과 분석 불충분을 이 경계에서 확인한다. 기존 호출 수와 외부 요청 인자의 보존도 확인하며 내부 함수 배치나 문서 문구를 고정하지 않는다. 구현 검증에는 #262의 수정 전 회귀 실패·필요한 형식·린트·타입·전체 테스트·위험 로직 음성 대조·고정 변경본의 Standards·Spec 리뷰를 적용한다. 모의 검사와 실제 서비스 검증을 구분한다.

이번 설계의 리뷰 기준점은 `41a4188e0413a95dc6757658c1e4d99a492f8859`와 이 파일 생성 직전의 작업 트리다. 향후 구현의 티켓상 리뷰 기준점도 같은 SHA이며 작업 시작 시 선행 티켓과 동시 변경을 구분하여 관련 변경을 고정한다. 기존 미커밋 설계 문서는 이번 인터뷰의 수정·리뷰 범위에 포함하지 않는다.

## 확인한 현재 동작

인터뷰 시작 HEAD는 `41a4188e0413a95dc6757658c1e4d99a492f8859`다. `scripts/llm-security-probe.ts`의 최상위 오류 처리에서 기존 `error`와 인증 관련 `retryAt`·로그인 안내를 출력한다. 현재 진단 객체는 없으며 미등록 예외는 `MODEL_FAILED`로 출력한다. `scripts/security-type-assessment.ts`는 조회와 최종 판단을 분리하지만 실패 단계가 CLI 오류 처리까지 전달되지는 않는다. 이 내용은 소스 조사 결과이며 실제 서비스 실행 결과가 아니다.

현재 CLI는 정적 import 이후에 최상위 오류 처리를 시작한다. 진단 출력 자체의 실패와 프로세스 강제 종료를 포함하여 모든 실패를 JSON으로 출력할 수 있다고 입증한 상태는 아니며 Q3에서 그 보장 범위를 정했다.

기존 수정·미추적 문서는 다른 설계 작업으로 보존하고 이번 인터뷰는 이 파일에 기록한다. 용어집에 추가할 새 도메인 용어나 별도 ADR이 필요한 장기 결정은 아직 확정하지 않았다.
