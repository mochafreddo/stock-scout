# RCA를 위한 공통 실행 관측 설계

2026-10-30 [#240](https://github.com/mochafreddo/stock-scout/issues/240)의 실제 실패 이후 진행한 설계 인터뷰다. 사용자는 Q1~Q6의 추천안을 모두 수락하고, 최종 제안 이후 `to-spec`으로 논의한 설계의 명세 게시와 `ready-for-agent` 라벨 적용을 요청했다. 현재 기준 소스는 `3343281ab3380f0174bdcf7595efac219acb5358`이며, 기존 [유형 판단 진단 설계](security-type-diagnostics-design.md)의 일정·추천 제외 범위를 확대하는 새 설계다. 이번 요청은 로컬 설계 기록과 별도 GitHub 명세 이슈 게시 범위이며 구현·추가 실연동·커밋·푸시·기존 이슈 변경·종료를 승인하지 않는다.

확정 명세를 [#272](https://github.com/mochafreddo/stock-scout/issues/272)에 게시했다. 원격 본문이 검토한 게시안과 바이트 단위로 일치하고 `ready-for-agent` 라벨과 OPEN 상태임을 다시 읽어 확인했다. 사용자 이야기 24개와 미완료 상태의 완료 조건 10개를 포함한다. 게시 완료는 구현이나 완료 조건 충족을 뜻하지 않는다.

## 문제와 관측 한계

[실행 기록](buy-candidates.md#승인-후-실제-실행-결과)의 통합 실행은 일정 단계의 `MODEL_INCOMPLETE`로 끝났고 KIS·유형 판단·추천은 시작되지 않았다. 일정 모델에는 유형 판단과 같은 요청별 상세 진단이 없어 기한 소진·공급자 불완전 응답·완료 이벤트 이상을 구분하지 못했다. 전체 경과 시간만으로 중단 원인을 확정하지 않는다. 추가 관측은 이후 실행에서 확인할 수 있는 클라이언트 측 사실을 늘리는 것이며 과거에 수집하지 않은 정보나 공급자 내부 원인을 복구하지 않는다.

## 합의한 관측 범위

후보군·매수 후보·유형 검증·일정 CLI가 사용하는 인증, 공식 자료 수집·파싱, KIS 요청, 모델 요청·도구 호출, 결과 검증·출력을 관측한다. 실행마다 관측 상태를 소유하는 곳을 하나로 두고 작업과 실제 요청을 연결한다. 기존 완료 판정·호출 상한·시간 제한·재시도 정책을 유지한다. 독립 인증·KIS 관측 CLI의 출력 계약 변경은 이 범위에 추가하지 않는다.

Metrics·Events·Logs·Traces의 정보는 하나의 제한된 진단 기록에서 제공한다. 기존 실패 stderr JSON에 단계·요청별 시간, 이벤트, 부모·자식 관계와 중단 사유를 추가한다. 성공 stdout과 기존 오류·종료 코드를 유지한다. 별도 영속 저널과 외부 수집 서버는 보류한다. Profiles는 CPU·메모리 병목의 관측 근거가 생겼을 때 검토한다. 실행 전 모듈 로딩 실패나 강제 종료로 최종 진단 자체가 사라지는 경우의 보존을 이번 범위에서 보장하지 않는다.

## 합의한 정보 경계

실행·작업 ID, 고정 작업명, 시각·경과 시간, HTTP 상태, 크기·횟수, 완료 이벤트 수, 종료 상태와 취소 출처만 기록한다. 프롬프트·응답 본문·헤더 원문·외부 오류 문자열·인증값·개인 경로는 수집하지 않는다. 최초 관측 실패와 최종 종료 사유를 별도로 보존하고 확인하지 못한 원인은 `unknown`으로 남긴다. 새 도메인 용어는 없으며 일반적인 관측 개념을 용어집에 추가하지 않는다.

## 합의한 기록 구조

기존 진단 필드를 유지하고 별도 관측 객체를 추가한다. 실행·작업의 부모 관계, 시작·종료 시간, 헤더 수신, 첫·마지막 이벤트, 완료 이벤트 수, 자연 EOF·오류·취소를 구분한다. 취소 출처는 전체 실행·대상 개장·단계·개별 요청 제한으로 구분하며, 확인하지 못한 출처를 경과 시간만으로 추정하지 않는다. 최초 실패와 최종 공개 오류 코드를 별도로 보존한다.

## 합의한 용량 제한

추가 관측 기록은 실행당 최대 512개 작업·요청과 직렬화 결과 256KiB로 제한한다. 기존 출력 전체에 적용하는 상한이 아니라 추가 관측 정보의 상한이다. 토큰·청크마다 이벤트를 누적하지 않고 중요한 시점과 횟수만 보존한다. 상한에 도달하면 최초 실패·실패한 작업·최종 요약을 우선하고 생략 건수를 표시한다. 이 수치는 성능 측정값이 아닌 초기 방어 상한이다. 부모 작업과 자식 요청의 시간은 중첩될 수 있으므로 단순 합산하지 않는다.

## 합의한 관측 실패 처리

관측 기록 생성·용량 제한·직렬화에 문제가 생겨도 원래의 성공·실패 판정, 인증 저장·잠금 해제, 스트림 취소를 방해하지 않는다. 가능한 경우 고정 상태로 `degraded` 또는 `truncated`를 표시하고 원래 오류를 보존한다. 진단을 얻기 위한 추가 호출·재시도는 하지 않는다. 검증에서는 관측 실패도 주입해 이 조건을 확인한다.

## 복구와 최종 중단의 관계

정상 복구된 KIS 만료 요청 실패와 나중에 실행을 중단시킨 모델 실패는 별개의 관측 사실이다. 최초 실패 기록을 곧바로 근본 원인으로 표시하지 않고 복구 여부와 최종 중단으로 전달된 관계를 함께 남긴다. 최종 공개 오류의 기존 우선순위는 변경하지 않는다.

## 구현 시 검증 경계와 검토 기준

공개 검증 경계는 네 CLI의 입력·stdout·stderr·종료 코드와 외부 HTTP·시계 목업이다. 기존 CLI 자식 프로세스와 합성 인증·HTTP·시계 검사를 재사용한다. 불완전 응답·헤더 후 정지·자연 EOF와 취소·중첩 기한·복구된 실패·관측 실패·용량 초과·비밀값 비노출을 검증하고 기존 요청 인자·종류별 집계·한도·비용 정책을 보존한다. 진단 누락·조기 완료·잘못된 원인·요청 연결을 잡는 음성 대조를 수행한다.

향후 구현 검토 기준은 `3343281ab3380f0174bdcf7595efac219acb5358` 이후 이 작업의 설계·구현 변경이다. 형식·린트·타입·관련 검사와 Standards·Spec 두 축 리뷰를 마친 뒤 소스를 고정하고 최종 전체 모의 검사를 수행한다. 모의 통과를 실제 공급자 원인 확인이나 보고서 연결 성공으로 표시하지 않는다. 이 절은 후속 구현의 검증 계약이며 이번 명세 게시에서 해당 검사를 수행했다는 뜻이 아니다.

## #273의 공통 구현 계약

`scripts/execution-observation.ts`의 `ExecutionObservation`이 실행별 관측 상태를 소유한다. 통합 CLI는 `CandidateRuntime.observation`을 사용하고 독립 일정 CLI는 관측 소유자만 생성한다. 독립 CLI에 통합 600초·요청 예산을 새로 적용하지 않는다. `ExecutionContext`의 `observation`과 `parentId`가 같은 소유자와 부모 작업 ID를 전달하며, `runtime`이 있는 기존 호출에서는 그 관측 소유자를 재사용한다. 모듈이 반환하는 작업 토큰은 읽기 전용이며 변경은 소유자의 메서드를 통한다.

실패 JSON의 최상위 `observation`은 기존 `diagnostic`, `reason`, `location`, `usage`와 별개다. `runId`와 실행 시작 시각, 실행 경과 시간, `operations`, `firstFailure`, `finalError`, `coverage`, `degraded`, `truncated`, `omittedOperations`를 제공한다. 작업의 `startedAt`, `endedAt`, `headersAt`, `firstEventAt`, `lastEventAt`은 실행 시작부터의 단조 시계 밀리초 오프셋이고 `elapsedMs`는 그 작업의 경과 시간이다. 시간 값 `null`은 미관측이다. 부모와 자식의 시간은 중첩된다.

`start(name, parentId, kind)`는 고정 이름의 논리 작업·실제 요청·논리 도구 호출을 구분한다. 실제 전송 기록은 기존 정책 검사와 전송 집계 뒤, `fetch` 직전에 생성한다. `headers`는 상태 코드와 헤더 수신 시점만 기록하며 작업을 완료하지 않는다. `streamEnd`는 처음 관측한 `eof`, `read_error`, `cancelled`를 보존한다. `end`는 업무의 기존 검증을 마친 뒤 호출하며 `fail`은 허용한 오류 코드만 기록한다. 결과 검증 실패는 검증 작업과 모델 작업의 실패이며, 이미 정상 EOF로 끝난 HTTP 전송을 뒤늦게 통신 실패로 바꾸지 않는다.

모델 HTTP 응답은 `observeResponse(response, observation, request, signal, true)`를 한 번 통과한다. 반환된 응답은 기존 소비자에게 전달한다. 래퍼는 소비자의 읽기 요구마다 원래 리더를 한 번 읽고, 추가 선읽기 없이 원래 취소를 전달한다. 받은 SSE의 완성된 이벤트에서 첫·마지막 시점, `completionEvents`와 `errorEvents`를 세며 본문·외부 오류 문자열·헤더·URL은 기록하지 않는다. 이 관측을 사용하는 경로에서는 기존 SDK 미들웨어에 같은 관측 계수를 다시 추가하지 않는다. 단계가 기존에 사용하던 완료 이벤트 계수와 완료 판정은 그대로 유지한다. 공급자 실패 이벤트를 본 뒤 읽기 오류나 취소가 발생해도 최초 관측 실패를 유지한다.

SSE 메타데이터의 임시 버퍼에도 상한을 적용한다. 큰 이벤트나 해석 실패 때문에 정확한 계수를 보장할 수 없으면 관측만 `degraded`로 표시하고 계수는 `null`로 둔다. SDK에 전달하는 원래 바이트, 모델 결과와 완료 판정은 바꾸지 않는다. 요청별 관측 토큰은 해당 `fetch` 호출의 클로저에 고정하며 다음 도구 왕복 요청의 가변 전역 포인터로 바꾸지 않는다.

`requestSignal`의 선택 인수는 제한 소유자를 전달한다. `tagSignal`은 실제 abort 이벤트가 발생한 순간의 출처를 저장한다. 이후 다른 제한이 취소되더라도 처음 출처를 바꾸지 않는다. `execution_limit`, `target_open`, `stage_limit`, `request_limit`은 직접 연결한 제한에만 쓰며 외부 취소나 출처를 잃은 신호는 `unknown`이다. 시간 경과만으로 공급자 오류나 취소 출처를 추정하지 않는다.

`fail(operation, error)`는 최초 실패를 남기고, `propagate(mappedError, originalError)`는 기존 오류 매핑을 유지하면서 공개 오류와 관측 실패의 연결을 전달한다. 정책상 정상 복구한 실패에는 `recover(operation)`을 사용한다. 최상위 catch는 기존 우선순위로 공개 코드를 먼저 정한 뒤 `finish(code, error)`를 호출한다. `firstFailure`는 근본 원인이라는 뜻이 아니며 `failure.recovered`와 `failure.propagated`가 복구 및 최종 중단 전달 여부를 구분한다.

`observeFetch`는 실제 `fetch` 거부 경계에서 원래 예외를 그대로 전달하면서 실패 코드를 `unknown`으로 기록하고, 연결한 신호가 실제 취소됐으면 종료 상태와 취소 출처를 남긴다. 본문 리더의 거부도 `unknown`으로 기록한다. 예외 메시지가 내부 오류 코드를 흉내 내도 내부 인증·정책 오류로 분류하지 않는다. 처음 기록한 실패 코드는 예외 연결과 함께 상위 작업 및 매핑된 오류로 전달하며, 요청 작업 토큰을 만들지 못한 경우에도 이 분류를 보존한다. 로컬 인증·프로토콜·제한 검사는 기존 고정 코드를 유지하고 최종 공개 오류의 선택은 기존 CLI가 담당한다.

작업·요청은 최대 512개를 보관하고 `snapshot()`은 추가 관측 JSON을 최대 256KiB로 제한한다. 최초 실패·실패한 작업·최종 오류 연결을 우선하며 생략은 계수로 남긴다. 기록 생성과 직렬화가 실패하면 가능한 최소 실패 요약과 `degraded`를 제공한다. 관측 메서드는 원래 오류를 대신 던지지 않는다. 인증 저장·잠금 해제와 원래 리더 취소는 기존 정리 경로에서 실행한다.

기반 작업 #273의 적용 범위는 일정·SIWC 인증과 이를 호출하는 후보군·매수 후보 CLI의 실패 출력이다. `coverage`는 실제 관측 작업이 시작된 영역을 나열하며, 없는 작업은 성공이나 미시작의 증거가 아니다. 후속 #274·#275·#276은 유형·추천·의미 검토·KIS의 상세 관측에 같은 소유자·토큰·전송 래퍼를 사용한다. 독립 인증·KIS 관측 CLI의 출력 계약은 유지한다. KIS 관측 도구의 실행 소스 스냅샷에는 새 공통 모듈도 포함된다.

공통 모의 경계는 기존 `runCalendar`와 `run` CLI 프로세스 도우미다. 일정 도우미는 기존 요청 추적 외에 합성 인증의 만료 시각·잠금 존재 여부와 스트림 취소 기록을 반환한다. `market-calendar-http-mock.mjs`는 헤더 후 정지, 완료 뒤 읽기 오류, 중복 완료, 불완전 이벤트 뒤 취소, 청크 경계와 큰 이벤트, 관측 생성·직렬화 실패를 제공한다. 제한 타이머 주입은 `TEST_TIMEOUT_MATCH`와 선택한 발생 순서 `TEST_TIMEOUT_OCCURRENCE`로 실제 abort를 일으킨다. 이는 모의 전송과 모의 시계 검증이며 실제 공급자 호환성·과거 중단 원인·보고서 연결·추천 품질을 입증하지 않는다. 최종 통합 리뷰·변이 음성 대조·전체 모의 검사는 모든 후속 변경이 합쳐진 소스로 별도 수행한다.

## 통합 구현의 관측 범위

일정·후보군·매수 후보·유형 검증 CLI의 실패 출력은 같은 `observation` 형식을 사용한다. 유형 검증 CLI는 독립 관측 소유자만 생성하며 기존 독립 실행 예산을 유지한다. 통합 경로는 기존 `CandidateRuntime` 소유자를 인증·일정·순위·유형·일봉·추천·의미 검토와 최종 검증에 전달한다. 상세 사용법은 [일정](market-calendar.md), [유형 판단](llm-security-probe.md), [매수 후보](buy-candidates.md), [KIS 인증](kis-auth.md) 안내를 따른다.

유형 판단의 기존 `diagnostic.typeAssessment`와 요청 통계는 공통 관측과 함께 유지한다. 논리 정보 도구·관측된 웹 도구와 실제 HTTP 전송은 서로 다른 작업이다. 추천의 일봉 도구는 이미 검증한 자료만 읽으며 진단을 위해 자료를 다시 조회하지 않는다. 추천 선정과 의미 검토는 별도 부모 작업에 연결하지만 기존 추천 단계 예산을 공유한다.

KIS 조회는 논리 조회와 실제 전송을 구분한다. 명시적 만료 뒤 허용된 재조회가 정상 검증되면 최초 만료 실패의 `recovered`가 참이 된다. 나중의 모델 실패가 실행을 중단해도 복구된 실패를 최종 중단으로 전달된 원인으로 표시하지 않는다. 본문을 읽지 않는 기존 인증 거부 경로는 헤더와 오류만 기록하며 `streamEnd`를 미확인으로 남긴다. 헤더 수신·본문 EOF·업무 검증 완료를 구분한다.

통합 후보군·매수 후보 경로와 독립 유형 검증 CLI의 순위 조회는 `ranking` 작업 아래의 KIS 조회와 `ranking.validation`으로 연결한다. 통합 경로의 일봉 조회는 `daily` 아래의 KIS 조회와 `daily.validation`으로 연결한다. 행·식별·필수 날짜·수치 검증 실패는 해당 검증 작업을 가리키며, 이미 정상 종료한 KIS HTTP의 EOF와 완료 상태를 바꾸지 않는다.

모의 검사는 클라이언트 측 기록·기존 출력·요청 인자·제한·정리 동작을 확인한다. 실제 공급자의 내부 처리·과거 중단 원인·최종 보고서 실연동·추천 품질·제품 인수는 이 구현의 검증 범위에 포함되지 않는다. 새로운 실제 실행은 별도 승인 범위다.
