# KIS EGW00316 공개 자료 조사

2026-10-31의 #240 진단 기록과 한국투자증권 공식 공개 자료를 바탕으로 한 조사다. 이 조사 단계에서는 KIS 조회·인증·주문 API와 OpenAI API를 다시 호출하지 않았다. 아래 대응안은 제안이며 실행하거나 공급자에게 전송하지 않았다.

## 후속 근거와 승인한 복구 정책

이 조사 뒤 사용자가 2026-10-31 공식 KIS 포털 챗봇 화면을 제공했다. 해당 답변은 `EGW00316`을 일시적인 조회 시간 초과로 설명하고 잠시 뒤 재호출을 안내했다. 이는 공식 포털 AI의 안내이며 이번 요청의 서버 내부 원인을 독립적으로 확인한 자료는 아니다. 아래 공개 문서·소스 검색의 미확인 기록은 이 후속 안내 이전의 조사 범위다.

사용자는 해당 조회에 한정한 제한적 재시도를 승인했다. 구현은 같은 GET을 1초 뒤 최대 한 번 재시도하고 기존 공통 마감·단계 신호·전송 상한을 유지한다. 이 횟수와 간격은 로컬 설계값이며 챗봇이 제시한 수치가 아니다. 명시적 토큰 만료 복구와 각각 논리 조회 전체에서 한 번만 허용하며, 다른 오류에는 확대하지 않는다. 상세 조건은 [공통 조회 정책](kis-probe-reference.md#요청과-제한)에 있다. 실제 API 재호출과 복구 성공 검증은 수행하지 않았다.

## 확인된 의미와 한계

`EGW00316`의 공식 정의와 발생 조건은 조사한 공개 자료에서 확인하지 못했다. 확보한 [KIS Developers 오류코드 표](https://apiportal.koreainvestment.com/faq-error-code)의 공개 콘텐츠에는 해당 코드가 없다. 이 콘텐츠의 최종 수정 메타데이터는 2025-04-25이고 `useYn`·`showYn`은 모두 `N`이다. 따라서 이 표의 누락을 전체 현행 오류 목록에 코드가 없다는 뜻으로 해석하지 않는다. 정확한 코드 검색에서도 정의를 설명하는 공식 문서를 찾지 못했으며, 코드 번호의 인접성으로 의미를 추정하지 않는다.

같은 표는 토큰 만료를 `EGW00123`, 초당 거래건수 초과를 `EGW00201`, 유효하지 않은 IP를 `EGW00207`, 법인고객에게 허용되지 않은 IP 접근을 `EGW00303`으로 구분한다. 이 구분은 `EGW00316`이 만료·유량·IP 문제라는 근거가 아니다. HTTP 500도 이번 요청이 실패했다는 사실만 보여주며, 공급자 내부 장애와 요청·계정별 거부 조건을 구분하지 못한다.

## 이번 실행에서 관측한 사실

2026-10-31 13:09:16부터 13:12:36까지의 KST 실행은 첫 NAS 거래량순위 요청에서 HTTP 500으로 종료했다. 해당 요청은 86ms 동안 128바이트를 받고 EOF에 도달했으며, JSON 해석에 성공하고 `providerCode: "EGW00316"`을 남겼다. 이 기록은 읽기 타임아웃이나 JSON 해석 실패와 구분된다. 토큰 발급은 0회였고 증권 유형 판단과 추천 모델 호출도 각각 0회였다. 공급자 메시지 원문은 이 진단 기록에 없어 코드 이외의 상세 설명을 복원할 수 없다. 관측 근거는 [진단 보강 후 실제 통합 실행 기록](buy-candidates.md#2026-10-31-진단-보강-후-실제-통합-실행)에 정리되어 있다.

로컬 캐시에 기록된 만료 시각은 2026-11-01 12:04:55 KST로, 실패 당시에는 만료 전이었다. 이는 로컬 만료 시각이 지났다는 설명과 맞지 않는다. 서버가 토큰을 유효하게 인정했는지, 토큰이 폐기되었는지, 계정·앱에 별도 제한이 있었는지는 이 메타데이터만으로 확인할 수 없다. 12:01의 별도 실행에서 발생한 상품정보 조회 HTTP 500은 공급자 코드가 확인되지 않았으므로 이번 `EGW00316`과 같은 오류로 묶지 않는다.

별도 로컬 정적 대조에서 [공식 거래량순위 예제](https://github.com/koreainvestment/open-trading-api/blob/2077773a69a428daf63e148182511f068cc45de3/examples_llm/overseas_stock/trade_vol/trade_vol.py)와 비교한 경로·TR ID·파라미터에는 뚜렷한 불일치가 없었다. [공식 인증 예제](https://github.com/koreainvestment/open-trading-api/blob/2077773a69a428daf63e148182511f068cc45de3/examples_llm/kis_auth.py)의 기본 헤더에는 `Content-Type: application/json`이 있지만 현재 GET 요청에는 이 헤더가 없다는 차이가 확인됐다. 같은 요청 코드로 앞선 여섯 순위 조회가 성공한 기록도 있어, 이 차이를 이번 오류의 원인이나 해결책으로 확정하지 않는다.

## 정책 자료로 판단할 수 있는 범위

[공식 유량 안내](https://apiportal.koreainvestment.com/community/10000000-0000-0011-0000-000000000001/post/d0d1a83f-6f8d-4437-9700-6d26702fd989)는 2026-04-20 기준 계좌별 REST 호출 한도와 동시 호출 간격을 설명하지만 `EGW00316`을 명시하지 않는다. 이번 프로세스의 KIS 조회 1회라는 기록은 다른 프로그램의 같은 계좌 호출이나 공급자 정책 적용까지 배제하지 못한다. 유량 문제가 확인된 경우에만 전체 호출 주체의 동시성·간격을 함께 점검하는 근거로 사용할 수 있다. 공지의 일반적인 재호출 권고는 미확인 코드의 자동 재시도를 정당화하지 않는다.

[공식 제휴 프로세스](https://apiportal.koreainvestment.com/provider-process)의 서버 IP 등록 안내는 제휴사·법인계좌 절차에 속한다. 이를 개인용 CLI에도 같은 IP 등록 의무가 있다는 근거나 이번 요청이 IP 차단됐다는 증거로 사용하지 않는다.

서비스 공지·FAQ의 HTML은 본문을 별도 공개 GET으로 불러오는 구조다. HTML 껍데기의 0건 표시는 공지 부재를 입증하지 않는다. 검색 색인에는 2026-09-16 유량제한 공지의 잠금 표시가 있었지만, 이번에 확보한 공개 목록에는 나타나지 않았다. 해당 비공개 본문을 열거나 로그인하지 않았으며 제목만으로 현재 정책과 이번 코드의 관계를 판단하지 않는다.

최근 공지 두 건의 공개 본문도 대조했다. [10월 29일 결과값 변경 공지](https://apiportal.koreainvestment.com/community/10000000-0000-0011-0000-000000000001/post/a075a300-09ed-4a79-8801-915d2bb468f6)는 11월 10일·13일의 일부 계좌·선물옵션 API 민감정보 필드 삭제 예정이며 이번 해외주식 거래량순위 API를 대상으로 명시하지 않는다. [10월 21일 미국주식 주간거래 공지](https://apiportal.koreainvestment.com/community/10000000-0000-0011-0000-000000000001/post/cfdf8ab9-adfb-4a89-b6e1-bb9d6a3eda22)는 그날 블루오션 시스템 문제와 15:30 정상화를 알린다. 어느 공지도 `EGW00316`을 명시하지 않으며 10월 31일 실패의 원인으로 연결할 근거는 확보하지 못했다. 이번 공개 검색과 목록 확인이 모든 과거·비공개 공지를 포괄한다는 뜻은 아니다.

## 가능한 대응과 필요한 추가 근거

현재 근거로 특정 원인을 제거하는 확정 수정안은 없다. 확인 전에는 토큰 삭제·강제 재발급·반복 호출을 해결책으로 적용하지 않는다. 기존 명시적 만료 처리의 경계는 [ADR 0002](adr/0002-kis-expired-token-invalidation.md)에 따른다. `EGW00316`을 만료 코드로 추가할 근거는 확보하지 못했다.

공급자 문의에는 다음처럼 비밀을 제거한 기존 관측 자료를 사용할 수 있다.

```text
발생 시각: 2026-10-31 13:12:36 KST
요청: GET /uapi/overseas-stock/v1/ranking/trade-vol
TR ID: HHDFS76310010
파라미터: EXCD=NAS, NDAY=0, VOL_RANG=0, 나머지 선택 필터는 빈 값
결과: HTTP 500, msg_cd=EGW00316
진단: JSON 해석 성공, 128바이트, EOF, 요청 경과 86ms
인증 관측: 이번 실행의 신규 발급 0회, 로컬 기록상 만료 전
질문: 코드의 정확한 의미와 발생 조건은 무엇인가?
질문: 계정·앱·IP·유량 정책 중 적용 범위와 해제 조건이 있는가?
질문: 재시도 가능한 오류인가? 가능하다면 권장 간격·횟수는 무엇인가?
```

앱 키·시크릿·Bearer 토큰·계좌번호·요청 헤더 원문은 이 자료에 포함하지 않는다. 로컬 실행 ID는 공급자의 요청 추적 ID가 아니므로 공급자 요청 ID로 제시하지 않는다. 문의는 아직 보내지 않았다.

공급자가 유량 제한을 확인하면 같은 계좌의 모든 호출 주체와 간격을 점검하고, IP·계정·앱 제한을 확인하면 그 적용 범위에 맞는 조치를 정한다. 공급자 장애로 확인되면 정상화 공지와 재시도 조건을 따른다. 헤더를 공식 예제와 맞추는 변경은 별도로 검토할 수 있으나, 원인 확인이나 해결 검증으로 표현하지 않는다. 어떤 대응도 추가 실제 호출로 검증하지 않은 상태다.

## 공식 저장소의 최신 소스에서 얻은 단서

추가 정적 조사는 공식 저장소의 한국 시각 2026-10-28 커밋 [`3a9be59a3ed8745720dc3aa9d584bdf3b7830362`](https://github.com/koreainvestment/open-trading-api/commit/3a9be59a3ed8745720dc3aa9d584bdf3b7830362)에 고정했다. 확보한 1,203개 일반 파일의 텍스트 검색에서는 `EGW00316`, `00316`, `EGW003`이 발견되지 않았다. 이는 확보한 소스 범위의 결과이며 공급자 내부 코드와 비공개 정책까지 설명하지 않는다. 소스를 실행하거나 실제 API를 호출하지 않았다.

가장 최근의 인증 수정은 실전·모의 토큰 파일 충돌을 해결한다. [커밋의 인증 변경](https://github.com/koreainvestment/open-trading-api/commit/3a9be59a3ed8745720dc3aa9d584bdf3b7830362)은 `examples_llm/kis_auth.py`와 `examples_user/kis_auth.py`에 같은 변경을 적용했다. 기존 날짜별 단일 파일을 서버 구분별 파일로 나누고, `auth(svr)`가 `read_token(svr)`·`save_token(..., svr)`를 사용하게 했다. 변경 전에는 같은 날 실전과 모의를 함께 사용하면 다른 환경의 토큰을 덮어쓰거나 읽을 수 있었다. 커밋 메시지도 이 인증 실패를 수정 대상으로 명시하지만, `EGW00316`과의 관계는 설명하지 않는다. 다른 변경은 백테스터 UTF-8 처리와 종목 마스터 경로·인코딩 호환성으로, 이번 순위 조회를 직접 고치는 변경은 아니다.

Stock Scout의 현재 [토큰 관리](../scripts/kis-auth.ts)는 앱 키·시크릿 조합의 SHA-256 지문과 만료까지 60초 넘게 남았는지를 확인한 뒤 자체 JSON 캐시를 재사용한다. 토큰 발급과 [조회](../scripts/kis-query.ts)는 모두 실전 서버로 고정되어 있으며 공식 Python 예제의 날짜별 파일을 읽지 않는다. 따라서 현재 표준 실행 경로에는 공식 예제의 실전·모의 파일 충돌 수정이 직접 적용되지 않는다. 이 수정은 토큰의 저장 대상과 요청 환경이 일치하는지 살펴볼 단서이지만, Stock Scout 캐시가 잘못됐다는 증거는 아니다. 지문과 로컬 만료 검사는 서버의 폐기·권한 변경까지 확인하지 못하므로 오래되었거나 거절된 캐시라는 가설도 확정하거나 완전히 배제할 수 없다.

요청 형식에서 남은 차이는 헤더다. 최신 [공식 인증·HTTP 래퍼](https://github.com/koreainvestment/open-trading-api/blob/3a9be59a3ed8745720dc3aa9d584bdf3b7830362/examples_llm/kis_auth.py#L61-L66)는 `Content-Type: application/json`, `Accept: text/plain`, `charset: UTF-8`, 설정된 `User-Agent`를 기본값으로 두고 [`_url_fetch`](https://github.com/koreainvestment/open-trading-api/blob/3a9be59a3ed8745720dc3aa9d584bdf3b7830362/examples_llm/kis_auth.py#L444-L490)가 빈 `tr_cont`도 명시한다. Stock Scout는 인증·앱 정보·TR ID·`custtype`만 명시하고 나머지는 Node.js의 기본 동작에 맡긴다. 반면 [최신 거래량순위 예제](https://github.com/koreainvestment/open-trading-api/blob/3a9be59a3ed8745720dc3aa9d584bdf3b7830362/examples_llm/overseas_stock/trade_vol/trade_vol.py)와 경로·TR ID·조회 파라미터는 일치한다. 헤더 차이는 구체적인 대조 지점이지만 해당 헤더가 필수이거나 그 누락이 `EGW00316`을 일으킨다는 근거는 없다. 공식 예제의 브라우저형 `User-Agent`를 차단 우회 수단으로 복사하는 결론도 내리지 않는다.

오류 처리에서도 이번 코드의 해결법은 나오지 않는다. 공식 [`APIRespError`와 `_url_fetch`](https://github.com/koreainvestment/open-trading-api/blob/3a9be59a3ed8745720dc3aa9d584bdf3b7830362/examples_llm/kis_auth.py#L394-L490)는 HTTP 200 이외의 응답 상태와 본문을 전달하며, HTTP 500에 대한 자동 재시도나 `EGW00316` 해석은 제공하지 않는다. 별도 [백테스터 데이터 공급자](https://github.com/koreainvestment/open-trading-api/blob/3a9be59a3ed8745720dc3aa9d584bdf3b7830362/backtester/kis_backtest/providers/kis/data.py#L93-L107)는 명시적인 `EGW00201`에 한해 61초 간격과 3회 시도를 사용한다. 이는 특정 호출자의 유량 제한 대응이며 미확인 코드에 같은 대기·재시도를 적용할 근거가 아니다. 오류 본문을 그대로 출력하는 공식 예제의 방식도 비밀을 제한하는 Stock Scout 진단 정책에 그대로 옮기지 않는다.

이 조사에서 구체화된 후속안은 실제 호출 없이 공개 CLI·모의 HTTP 경계에서 요청 경로·TR ID·파라미터·의도한 헤더를 확인하고, 공식 예제와 헤더를 맞출 필요가 있는지 별도 변경으로 검토하는 것이다. 이 검사는 전송 형식에 관한 회귀를 확인할 수 있지만 공급자 서버의 거절 원인이나 해결 여부는 입증하지 못한다. 현재는 제안만 기록했으며 코드·캐시·테스트를 변경하지 않았다. 캐시 삭제나 강제 재발급보다 먼저 위 문의 자료에 공식 저장소의 토큰 충돌 수정과 이번 실전 전용 경로의 차이를 덧붙여 공급자에게 정확한 코드 의미를 확인할 수 있다.
