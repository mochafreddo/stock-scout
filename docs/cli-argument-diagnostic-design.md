# 기본 실패 진단과 인수 오류 진단

[#270](https://github.com/mochafreddo/stock-scout/issues/270)의 2026-10-21 설계 인터뷰 기록이다. 상위 #268·#265·#262·#258과 #250·#237의 공통 계약을 따른다. 사용자는 Q1·Q2의 추천안을 모두 수락하고 Q3에서 작업 범위·공개 검증 경계·리뷰 기준을 확정했다. 이어 `to-spec`으로 #270 명세 게시와 `ready-for-agent` 라벨 적용을 요청했다. 게시 요청과 실제 반영 성공은 구분한다. 구현·실연동·커밋·푸시·이슈 종료는 이번 요청에 포함하지 않는다.

## 합의한 사항

Q1에서 단계와 원인의 확인 여부를 독립적으로 취급하기로 했다. 후속 단계 전달이 아직 연결되지 않아 `stage`가 `unknown`이어도 코드가 직접 확인한 단일 원인은 `reason`에 제공한다. 예를 들어 순위 누락을 직접 확인한 실패는 `stage: "unknown"`, `reason: "RANKING_INCOMPLETE"`로 표시한다. 기존 식별자를 재사용할 때는 철자를 유지한다.

여러 조건을 묶는 `RANKING_FAILED`·`MODEL_OUTPUT`, 미등록 예외와 외부 메시지에서 가져온 식별자의 `reason`은 `unknown`이다. 기존 `error`의 메시지 기반 호환 동작을 진단 원인의 신뢰 근거로 삼지 않는다. 알려진 식별자와 같거나 `siwc_`로 시작하는 외부 메시지도 그 문자열만으로 원인을 확정하지 않는다. 구체적인 고정 원인은 구현 시 실제 발생 지점과 전달 경로를 확인하여 선택하며, 기존 오류 코드를 일괄 복사하지 않는다.

Q2에서 #270의 모든 실패는 `location: null`로 제공하기로 했다. 안전한 응답 배열·필드 경로라는 상위 계약은 유지하되 이번 티켓에서는 위치 정보를 새로 수집하거나 전달하지 않는다. 응답 위치 전달은 상세 진단의 후속 범위로 둔다. 인수 위치·평가 파일 내부 경로·개인 파일 경로도 추가하지 않는다.

## 유지하는 범위와 계약

유형 판단 CLI가 처리할 수 있는 모든 실패의 기존 stderr JSON에 별도 옵션 없이 `diagnostic`을 추가하고 `stage`·`reason`·`location` 세 필드를 항상 제공한다. 인수 오류와 인수 처리 범위의 예상하지 못한 예외는 `input`·`unknown`·`null`이다. 기존 `USAGE`는 보존하며 구체적인 진단 원인으로 사용하지 않는다.

평가 파일 읽기·JSON 파싱·내용 검사와 초기 인증·순위·조회·판단·출력은 실제 단계 전달 전까지 `unknown`이다. 평가 파일의 `input` 단계 연결은 후속 티켓에서 완성한다. 인수 검사에 포함된 평가 모드의 파일 인수 개수·절대 경로 형식 검사는 평가 파일을 실제 읽고 검사하는 작업과 구분한다.

기존 stderr 필드·오류 코드·종료 코드·실패 stdout·성공 출력·정상 분석 불충분과 인증 재시도 시각·로그인 안내를 보존한다. 독립된 인증·KIS 관측 CLI의 출력 계약은 변경하지 않는다. 기존 근거 검사·검증 순서·최초 실패 동작·호출 및 시간 한도를 유지하며 진단을 위한 추가 모델 호출·조회·재시도를 하지 않는다. Actions는 비활성 상태를 유지한다.

진단에 모델 원문·외부 메시지·인증 값·개인 경로·동적 필드명과 값을 넣지 않는다. 실행 전 런타임·정적 모듈 로딩 실패·강제 종료·진단 출력 자체의 실패는 보장 범위 밖이며 별도 실행기를 추가하지 않는다. 실제 실패 진단·고정 표본 평가·실제 KIS·OpenAI 검증과 상위 티켓 전체 완료 선언은 범위 밖이다.

## 최종 확정 대상

저장소는 stock-scout 한 곳이며 이번 작업 범위는 이 로컬 설계 문서다. 기존 미커밋 설계 문서는 별도로 보존한다. 새 도메인 용어나 별도 ADR이 필요한 장기 결정은 발생하지 않아 용어집과 ADR은 수정하지 않는다.

Q3에서 사용자는 이 문서의 설계·작업 범위·공개 검증 경계·리뷰 기준을 확정하고 `to-spec`으로 #270 본문과 `ready-for-agent` 라벨의 명세 게시를 요청했다. 2026-10-21 명세를 게시하고 원격 본문과 제안 본문의 정확한 일치를 확인했다. 기존 `ready-for-agent` 라벨과 OPEN 상태를 유지했다. 기존 완료 조건 아홉 개의 문구·순서·미완료 상태를 보존하고 Q1·Q2를 구체화한 두 조건을 추가했으며 열한 조건 모두 미완료다. 구현·실연동·커밋·푸시는 수행하지 않았다.

향후 구현의 공개 검증 경계는 CLI 입력·stdout·stderr·종료 코드와 외부 HTTP 요청이다. 기존 Node.js CLI 프로세스·외부 HTTP 모의 검사 선례를 재사용한다. 인수 대표 실패·인수 처리 중 미등록 예외·외부 메시지의 식별자 흉내·후속 경로의 기본 진단과 기존 성공·실패 계약을 확인한다. 단계가 `unknown`인 확인된 단일 원인과 원인을 확인하지 못한 경우를 구분하며 모든 실패의 `location`이 `null`인지 확인한다. 인수 실패 뒤 외부 요청이 없고 외부 부수 효과는 요청 인자·호출 수까지 검증한다. 내부 함수 배치나 문서 문구를 고정하지 않는다.

향후 구현은 #270의 수정 전 회귀 실패·필요한 형식·린트·타입·전체 테스트·위험 로직 음성 대조와 고정 변경본의 Standards·Spec 리뷰를 따른다. 모의 검사와 실제 서비스 검증을 구분하고 미수행 조건과 이유를 남긴다.

인터뷰 시작 HEAD와 티켓상 리뷰 기준점은 `41a4188e0413a95dc6757658c1e4d99a492f8859`다. 이번 문서 검토 범위는 이 파일과 확보한 #270 원문이다. 구현 시작 시 선행 티켓과 동시 변경을 구분해 관련 변경을 고정한다.

## 현재 확인한 사실과 한계

읽기 전용 소스 조사에서 `scripts/llm-security-probe.ts`의 인수 검사와 이후 평가 파일 읽기·파싱·내용 검사가 구분되지만 현재 모두 `USAGE`로 출력될 수 있음을 확인했다. 최상위 오류 처리에는 아직 진단 객체가 없으며 기존 오류 코드 목록 또는 `siwc_` 접두사와 일치하는 예외 메시지를 `error`로 출력한다. `RANKING_FAILED`는 순위 조회 예외와 응답 검사 실패를 함께 다룬다. 이 관찰은 실제 서비스 실행 결과가 아니다.

이번 작업에서는 문서만 작성하며 코드 테스트와 실연동은 수행하지 않는다. 명세 게시와 구현·검증 완료는 별개다.
