# 구독 인증 자동 갱신 설계

2026-10-20 시작한 `grill-with-docs` 인터뷰에서 Sign in with ChatGPT 구독 인증의 자동 갱신을 설계하고 2026-10-21 #252 후속 인터뷰 Q10에서 최종 확정했다. 상위 제품 요구사항은 [#237](https://github.com/mochafreddo/stock-scout/issues/237)이며 [기존 CLI](llm-security-probe.md)의 인증 경로에 적용한다. 시작 커밋은 `21a40607ac59638375bbca88c7b97505c4e48cd4`이고 시작 시 Git 작업 트리에 변경은 없었다. 티켓 게시 이력은 아래에 기록하며, 이번 후속 인터뷰에서는 설계 문서만 수정했다. 구현·실제 인증 갱신·원격 이슈 반영·커밋·푸시는 수행하지 않았다.

## 합의한 정책

사용자는 Q1에서 CLI가 API 요청을 시작하기 전에 토큰을 확인하고, 이미 만료됐거나 남은 시간이 5분 이하면 자동 갱신하는 추천안을 수락했다. 유효기간이 충분하면 기존 토큰을 사용하며 정상적인 갱신에는 브라우저 로그인이나 실행별 확인을 요구하지 않는다. 서버가 정한 갱신 가능 시점을 준수한다. 구체적인 응답 필드의 해석과 갱신 거부 처리는 공식 근거를 확인한 뒤 정한다.

사용자는 Q2에서 이번 범위를 실행 전 자동 갱신으로 한정하고 모델 실행 중 인증 오류에는 모델·도구 호출을 자동 재실행하지 않는 추천안을 수락했다. 중간 인증 오류는 기존 실패 계약을 유지한다. 이후 실행에서도 갱신할 수 없는 인증 상태라면 재로그인이 필요하다고 알린다.

2026-10-21 사용자는 Q3에서 로그인과 갱신이 같은 잠금을 사용하고 다른 프로세스가 처리 중이면 최대 30초 기다린 뒤 인증 파일을 다시 확인하는 추천안을 수락했다. 다른 프로세스가 갱신했다면 새 토큰을 재사용한다. 대기 한도를 넘으면 명확히 실패하며 비정상 종료로 남은 잠금은 자동 삭제하지 않는다.

사용자는 Q4에서 일시적인 통신 오류·시간 초과·서버 장애와 공식 오류로 확인된 갱신 토큰 무효화를 구분하는 추천안을 수락했다. 일시적 실패에는 기존 인증을 보존하고 해당 실행을 실패시키며 같은 실행에서 다시 요청하지 않는다. 다음 명시적 실행에서 다시 시도한다. 갱신 토큰 무효화가 확인되면 토큰을 정리하고 재로그인이 필요하다고 알리되 기존 계정·client ID·호스트 등록 정보는 보존한다. 브라우저를 자동으로 열지 않는다. 서버가 토큰을 교체했지만 응답을 받지 못했을 때 성공으로 추정하지 않으며 이후 시도가 거부되어 재로그인이 필요할 가능성을 남긴다.

사용자는 Q5에서 `earliest_refresh_at`이 있으면 공식 예제의 처리 방식을 참고해 그 시각 전에는 갱신을 요청하지 않는 추천안을 수락했다. 숫자는 Unix 초로 해석하며 날짜 문자열은 시간대를 명확히 해석할 수 있어야 한다. 값이 없으면 만료 5분 전 기준을 적용한다. 값이 잘못됐거나 아직 갱신할 수 없는 시각이면 요청하지 않고 이유를 알리며, 시각이 유효한 경우 재실행 가능 시각도 알린다. 이는 공식 예제의 해석을 채택한 설계이며 서버 계약을 독립 검증한 결과는 아니다.

사용자는 Q6에서 갱신 응답의 scope나 ID 토큰 생략을 허용하는 추천안을 수락했다. scope가 없으면 기존에 검증한 권한을 유지하며 새 목록이 있으면 필수 권한을 다시 검사하고 옛 목록으로 보충하지 않는다. ID 토큰이 없으면 기존 신원 정보를 유지하며 새 ID 토큰이 있으면 서명·발급자·대상·계정 일치를 검증한 뒤 교체한다. 액세스 토큰·교체 갱신 토큰·유효기간은 필수로 검사하고 인증 상태를 한 번에 저장한다. 검증이나 저장에 실패하면 모델 요청을 시작하지 않는다.

사용자는 #252의 후속 인터뷰 Q8에서 갱신 응답의 검증을 마친 뒤 취소가 들어오면 새 인증의 원자적 저장과 잠금 해제를 마친 다음 취소로 종료하는 추천안을 수락했다. 서버에서 이미 교체한 갱신 토큰을 잃지 않기 위한 정책이며 이후 데이터·모델 요청은 시작하지 않는다. 응답을 받지 못했다면 기존 합의대로 갱신 성공을 추정하지 않는다. 강제 종료나 저장 실패에도 저장 완료를 보장한다는 뜻은 아니다.

사용자는 Q9에서 잠금 대기와 별도로 갱신 요청과 필요한 원격 신원 검증을 합쳐 최대 30초로 제한하는 추천안을 수락했다. 한도를 넘으면 기존 인증을 보존하고 같은 실행에서 재시도하지 않으며 실패한다. 이미 검증을 마친 새 인증의 저장은 Q8에 따라 완료한다.

## 확인한 기반과 남은 사실 확인

현재 인증 모듈은 갱신 토큰을 저장하지만 사용하지 않으며 만료한 액세스 토큰을 거부한다. 기존 원자적 저장과 로그인 잠금을 재사용할 수 있다. KIS 인증의 발급 간격 정책은 별도 공급자의 계약이므로 구독 인증 갱신에 승계하지 않는다.

[공식 계정·세션 문서](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions)는 만료 무렵의 갱신과 같은 세션 갱신의 직렬화를 요구한다. [토큰 참조](https://developers.openai.com/siwc/token-sharing-open-source/token-reference)는 액세스 토큰 1시간, 갱신 토큰 30일과 성공 시 갱신 토큰 교체를 설명한다. 요청에는 발급된 client ID와 갱신 토큰·resource를 사용하며 scope는 생략한다.

조사한 공식 문서는 `earliest_refresh_at`을 응답 필드로 열거하지만 단위·기준 시각·갱신 허용 시점과의 관계를 정의하지 않았다. 갱신 응답의 ID 토큰과 scope가 항상 포함되는지도 확인하지 못했다. 이 항목의 의미를 추정해 구현하지 않으며 후속 조사와 설계에서 처리 범위를 정한다. 네트워크 응답을 받지 못했을 때 회전된 갱신 토큰과 재동기화하는 절차도 미확정이다.

후속 조사에서 공식 Cookbook이 연결한 OpenAI 소유 [SIWC devkit](https://github.com/openai/sign-in-with-chatgpt-devkit)의 구현을 확인했다. [갱신 코드](https://github.com/openai/sign-in-with-chatgpt-devkit/blob/main/packages/local/src/oauth.ts)는 응답 scope가 없으면 저장된 권한을 유지하고 ID 토큰 생략을 허용하며, 새 ID 토큰이 있으면 검증한다. [호출 코드](https://github.com/openai/sign-in-with-chatgpt-devkit/blob/main/packages/local/src/index.ts)는 숫자 `earliest_refresh_at`을 Unix 초로, 문자열은 날짜 파싱으로 해석한다. 이는 공식 예제의 처리 방식이며 서버 응답에 대한 문서상 보장과 구분한다. 이 예제를 참고한 시간 필드 처리와 생략된 ID 토큰·scope 정책은 Q5·Q6에서 합의했다.

## 최종 합의와 티켓 분할

사용자는 Q7의 추천안을 수락하고 `to-tickets`로 티켓 분할을 요청했다. 최종 범위는 이 저장소의 공용 SIWC 인증 경로에 실행 전 갱신을 추가하고, 기존 저장·로그인 경로와 CLI 호출부 및 안내를 함께 조정하는 것이다. 별도 갱신 명령이나 실행 중 모델 재시도는 추가하지 않는다. 공용 검증 경계는 CLI 입력·stdout·stderr·종료 코드, 인증 저장 파일의 상태 변화, 외부 인증·모델 요청이다. 시간·HTTP를 대체한 검사에서 갱신·재사용·동시 실행·회전 저장·권한·신원·실패·취소를 확인하고 위험 로직의 음성 대조를 수행한다.

실제 검증은 승인된 기존 보관 위치에서 갱신이 필요한 시점의 공식 갱신 1회와 다음 별도 프로세스의 재사용을 확인한다. 기존 파일의 만료 시각을 조작하거나 인증 값을 출력하지 않는다. 갱신 시점을 충족하지 못하거나 서비스 오류가 발생하면 실제 검증은 미완료로 기록한다. 모의 검사와 실제 갱신을 구분하며 종목 유형 정확도 평가는 이번 범위에 포함하지 않는다.

리뷰 기준은 인터뷰 시작 커밋 `21a40607ac59638375bbca88c7b97505c4e48cd4` 이후 이 작업의 설계·구현 변경이며 Standards·Spec 두 축을 사용한다. 이번 요청은 설계 확정과 티켓 분할·승인 후 게시이며 구현·실제 갱신·커밋·푸시 요청과 구분한다.

사용자는 두 티켓 분할안과 첫 티켓에서 둘째 티켓으로 이어지는 선행 관계를 승인했다. [#252](https://github.com/mochafreddo/stock-scout/issues/252)는 실행 전 자동 갱신의 전체 CLI 경로와 모의 검증을 구현하며 선행 차단이 없다. [#253](https://github.com/mochafreddo/stock-scout/issues/253)은 고정된 최종 구현에서 실제 갱신·다음 별도 프로세스 재사용을 확인하며 GitHub 기본 차단 관계로 #252에 연결했다. 두 본문과 `ready-for-agent` 라벨, OPEN 상태, 차단 관계를 원격에서 다시 읽어 확인했다. 갱신은 기존 인증 경로를 확장하므로 종목 유형 판단이나 매수 보고서 완성을 선행 조건으로 두지 않는다. 기존 #237·#240·#241은 수정하거나 종료하지 않았으며 티켓 게시를 구현·실제 갱신 완료로 취급하지 않는다.

## #252 후속 인터뷰 최종 확정

2026-10-21 사용자는 Q10의 추천안을 수락하여 Q1~Q9의 정책과 구현 범위·공용 검증 경계·리뷰 기준을 최종 확정했다. 범위는 공용 SIWC 인증 경로의 실행 전 갱신·재사용·저장·실패·취소 처리다. 검증을 마친 새 인증은 취소 시에도 원자적 저장과 잠금 해제를 마치며 이후 데이터·모델 요청은 시작하지 않는다. 갱신 요청과 필요한 원격 신원 검증은 잠금 대기와 별도로 합계 30초로 제한한다.

공용 검증 경계는 CLI 입력·stdout·stderr·종료 코드, 인증 파일 상태 변화, 외부 인증·모델 요청이다. 시간·HTTP 모의와 위험 로직 음성 대조를 사용하고 실제 갱신·다음 별도 프로세스 재사용은 #253에서 확인한다. 리뷰 기준은 `21a40607ac59638375bbca88c7b97505c4e48cd4` 이후 이번 설계·구현 변경이며 Standards·Spec 두 축으로 검토한다. 설계 확정은 구현이나 실제 검증 완료를 뜻하지 않는다. Q8~Q10 합의의 원격 이슈 반영은 아직 수행하지 않았다.
