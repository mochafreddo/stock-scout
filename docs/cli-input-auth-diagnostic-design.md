# 유형 판단 CLI의 기본 진단과 입력·초기 인증 경계

[#265](https://github.com/mochafreddo/stock-scout/issues/265)의 2026-10-21 설계 인터뷰 기록이다. 상위 [#262](https://github.com/mochafreddo/stock-scout/issues/262)와 [공통 진단 설계](cli-failure-diagnostic-design.md)를 따른다. 사용자는 Q1·Q2의 추천안을 모두 수락하고 Q3에서 설계를 확정한 뒤 명세 게시를 요청했다. 이번 범위는 로컬 설계와 #265 명세 게시이며 구현·실연동·커밋·푸시·이슈 종료는 포함하지 않는다.

## 확정 사항

Q1에서 “모든 CLI 실패”의 적용 대상을 `scripts/llm-security-probe.ts`가 처리할 수 있는 모든 실패로 한정했다. 저장소의 독립된 인증·KIS 관측 CLI의 출력 계약은 이번 범위에 포함하지 않는다. 공통 인증 함수의 수정이 필요해도 이 적용 범위를 확대하지 않는다.

Q2에서 초기 인증 준비를 위해 실행하는 SIWC 동적 import의 실패도 `authentication` 단계로 표시하기로 했다. 입력 검사를 마친 뒤 초기 인증 준비에 진입하며, 해당 단계에서 포착한 동적 import 실패의 진단은 `stage: "authentication"`, `reason: "unknown"`, `location: null`이다. 공통 명세의 모듈 로딩 실패 제외는 애플리케이션 오류 처리 시작 전의 정적 import 실패에 적용한다. 프로세스 강제 종료와 진단 출력 자체의 실패도 기존 보장 범위 밖으로 유지하며 별도 실행기는 추가하지 않는다.

## 유지하는 상위 계약

처리 가능한 실패의 기존 stderr JSON에 `diagnostic`의 `stage`·`reason`·`location` 세 필드를 항상 제공한다. 인수·평가 파일 읽기와 검사는 `input`, 초기 인증 준비는 `authentication`이다. 이 범위의 예상하지 못한 예외도 확인된 단계를 유지한다. 순위·조회·판단·출력의 실제 단계 전달은 후속 티켓에서 완성하며 그전에는 `unknown`을 제공한다. 초기 인증 이후의 실패를 계속 `authentication`으로 표시하지 않는다.

원인은 코드 내부에서 확인한 고정 식별자만 사용하며 재사용하는 식별자의 철자를 보존한다. 여러 조건을 묶은 오류와 미등록 예외는 `reason: "unknown"`이다. 기존 오류 코드의 출력 호환성과 진단 원인의 신뢰성은 구분한다. 외부 메시지가 알려진 식별자나 `siwc_` 접두사를 흉내 내도 그 문자열만으로 진단 원인을 확정하지 않는다. 상세 원인 세분화는 후속 범위다.

위치는 코드가 확인한 안전한 응답 배열·필드 경로 또는 `null`이다. 배열 번호는 0부터 시작한다. 모델 원문·외부 오류 메시지·인증 값·개인 경로·동적 필드명과 값을 진단에 넣지 않는다. 기존 오류·종료 코드·stderr 필드·실패 stdout·성공 출력과 인증 재시도 시각·로그인 안내를 유지하고 정상적인 분석 불충분을 새 실패로 바꾸지 않는다.

기존 검증 순서와 최초 실패 동작, 호출·시간 한도를 유지한다. 진단을 위한 추가 모델 호출·조회·재시도, 상세 거부 사유·시간·호출 통계, 실제 실패 진단·고정 표본 평가와 #250 완료 선언은 범위 밖이다.

## 최종 확정과 게시 범위

사용자는 Q3에서 Q1·Q2와 유지하는 상위 계약, 이 로컬 설계 문서·작업 범위·공개 검증 경계·리뷰 기준을 확정했다. 이어 `to-spec`으로 #265 명세 게시와 `ready-for-agent` 라벨 적용을 요청했다. 게시 요청과 원격 반영 성공은 구분한다. 구현·실연동·커밋·푸시·이슈 종료는 이번 요청에 포함하지 않는다.

2026-10-21 #265 명세를 게시하고 원격 본문과 제안 본문의 정확한 일치를 확인했다. 기존 `ready-for-agent` 라벨과 OPEN 상태를 유지했다. 기존 완료 조건 여덟 개의 문구·순서·미완료 상태를 보존하고 Q1·Q2를 구체화한 두 조건을 추가했다. 열 조건 모두 미완료이며 구현·검증 완료를 뜻하지 않는다.

저장소는 stock-scout 한 곳이며 공개 검증 경계는 CLI 입력·stdout·stderr·종료 코드와 외부 HTTP 요청이다. 기존 CLI 프로세스·외부 HTTP 모의 검사 선례를 재사용하고 요청 인자·호출 수, 기본 진단과 미등록 예외, 알려진 식별자를 흉내 낸 외부 메시지, 기존 출력·검증 순서를 확인한다. 내부 함수 배치나 문서 문구를 고정하지 않는다.

향후 구현 검증은 #265의 수정 전 회귀 실패·필요한 형식·린트·타입·전체 테스트·위험 로직 음성 대조·고정 변경본의 Standards·Spec 리뷰를 따른다. 모의 검사와 실제 KIS·OpenAI 동작을 구분한다. 인터뷰 시작 HEAD와 티켓상 리뷰 기준점은 `41a4188e0413a95dc6757658c1e4d99a492f8859`다. 이번 문서 검토에는 이 파일을 추가한 변경을 포함하고 기존 미커밋 설계 작업은 구분한다. 구현 착수 시 선행 티켓과 동시 변경을 확인하여 관련 변경을 고정한다.

## 설계 당시 확인 범위

소스 조사에서 입력 검사 뒤 SIWC 동적 import와 초기 자격 증명 읽기를 실행하고 이후 순위 수집으로 진행하는 흐름을 확인했다. 현재 최상위 오류 출력에는 진단 객체가 없다. 이 관찰은 실제 서비스 실행 결과가 아니다.

새 도메인 용어와 별도 ADR이 필요한 장기 결정은 발생하지 않아 용어집과 ADR은 수정하지 않았다. 기존 미커밋 설계 문서는 이번 수정 범위에서 제외했다. 이번 인터뷰에서는 코드 테스트와 실연동을 실행하지 않았다.

## 2026-10-22 구현 확인

사용자가 `implement #265`로 구현·검증·리뷰·현재 브랜치 커밋을 요청했다. 착수 HEAD는 `280d39da492387f558fe28c13014e4ba7687fb6b`이며 작업 트리에 미커밋 변경은 없었다. 기본 진단은 `9bc042a`의 #270, 평가 입력 경계는 `458a6bf`의 #271, 초기 인증 경계는 `280d39d`의 #269에서 이미 구현되어 있었다. 이번에는 기존 구현을 재사용하고 #265 전체 계약과 대조한다. 사용법과 현재 동작은 [기본 실패 진단 읽기](llm-security-probe.md#기본-실패-진단-읽기)를 따른다.

입력 실패는 `input`, 초기 인증과 포착한 SIWC 동적 import 실패는 `authentication`, 인증 이후 아직 실제 단계를 전달하지 않는 실패는 `unknown`이다. 코드가 확인한 고정 원인만 전달하며 외부 메시지나 임의의 `reason` 속성은 진단 원인의 근거로 사용하지 않는다. 위치는 모두 `null`이며 상세 응답 위치와 후속 단계 전달은 이번 범위에 추가하지 않는다.

리뷰는 티켓 기준점 `41a4188e0413a95dc6757658c1e4d99a492f8859`부터 착수 HEAD까지의 관련 런타임·테스트·사용 문서 변경과 이번 문서 변경을 대상으로 한다. 다른 설계 문서와 이미 완료한 전달 도구 변경은 포함하지 않는다. 회귀 검사는 합의한 CLI 입력·stdout·stderr·종료 코드와 외부 HTTP 요청 경계에서 실행한다. 진단 추가 전 코드와 단계·원인 전달을 제거한 변이에서 기존 회귀 검사가 실패하는지도 확인한다.

실제 KIS·OpenAI 요청, 실제 계정 인증·갱신, 고정 표본 평가와 실제 실패 진단은 이번 범위 밖이므로 수행하지 않는다. 로컬 모의 검증은 실연동·유형 정확도나 #262·#250의 완료 근거가 아니며 후속 차단을 해제하지 않는다. 푸시·원격 이슈 갱신·이슈 종료는 이번 요청에 포함하지 않는다.
