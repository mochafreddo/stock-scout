# KIS 순위에서 LLM으로 종목 유형 확인하기

이 CLI는 KIS 순위를 자동 수집한 뒤 LLM이 조회 근거로 개별 상장 종목의 유형을 판단하는 검증 도구입니다. [#250](https://github.com/mochafreddo/stock-scout/issues/250)과 [ADR 0007](adr/0007-llm-security-type-judgment.md)의 작은 흐름을 구현합니다. 매수 추천이나 장전 보고서를 생성하지 않으며, 정상 출력에서도 `validation: unverified`, `dataSession: null`을 유지합니다.

## 현재 검증 상태

2026-10-20 후속 설계 구현 기준입니다. 자료 조회와 최종 유형 판단을 분리하고 평가 전용 입력을 추가했습니다. 기존 연결 확인과 이번 실제 실행의 결과를 구분하며, 작은 흐름과 독립 표본 전체의 실제 인수는 미완료입니다.

| 구분 | 확인한 결과와 남은 작업 |
| --- | --- |
| 연결·도구 호환성 | 공식 구독 인증과 실제 KIS·검색 도구 호출을 확인했습니다. |
| 최종 결과 생성 | 새 두 단계 흐름의 실제 순위 실행은 92.491초 후 `MODEL_OUTPUT`으로 끝났습니다. 진단에서 조회 근거 검증 지점의 거부를 확인했지만 세부 원인은 확정하지 못했습니다. 정상 stdout 결과는 없습니다. |
| 유형 정확도 | 최종 소스의 고정 AAPL 입력도 33.178초 후 `MODEL_OUTPUT`으로 실패했습니다. 진단용 임시 소스의 다른 AAPL 실행은 현재 적용 여부 미확인으로 제외했고, 여러 순위 종목 실행은 조회 120초 제한에 도달했습니다. 전체 표본 3회 평가는 미완료입니다. |
| 후속 구현 | #250과 장전 데이터·일정·운영값의 필수 조건이 남아 후보군·매수 추천의 차단을 유지합니다. |

다음 작업은 조회 근거의 거부 조건과 여러 종목을 처리할 때의 조회 부담을 다시 검토하는 것입니다. 한도 연장이나 근거 검사 완화로 성공을 대신하지 않습니다. 이번에는 기존 인증 만료를 확인하고 사용자 승인 후 공식 재로그인을 완료했으며, 이후 실행 실패는 로그인 대기 때문이 아닙니다. 이전 실행은 [로그인 재개 후 실제 검증](#로그인-재개-후-실제-검증), 이번 흐름은 [두 단계 흐름의 구현과 검증](#두-단계-흐름의-구현과-검증)에서 구분해 확인하세요.

## 실행 책임

[#254](https://github.com/mochafreddo/stock-scout/issues/254)·[#255](https://github.com/mochafreddo/stock-scout/issues/255)의 구조 개선에서 [종목 유형 판단 실행 모듈](../scripts/security-type-assessment.ts)이 자료 조회, 근거 검증과 ID 부여, 추가 조회 없는 최종 판단, 결과 검증을 한 번의 호출로 처리합니다. 요청·완료 횟수, 열린 출처, 실패 상태와 두 단계가 공유하는 호출·시간 한도 및 타이머도 모듈 안에서 관리합니다. [CLI](../scripts/llm-security-probe.ts)는 인증, 순위 또는 평가 입력 준비, 출력과 종료 처리를 맡습니다.

기존 명령·출력·오류 계약과 공용 KIS·SIWC 경로를 유지합니다. 이 구조 개선의 검증 범위는 CLI와 외부 HTTP 경계의 로컬 모의 검사입니다. 실제 KIS·OpenAI 호출과 독립 표본의 유형 정확도 평가는 포함하지 않으며, 위의 실제 검증 상태와 후속 차단 조건은 유지합니다.

## 준비하기

Node.js 24 이상과 잠금 파일의 의존성이 필요합니다. Vercel AI SDK와 OpenAI 공급자를 사용하며 별도 MCP 서버는 필요하지 않습니다. 기존 설치가 없으면 패키지 설치를 승인한 뒤 저장소 루트에서 `npm ci`를 실행하세요.

실제 실행에는 기존 KIS 앱 키·시크릿과 Stock Scout 전용 Sign in with ChatGPT 인증이 필요합니다. Codex 인증 파일이나 ChatGPT 브라우저 쿠키를 복사하지 마세요. API 키만으로 구독 인증을 대신하지 않습니다.

## 공식 구독 인증 연결하기

저장소 밖의 비동기화 로컬 경로를 승인된 보관 위치로 선택하세요. 경로는 절대 경로이고 심볼릭 링크를 통과하지 않아야 하며 부모 폴더가 존재해야 합니다. 도구는 마지막 폴더를 0700으로 생성하거나 기존 폴더의 소유자·권한을 검사합니다.

```sh
node scripts/siwc-auth.ts login /absolute/private/stock-scout
```

출력의 `authorizationUrl`을 브라우저에서 열어 Stock Scout 등록과 구독 사용 권한을 승인하세요. 로그인 코드를 복사할 필요는 없습니다. 도구가 `127.0.0.1`의 일시적인 포트에서 callback을 받고 PKCE·state, ID 토큰의 서명·issuer·audience·만료·nonce와 부여된 구독 권한을 검증합니다. 성공하면 `status: authenticated`를 출력합니다.

선택한 폴더에는 고정 호스트 식별자의 `host.json`과 인증의 `credentials.json`을 각각 0600으로 저장합니다. 토큰은 stdout·stderr에 출력하지 않습니다. 파일은 계정 식별자와 비밀 값을 포함하므로 커밋하거나 진단 로그에 첨부하지 마세요.

폴더 하나에는 계정·워크스페이스 등록 하나를 유지합니다. 같은 폴더에서 다시 로그인하면 기존 발급 client ID와 호스트 식별자를 재사용하며 다른 계정의 인증으로 덮어쓰지 않습니다. 다른 계정을 사용하려면 별도로 승인한 보관 위치를 선택하세요.

### 구독 연결 확인하기

종목 분석 없이 현재 구독 인증으로 모델 목록을 조회하려면 다음 명령을 실행하세요. KIS 인증이나 모델 ID는 필요하지 않습니다.

```sh
node scripts/siwc-auth.ts check /absolute/private/stock-scout
```

기존 공용 인증 경로에서 필요한 갱신을 마친 뒤 공식 `GET /v1/models`를 한 번 조회합니다. 목록 조회의 시간 제한은 응답 본문 수신을 포함해 15초이고 응답 크기 상한은 1MiB입니다. 인증 응답의 기존 128KiB 상한과 구분합니다. 자동 재시도·추론·검색·유료 API 전환은 없습니다. 갱신·신원 검증과 잠금 대기의 한도는 기존 정책을 따릅니다.

성공하면 stdout의 JSON 한 줄에 `status: connected`, `auth`, `models`가 출력되고 종료 코드 0을 반환합니다. `models`에는 표시 가능한 모델의 `slug`와 `displayName`을 서버 순서대로 담습니다. 빈 목록도 조회 성공이며 사용 가능한 표시 모델이 없다는 뜻입니다. 목록 조회 성공만으로 추론 실행 가능성을 입증하지는 않습니다.

`auth.status`는 `reused` 또는 `refreshed`이며 `refreshRequests`는 해당 프로세스에서 시도한 갱신 요청 수입니다. 갱신한 경우 `responseValidated`·`credentialsStored`·`storedCredentialsMatch`로 검증·저장·저장값 대조 결과를, `accessTokenChanged`·`refreshTokenChanged`로 이전 값과의 메모리 비교 결과를 확인하세요. `expiresAt`은 액세스 토큰의 UTC 만료 시각입니다. 토큰 원문이나 해시는 출력하지 않습니다.

실패하면 stdout은 비우고 stderr에 안전한 오류 JSON을 출력하며 종료 코드 1을 반환합니다. 실패 JSON의 `auth`에는 완료한 인증 단계와 요청 수가 남으며 인증이 끝나지 않았으면 `status: pending`입니다. 목록 조회가 실패해도 이미 저장한 갱신 인증은 유지합니다. `retryAt`이 있으면 해당 시각 이후 재개하고 `action: login`이면 명시적 재로그인이 필요합니다. 실패 증거를 보존한 뒤 복구하세요.

실제 갱신 검증에서는 [확정한 검증 설계](siwc-refresh-live-validation-design.md)에 따라 자연스러운 갱신 시점에 실행하고, 곧바로 별도 프로세스에서 같은 명령을 실행해 `reused`와 갱신 요청 0회를 확인합니다. 첫 실행이 단순 재사용이면 실제 갱신 성공의 증거가 아닙니다. 만료 시각을 조작하거나 인증을 다른 위치에 복사하지 마세요. 실제 동시 회전·무효화·응답 유실의 검증과도 구분하세요.

CLI는 데이터·모델 요청 전에 액세스 토큰을 확인합니다. 만료했거나 남은 시간이 5분 이하면 저장된 갱신 토큰으로 자동 갱신하고, 충분히 유효하면 기존 인증을 재사용합니다. 정상 갱신에는 브라우저 로그인이나 실행별 확인이 필요하지 않습니다. 별도 갱신 명령은 없습니다.

`earliest_refresh_at`이 있으면 해당 시각 전에는 갱신하지 않습니다. 숫자는 공식 예제를 참고해 Unix 초로 해석하고 날짜 문자열은 시간대를 명확히 확인할 수 있어야 합니다. 잘못된 값이나 아직 갱신할 수 없는 시각에서는 실행을 중단합니다. 유효한 시각이면 안내된 시각 이후에 다시 실행하세요. 이 해석의 채택과 실제 서버 계약의 검증은 구분합니다.

로그인과 갱신은 같은 `.login.lock`으로 직렬화하고 최대 30초 기다립니다. 갱신 요청과 필요한 원격 신원 검증에는 잠금 대기와 별도로 합계 30초의 제한을 적용합니다. 통신 오류·시간 초과·서버 장애는 기존 인증을 보존하고 해당 실행을 실패시키며 같은 실행에서 다시 요청하지 않습니다. 응답을 받지 못했더라도 서버에서 갱신 토큰을 교체했을 수 있으므로 다음 실행에서 재로그인이 필요할 수 있습니다.

공식 갱신 오류로 토큰 무효화를 확인하면 토큰을 정리하고 재로그인을 안내합니다. 기존 계정·client ID·호스트 등록은 보존하므로 같은 로그인 명령으로 다시 인증하세요. 브라우저는 자동으로 열지 않습니다. [공식 오류 문서](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery)에 따라 갱신 요청의 `invalid_grant`, `invalid_refresh_token`, `token_expired`, `refresh_token_expired`, `refresh_token_invalidated`, `refresh_token_reused`를 토큰 무효화로 구분합니다. `invalid_client`는 설정 오류이므로 토큰을 지우지 않습니다. 최초 등록의 코드 교환이 `invalid_grant`로 실패하면 아직 검증하지 않은 새 client ID는 저장하지 않습니다. 최초 등록 실패 후의 등록 복구와 다중 계정 UI는 구현하지 않았습니다.

갱신 응답의 검증을 마친 뒤 취소하면 새 토큰의 원자적 저장과 잠금 해제를 마친 뒤 종료하며 이후 데이터·모델 요청은 보내지 않습니다. 강제 종료나 저장 실패에도 저장을 보장하는 것은 아닙니다. 모델 실행 중 인증 오류에는 전체 실행을 실패시키고 모델·도구 호출을 자동 재실행하지 않습니다.

강제 종료로 `.login.lock`이 남으면 해당 폴더를 쓰는 로그인·갱신 프로세스가 모두 종료됐는지 확인한 뒤 잠금 파일만 제거하세요. 남은 잠금은 자동 삭제하지 않습니다. 인증 파일이나 호스트 식별자는 그대로 두세요. 정상 취소와 종료에서는 잠금을 정리합니다.

갱신 관련 오류는 stderr의 JSON으로 확인하세요. 실패한 실행은 종료 코드 1을 반환하며 다음 단계의 데이터·모델 요청을 시작하지 않습니다.

| 오류 | 조치 |
| --- | --- |
| `siwc_refresh_not_allowed` | `retryAt`에 표시된 UTC 시각 이후 다시 실행하세요. |
| `siwc_invalid_refresh_time` | 갱신 시각을 해석할 수 없습니다. 인증 파일을 임의로 수정하지 말고 같은 보관 위치에서 명시적으로 다시 로그인하세요. |
| `siwc_relogin_required` | `action: login` 안내에 따라 같은 보관 위치에서 다시 로그인하세요. |
| `siwc_session_locked` | 다른 로그인·갱신이 끝난 뒤 다시 실행하세요. 종료된 프로세스의 잠금이면 위 복구 절차를 따르세요. |
| `siwc_client_configuration` | 발급 client ID와 앱 설정을 확인하세요. 토큰 무효화로 취급하지 않습니다. |
| `siwc_refresh_failed` | 통신·서비스 문제를 확인하고 다음 명시적 실행에서 다시 시도하세요. |

## 종목 유형 흐름 실행하기

사용 가능한 구독 모델 ID와 거래소별 각 순위의 상위 N을 지정하세요. 다음 예제의 모델은 실제 계정의 지원 모델인지 확인해야 합니다. `.env`는 Node의 명시적 옵션으로만 읽습니다. 기존 두 KIS 인증 값이 프로세스 환경에 이미 있으면 `--env-file`을 생략하세요.

```sh
node --env-file=.env scripts/llm-security-probe.ts /absolute/private/stock-scout gpt-6.1-sol 1
```

NAS·NYS·AMS의 거래량·거래대금 순위를 각각 한 페이지 조회하고 원래 순위가 N 이하인 행만 선택합니다. 같은 거래소·종목 코드의 중복은 연결하고 순위 출처를 보존합니다. 같은 회사의 다른 종류주·ADR을 합치지 않으며 제외된 종목을 아래 순위로 보충하지 않습니다. 필요한 상위 N을 확보하지 못했는데 연속 조회 표시가 있으면 실패합니다.

실험용 입력 N은 1~10입니다. 조회와 최종 판단은 모델 요청 최대 12회, 종목 정보 도구 최대 32회, 관측한 웹 호출 최대 32회의 한도를 공유합니다. 이는 서버가 이미 실행한 웹 호출 수의 사전 상한을 보장하지 않으며, 유료 검색 비용 상한을 보장할 수 없는 이유 중 하나입니다. 종목 정보 도구는 기존 KIS 인증 잠금과 충돌하지 않도록 순서대로 실행합니다. 순위 수집 뒤 시작하는 모델 단계의 전체 시간 제한은 180초이며 조회 단계는 최대 120초입니다. KIS 조회 자체에는 기존 요청별 시간 제한과 만료 복구 정책이 적용됩니다. 이 배분은 검증용이며 최종 장전 지원 시간이나 운영값의 실측이 아닙니다.

LLM에는 입력 종목에 한정한 `get_info`와 OpenAI 웹 검색을 제공합니다. 웹 검색의 실제 지원은 모델·계정 정책에 따라 달라지며 미지원 오류를 다른 서비스로 자동 우회하지 않습니다. 웹 근거는 검색 결과 목록이나 인용 URL만으로 인정하지 않고 실제 `open_page` 또는 `find_in_page`를 완료한 URL에 연결합니다. KIS 근거는 성공한 조회에 부여한 `kis:거래소:종목코드`에 연결합니다.

조회 단계는 실제로 읽은 유형 관련 발췌문, 해당 증권과의 연결, 기준일·적용일, 후속 변경 확인 결과와 현재 적용 가능성 설명을 모읍니다. 코드는 실제 조회에 연결된 근거에 `e1` 같은 ID를 부여합니다. 최종 판단 단계에는 입력 종목과 이 근거 목록을 전달하며 추가 조회 도구를 제공하지 않습니다. 최종 판단은 URL을 다시 작성하지 않고 근거 ID를 참조합니다. 미열람 URL을 보정하던 이전 경로는 이 두 단계 흐름으로 대체했습니다.

호스팅된 웹 검색은 클라이언트에 원문 본문 전체를 제공하지 않으므로 발췌문은 조회 모델이 추출한 내용이며 `excerptOrigin: model_extracted`로 구분합니다. 페이지 열기 기록과의 연결은 확인하지만 원문과 바이트 단위로 대조한 인용문은 아닙니다. 자료의 실제 내용·증권 연결·현재 적용 가능성은 독립 평가에서 확인해야 합니다. 날짜가 없는 페이지도 다른 근거로 현재 적용 여부를 확인할 수 있지만 확인하지 못하면 제외합니다. 원문과 발췌문의 보관·공개는 출처의 허용 범위를 따르세요.

코드는 근거가 실제 조회에 연결되고 필수 항목이 있는지 검사합니다. 자료의 의미, 유형과 현재 적용 가능성의 타당성은 LLM 판단과 별도 평가 대상입니다. 링크가 연결됐다는 사실만으로 판단이 맞다고 보장하지 않습니다.

## 결과와 실패 구분하기

stdout에는 완성된 결과 JSON 한 줄만 출력합니다. `securities`에서 원본 거래소·종목 코드·순위, 유형, 포함 여부, 판단 이유와 연결된 근거를 확인하세요. `evidenceRecords`에는 코드가 부여한 ID와 조회 모델이 추출한 근거 문맥이 담깁니다. `lookups`에는 허용 필드로 제한된 KIS 종목 정보와 개별 조회 실패가, `webSources`에는 실제로 읽은 웹 URL이, `webFailures`에는 개별 웹 호출 실패가 담깁니다. 순위 관측에는 요청 경로·거래 ID·파라미터도 보존합니다. `coverage`에서 입력·포함·제외·미확인 수와 개별 조회 실패 수를 확인하세요.

| 결과 | 종료 코드 | 의미 |
| --- | --- | --- |
| `status: assessed` | 0 | 유형 확인 결과입니다. 모두 제외 대상일 수 있으며 매수 추천이나 실제 정확도 검증 완료가 아닙니다. |
| `status: analysis_insufficient` | 2 | 모든 종목의 유형 또는 현재 적용 가능성을 확인하지 못했습니다. 정상적인 후보 없음과 구분합니다. |
| stderr의 안전한 오류 코드, stdout 없음 | 1 | 순위·인증·모델·공통 조회 실패, 식별 모호함, 형식·근거 오류 등으로 실행을 완료하지 못했습니다. |

개별 정보 요청의 HTTP 404는 해당 종목의 조회 실패로 기록하고 나머지 분석을 계속합니다. 다른 허용 근거가 없다면 제외합니다. 인증·전송·응답 구조·정체를 알 수 없는 KIS 오류는 개별 종목의 부재로 단정하지 않고 전체 실패합니다. 모델이 정보 도구에 순위 밖 종목을 요청하거나 결과에서 종목을 추가·누락·중복하면 실패합니다.

개별 웹 페이지 조회 실패는 해당 호출의 실패로 기록하고 다른 근거가 없으면 그 종목을 제외합니다. 특정 URL의 `open_page`·`find_in_page` 실패만 개별 처리합니다. 검색 자체의 실패나 실패 범위를 특정할 수 없는 호출, OpenAI 요청의 인증·통신·서비스 오류와 스트림의 명시적 실패는 전체 실패입니다.

주요 오류는 `RANKING_FAILED`, `RANKING_INCOMPLETE`, `IDENTITY_AMBIGUOUS`, `AUTH_FAILED`, `QUERY_FAILED`, `SEARCH_FAILED`, `MODEL_FAILED`, `MODEL_INCOMPLETE`, `MODEL_OUTPUT`, `MODEL_LIMIT`입니다. 인증 파일 오류는 `siwc_`로 시작합니다. 모델의 중간 도구 단계와 최종 응답 모두 명시적인 `response.completed`를 받아야 하며 JSON이나 스트림 종료만으로 성공을 판정하지 않습니다.

구독 한도 소진의 명시적 오류는 `SUBSCRIPTION_LIMIT`로 구분합니다. 기존 유료 API 키가 있어도 이 도구의 서버 실행 웹 검색을 포함한 최대 과금액을 보장할 수 없으면 `PAID_BUDGET_UNPROVABLE`로 중단하고 유료 요청을 보내지 않습니다. 인증 실패·검색 미지원·일반적인 429·사용량 확인 불가에서는 유료 요청을 보내지 않습니다. 비용 상한을 보장할 수 있는 유료 경로는 후속 구현 대상입니다.

### 기본 실패 진단 읽기

[#262](https://github.com/mochafreddo/stock-scout/issues/262)의 여섯 단계 기본 진단은 #265·#266·#267의 구현을 합쳐 제공합니다. [#265](https://github.com/mochafreddo/stock-scout/issues/265)의 입력·초기 인증 실패 진단은 [#268](https://github.com/mochafreddo/stock-scout/issues/268)·[#269](https://github.com/mochafreddo/stock-scout/issues/269)의 구현으로 제공합니다. #268의 기본 진단과 입력 경계는 [#270](https://github.com/mochafreddo/stock-scout/issues/270)·[#271](https://github.com/mochafreddo/stock-scout/issues/271)에서 구현했습니다. 유형 판단 CLI가 처리할 수 있는 실패의 기존 stderr JSON에 별도 옵션 없이 `diagnostic`을 추가합니다. `stage`·`reason`·`location`은 항상 제공하며 기존 `error`·인증 재시도 시각·로그인 안내와 종료 코드는 유지합니다. 성공 결과와 정상적인 분석 불충분에는 진단을 추가하지 않습니다. 독립된 인증·KIS 관측 CLI의 출력 계약도 유지합니다.

인수 오류와 평가 파일 읽기·JSON 파싱·내용 검사 실패, 이 입력 범위의 예상하지 못한 예외는 [#271](https://github.com/mochafreddo/stock-scout/issues/271)에 따라 `stage: input`, `reason: unknown`, `location: null`입니다. 기존 오류 코드와 검사 순서를 유지하며 잘못된 항목을 알아도 인수 위치·평가 파일 내부 경로·파일 경로를 추가하지 않습니다. 입력 검사 뒤 초기 인증 준비 실패는 [#269](https://github.com/mochafreddo/stock-scout/issues/269)에 따라 `stage: authentication`입니다. 이 단계의 예상하지 못한 예외와 포착한 SIWC 동적 import 실패도 같은 단계를 유지하며 원인은 확인하지 못하면 `unknown`입니다. [#267](https://github.com/mochafreddo/stock-scout/issues/267)에 따라 조회 준비·실행·근거 검증 실패는 `retrieval`, 최종 판단 준비·실행·결과 검증 실패는 `judgment`, 최종 객체 구성·민감값 검사·직렬화 실패는 `output`입니다. 근거 검증과 판단 결과 검증을 각각 마친 뒤에만 다음 단계로 넘어가며 예상하지 못한 예외도 확인된 단계를 유지합니다. [#266](https://github.com/mochafreddo/stock-scout/issues/266)에 따라 순위 요청·응답 검사·입력 종목 구성과 종목 식별 실패는 `ranking`이며, 이 단계의 예상하지 못한 예외도 같은 단계를 유지합니다. #263의 응답 검증 실패는 아래 상세 진단 계약을 따르며, 위치를 특정할 수 없는 실패는 `location: null`입니다.

[#263](https://github.com/mochafreddo/stock-scout/issues/263)에 따라 근거·판단 응답의 필수 필드 누락은 `missing_required_field`, 실제 열람 기록이 없는 출처는 `unobserved_source`, 존재하지 않는 근거 ID는 `unknown_evidence_id`, 다른 증권의 근거 참조는 `cross_security_evidence`로 구분합니다. 기존 `error: MODEL_OUTPUT`과 종료 코드 1, 빈 stdout은 유지합니다. 필드의 값이나 형식이 잘못됐지만 이 네 사유로 확정할 수 없으면 `unknown`입니다.

`location`은 `evidence[0].subsequentChanges`, `judgments[1].evidence[0]`처럼 코드가 아는 응답 배열·필드명과 0부터 시작하는 번호만 담습니다. 입력 종목 순번이 아닌 응답 위치이며, 응답 전체 오류나 항목을 특정할 수 없는 경우는 `null`입니다. 예상하지 못한 필드명이 있으면 그 이름을 노출하지 않고 해당 응답 항목까지만 표시합니다. 기존 검증 순서에서 처음 발견한 조건 하나만 보고합니다. 판단 응답은 모든 항목의 형식을 먼저 검사한 뒤 증권·근거 연결을 검사하므로 뒤 항목의 형식 오류가 앞 항목의 잘못된 참조보다 먼저 보고될 수 있습니다. 추가 모델 호출·조회·재시도나 한도 변경은 없습니다.

단계와 원인의 확인 여부는 독립적입니다. 코드가 직접 확인한 `RANKING_INCOMPLETE`·`IDENTITY_AMBIGUOUS`·`SENSITIVE_OUTPUT`·`siwc_refresh_not_allowed`·`siwc_relogin_required`는 해당 내부 오류가 전달된 경우 같은 철자의 `reason`으로 제공합니다. 조회 중 코드가 확인한 KIS·모델 인증 실패는 `stage: retrieval`과 `reason: AUTH_FAILED`로 구분합니다. 모델·조회 한도, 불완전 완료·시간 제한, 검색 장애·미지원, 구독 한도·유료 예산 확인 실패도 내부에서 확인한 경우 기존 오류 코드와 같은 원인을 제공합니다. 순위 수집 중 공용 KIS 인증 경로가 `AuthError`로 확인한 실패는 기존 `error: RANKING_FAILED`를 유지하며 `stage: ranking`, `reason: AUTH_FAILED`로 제공합니다. 상세 진단으로 구분하지 못하는 `RANKING_FAILED`·`QUERY_FAILED`·`MODEL_OUTPUT` 등의 오류와 미등록 예외는 `reason: unknown`입니다. 기존 `error`는 호환을 위해 예외 메시지로 결정하는 동작을 유지하므로 진단 원인과 다를 수 있습니다. 개별 KIS 조회 결과에서 민감값을 발견한 경우에도 기존 `error: QUERY_FAILED`를 유지하고 `reason: SENSITIVE_OUTPUT`을 전달합니다. 알려진 식별자나 `siwc_` 접두사를 흉내 낸 외부 예외 메시지만으로 `reason`을 확정하지 않습니다.

진단에는 모델 원문·외부 메시지·인증 값·개인 경로를 추가하지 않으며 추가 조회·모델 호출·재시도를 하지 않습니다. 실행 전 런타임·정적 모듈 로딩 실패·강제 종료·진단 출력 자체의 실패는 JSON 진단 보장 범위 밖입니다. 기본 진단 구현은 실제 실패 진단·고정 표본 평가·실제 KIS·OpenAI 검증이나 상위 티켓 완료를 뜻하지 않습니다.

공개 CLI 회귀 검사는 `node --test tests/llm-security-probe.test.mjs`로 실행하세요. 인수·평가 파일 실패와 예상하지 못한 예외의 진단, 입력 실패 뒤 외부 요청 0회, 정상 입력 뒤 단계 전환, 외부 식별자 흉내와 인증 안내 보존을 확인합니다. 외부 HTTP와 시각은 모의 처리하므로 실제 서비스 동작을 입증하지는 않습니다. SIWC 동적 import 실패도 모의 검사로 확인합니다. 조회·판단 준비의 예상하지 못한 예외, 외부 HTTP 예외, 검증 전후의 단계 전환, 조회 중 인증 실패와 최종 직렬화 실패도 모의 검사합니다. 기존 검사 순서의 첫 거부 조건을 유지하고 추가 요청이 없음을 확인합니다. #263의 상세 거부 사유·응답 위치, 응답 순서 변경, 복합 오류의 우선순위와 동적 필드명·값의 비노출도 확인합니다.


[#264](https://github.com/mochafreddo/stock-scout/issues/264)에 따라 `retrieval`·`judgment` 실패의 `diagnostic.statistics`에는 두 단계의 통계를 제공합니다. 각 단계의 `status`는 `completed`·`failed`·`not_started`이며 `elapsedMs`는 준비와 검증을 포함해 완료 또는 중단 시점까지 단조 시계로 측정한 밀리초입니다. 미시작 단계는 `elapsedMs: null`과 호출 수 0으로 구분합니다. 다른 단계의 실패와 성공 출력에는 통계를 추가하지 않습니다.

`modelRequests`는 실제 전송을 시도한 모델 HTTP 요청 수로 실패한 시도도 포함합니다. 전송 전에 공통 한도로 차단한 요청은 포함하지 않습니다. `infoToolCalls`는 KIS 정보 조회 도구 실행 횟수이며 도구 한도로 거부된 실행도 포함합니다. 인증·재발급 등 내부 HTTP 요청 수와는 다릅니다. `observedWebToolCalls`는 단계 안에서 관측한 서로 다른 웹 도구 호출 ID 수이며 여러 이벤트나 모델 요청에 같은 ID가 반복되어도 한 번만 셉니다. 공급자 내부 HTTP 요청 수는 아닙니다. 세 종류의 호출은 합산하지 않으며 ID 원문은 진단에 넣지 않습니다.

조회·판단 시간 제한과 일반 실패, 실패한 HTTP 시도, 웹 호출 ID 중복, 미시작·완료 단계 보존을 같은 공개 CLI·외부 HTTP 모의 검사로 확인합니다. 기존 호출·시간 한도와 추가 조회·재시도 금지는 유지하며 실제 KIS·OpenAI 진단 및 고정 표본 평가는 이 변경의 검증 범위 밖입니다.

## 로컬 검증과 실제 평가

```sh
node --test tests/llm-security-probe.test.mjs tests/siwc-auth.test.mjs tests/siwc-refresh.test.mjs
npm run check
npm run typecheck
npm test
```

테스트는 공개 CLI와 실제 로컬 callback 서버를 실행하되 OpenAI·KIS HTTP와 시각을 대체합니다. callback 리스너를 금지하는 실행 환경에서는 loopback 허용이 필요하며 외부 서비스 접근으로 대체하지 마세요.

보통주·적격 ADR·우선주 ADR·워런트·ETF·ETN과 종류주, 유형 미확인·현재성 불확실·조회 실패, 식별 모호함, 모델 완료 누락과 근거 연결을 모의 검사합니다. 이 검사는 통제된 모델 응답을 처리하는 계약 검사이며 LLM의 실제 분류 정확도 평가는 아닙니다. 실제 평가에는 독립적으로 확인한 현재 표본 정답과 실제 KIS·검색·모델 응답을 대조해야 합니다. 제외 대상의 잘못된 포함이나 근거 없는 유형 확정이 없어야 하며 보통주와 적격 ADR의 실제 포함도 필요합니다.

모든 표본을 제외하는 결과는 검증 성공이 아닙니다. 실제 호환성·유형·현재 적용 가능성을 확인하지 못한 조건은 미검증으로 남기며 #250과 장전 데이터·일정·운영값의 후속 차단을 자동으로 해제하지 않습니다.

### #252 구독 인증 갱신의 검증 범위

[#252](https://github.com/mochafreddo/stock-scout/issues/252)의 자동 갱신은 [ADR 0008](adr/0008-siwc-preflight-refresh.md)과 [확정 설계](siwc-refresh-design.md)를 따릅니다. CLI의 입력·stdout·stderr·종료 코드, 인증 파일 변화, 외부 인증·모델 요청을 검증 경계로 사용합니다. 합성 인증과 모의 HTTP·시각으로 갱신·별도 프로세스 재사용, 시간 경계, 권한·신원 검증, 동시 실행, 저장 실패, 무효화·일시 오류와 취소를 확인합니다. 이 검사는 실제 계정의 갱신 성공을 입증하지 않습니다.

실제 갱신과 다음 별도 프로세스의 재사용은 [#253](https://github.com/mochafreddo/stock-scout/issues/253)의 후속 검증입니다. 이번 구현에서는 실제 인증 파일을 읽거나 수정하지 않고 공식 로그인·갱신과 실제 KIS·모델 요청도 수행하지 않습니다. 종목 유형 정확도와 장전 데이터·일정·운영값의 남은 검증은 계속 별개입니다.

### 고정 표본을 같은 판단 경로로 평가하기

[#260의 표본 조사와 입력 파일](security-type-evaluation-samples.md)에 2026-10-22 확인한 8개 사례·11개 증권의 독립 정답을 기록했습니다. 2026-10-22 후속 합의로 자료 부족·미해결 충돌의 실제 사례 확보를 필수 준비 조건에서 제외했습니다. 표본 버전 `2026-10-22.2`는 `sample_ready`이며 이 상태는 실제 모델 평가나 다른 실행 선행 조건의 충족을 뜻하지 않습니다. 모델용 JSON과 평가자용 정답을 분리했으며 이번 조사는 실제 모델 평가 통과가 아닙니다.

평가 전용 입력 파일에는 정답 없이 거래소·종목 코드만 넣으세요. 제품의 기본 실행은 계속 KIS 순위를 자동 수집합니다. 다음은 같은 회사의 서로 다른 ADR을 함께 확인하는 입력 예입니다.

```json

```

```sh
node --env-file=.env scripts/llm-security-probe.ts /absolute/private/stock-scout gpt-6.1-sol --evaluation-input /absolute/private/adr-case.json
```

이 모드는 순위 조회를 생략하고 같은 자료 조회·판단 경로를 실행합니다. 결과의 `inputMode: evaluation`을 확인하세요. 실제 순위에 포함됐다는 의미가 아니며 순위나 증권 식별자를 만들어 넣지 않습니다. 입력에 정답이나 임의 필드를 추가하지 마세요.

평가를 시작하기 전에 모델·구현·설정을 고정하고 공식 근거로 표본 정답을 별도로 확정하세요. 정답 파일과 참고 해설은 모델 요청에 넣지 않습니다. 보통주, 별도 종류주, 보통주·우선주 ADR, 우선주, 워런트, ETF·ETN과 후속 변경은 고정 표본의 실제 모델 평가로 다루세요. 자료 부족·미해결 충돌의 안전한 결과 처리는 통제된 HTTP·모델 응답의 CLI 회귀 검사로 확인하고, 운영 중 발견하는 실제 사례를 추가하세요. 이 두 종류의 실제 표본 확보는 평가 시작의 필수 조건이 아닙니다. 기존 표본의 입력 연결과 현재 적용 가능성도 다시 확인해야 합니다. 예를 들어 KIS의 VXX 입력은 저장 관측상 `AMS/VXX`이며 외부 상장 시장의 명칭과 KIS 조회 코드를 혼동하지 마세요.

사례별로 실행하되 같은 회사의 별도 증권을 구분하는 사례는 관련 종목을 함께 넣으세요. 전체 사례를 도는 것을 한 회차로 계산하며 각 실행은 기존 한도를 지킵니다. 실제 열린 출처와 발췌문, 증권 연결, ADR 기초 권리, 후속 변경과 현재 적용 가능성을 독립 정답에 대조하세요. 유형 문자열의 일치만으로 근거의 타당성이 확인되지는 않습니다. 매회 잘못된 포함과 근거 없는 유형 확정이 없어야 하고 보통주·적격 ADR의 실제 포함도 있어야 합니다.

같은 모델·설정·구현으로 세 회차를 모두 통과해야 고정 표본 평가를 완료한 것으로 기록하세요. 실패한 실행도 보존하고 중간에 수정하면 수정된 버전으로 세 회차를 다시 시작하세요. 표본 정답이나 현재성을 확보하지 못한 사례는 미검증으로 남기며 전체 통과를 선언하지 마세요. 별도로 실제 KIS 상위 순위를 수집해 여러 종목을 함께 처리하는 실행도 확인하세요. 모의 검사, 실제 순위 실행, 고정 표본 평가의 결과와 한계는 각각 기록하세요.

### 로그인 재개 전 기록

공식 로그인 창을 한 번 열었지만 5분 안에 callback을 받지 못해 `siwc_login_timeout`으로 종료했습니다. 사용자는 원격 작업 중이므로 실제 로그인은 퇴근 후 진행하기로 했습니다. 이번 실행에서 토큰 교환·실제 구독 모델·검색 호출과 실제 유형 정확도 평가는 수행하지 못했습니다. 기존 Codex 인증을 대용으로 사용하거나 유료 API로 우회하지 않았습니다.

당시에는 로그인 미완료로 실제 구독 도구 호환성과 표본 평가가 미검증이었습니다. 이후 로그인 재개 결과는 아래 별도 기록을 따르며, 로컬 검사와 음성 대조를 실제 호출 결과와 구분합니다.
