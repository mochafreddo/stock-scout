# KIS 순위에서 LLM으로 종목 유형 확인하기

이 CLI는 KIS 순위를 자동 수집한 뒤 LLM이 조회 근거로 개별 상장 종목의 유형을 판단하는 검증 도구입니다. [#250](https://github.com/mochafreddo/stock-scout/issues/250)과 [ADR 0007](adr/0007-llm-security-type-judgment.md)의 작은 흐름을 구현합니다. 매수 추천이나 장전 보고서를 생성하지 않으며, 정상 출력에서도 `validation: unverified`, `dataSession: null`을 유지합니다.

## 현재 검증 상태

실제 여섯 순위의 두 실행은 종목별 결과와 집계를 남겼으며 모두 `analysis_insufficient`와 종료 코드 2로 끝났습니다. 이 기록은 여러 종목을 처리하고 분석 불충분을 알리는 실행 흐름의 근거입니다. [ADR 0010](adr/0010-incremental-security-type-validation.md), [실행 이력](security-type-history.md)

판단 품질은 별도 표본으로 확인했습니다. [#261의 첫 점검](security-type-evaluation-samples.md#261-첫-점검-결과)은 AAPL·BBD·BBDO의 결과와 제출 근거를 대조했습니다. #277은 제한된 표본과 종목별 조사 경과를 확인했습니다. 전체 시장의 유형 정확도와 추천 품질은 미검증입니다. [#277](https://github.com/mochafreddo/stock-scout/issues/277)

## 실행 책임

[종목 유형 판단 실행 모듈](../scripts/security-type-assessment.ts)은 도구를 사용하는 하나의 모델 흐름에서 자료 조회와 최종 유형 판단을 처리합니다. 실제 열람 출처의 ID 연결·결과 검증, 명시적 완료·호출·시간 제한도 모듈에서 관리합니다. [CLI](../scripts/llm-security-probe.ts)는 인증, 순위 또는 평가 입력 준비, 출력과 종료 처리를 맡습니다. 구조 변경의 결정은 [ADR 0010](adr/0010-incremental-security-type-validation.md)을 따릅니다.

기존 실행 인수와 공용 KIS·SIWC 경로는 유지합니다. 별도 조회 산출물과 두 번째 판단 호출, 단계별 출력 통계는 제거했습니다. 결과 필드 변경과 실제 검증 범위는 아래에서 확인하세요.

## 종목 유형 흐름 실행하기

개발·테스트에서 모델 호출이 필요하면 `gpt-6-luna`를 사용합니다. 실사용에서는 사용자가 선택한 astra·sol 모델 ID를 CLI 인수로 지정합니다. 모델을 자동 교체하지 않으며 실제 계정의 지원 여부와 결과는 별도로 확인합니다.

사용 가능한 구독 모델 ID와 거래소별 각 순위의 상위 N을 지정하세요. 다음 예제의 모델은 실제 계정의 지원 모델인지 확인해야 합니다. `.env`는 Node의 명시적 옵션으로만 읽습니다. 기존 두 KIS 인증 값이 프로세스 환경에 이미 있으면 `--env-file`을 생략하세요.

```sh
node --env-file=.env scripts/llm-security-probe.ts /absolute/private/stock-scout gpt-6-luna 1
```

NAS·NYS·AMS의 거래량·거래대금 순위를 각각 한 페이지 조회하고 원래 순위가 N 이하인 행만 선택합니다. 같은 거래소·종목 코드의 중복은 연결하고 순위 출처를 보존합니다. 같은 회사의 다른 종류주·ADR을 합치지 않으며 제외된 종목을 아래 순위로 보충하지 않습니다. 필요한 상위 N을 확보하지 못했는데 연속 조회 표시가 있으면 실패합니다.

실험용 입력 N은 1~10입니다. 모델 요청 최대 12회, 종목 정보 도구 최대 32회, 관측한 웹 호출 최대 32회의 한도를 적용합니다. 이는 서버가 이미 실행한 웹 호출 수의 사전 상한을 보장하지 않으며, 유료 검색 비용 상한을 보장할 수 없는 이유 중 하나입니다. 종목 정보 도구는 기존 KIS 인증 잠금과 충돌하지 않도록 순서대로 실행합니다. 순위 수집 뒤 시작하는 모델 흐름의 전체 시간 제한은 180초입니다. 별도 조회 전용 120초 제한은 없습니다. KIS 조회 자체에는 기존 요청별 시간 제한과 만료 복구 정책이 적용됩니다. 이 값은 최종 장전 지원 시간이나 운영값의 실측이 아닙니다.

LLM에는 입력 종목에 한정한 `get_infos`, OpenAI 웹 검색과 읽기 전용 `list_sources`를 제공합니다. `get_infos`는 모델이 필요한 종목 목록을 요청한 순서대로 조회하고 종목별 결과를 반환합니다. 빈 목록·중복·입력 밖 종목과 남은 논리 조회 한도를 첫 조회 전에 검사합니다. 개별 404는 해당 종목의 실패로 남기고 계속하지만 공통 장애·인증·취소·한도 도달은 전체 실패입니다. 모든 종목을 미리 조회하지 않습니다.

성공한 KIS 조회와 완료된 HTTPS `open_page`·`find_in_page`에만 코드가 실행별 출처 ID(`s1` 등)를 부여합니다. 같은 원본 출처를 다시 읽어도 ID를 유지합니다. `get_infos`는 각 성공한 조회의 출처 ID를 반환하고, `list_sources`는 등록된 ID와 원본 출처 목록만 반환하며 외부 요청을 하지 않습니다. 검색 결과 목록·인용 URL·열람 실패에는 웹 출처 ID를 부여하지 않습니다. 웹 검색의 실제 지원은 모델·계정 정책에 따라 달라지며 미지원 오류를 다른 서비스로 자동 우회하지 않습니다.

묶음 하나를 정보 조회 한 번으로 세지 않습니다. 정보 조회 32회 한도는 시작하는 종목별 논리 조회에 적용합니다. `statistics.infoToolCalls`는 스키마에 맞는 도구 호출에서 요청한 종목 수이며 사전 거부·중간 실패 뒤 시작하지 않은 항목도 포함합니다. 실제 HTTP 전송 횟수와 구분하세요. 통합 경로의 KIS 집계는 기존처럼 인증·허용된 재조회까지 실제 전송마다 셉니다. 자세한 계약은 [보고서 완료 개선 설계](buy-candidate-completion-design.md)를 따릅니다.

모델은 도구를 사용한 뒤 입력 종목마다 최종 유형·현재 적용 여부·판단 이유와 근거를 제출합니다. 각 근거에는 실제 읽은 출처의 `sourceId`와 짧은 `explanation`만 필수로 요구합니다. 코드는 등록된 출처 ID에서 원본 URL 또는 `kis:거래소:종목코드`를 복원해 종목별 근거의 `source`로 출력합니다. 별도 `e1` 근거 ID나 중간 조회 산출물은 만들지 않습니다. 미등록 출처 ID와 다른 증권의 KIS 출처 참조는 전체 실패입니다.

자료의 날짜·변경 정보는 판단에 영향을 줄 때 설명합니다. 모든 근거에 기준일·적용일·후속 변경·현재성 필드를 각각 채울 필요는 없습니다. 개별 증권과 자료의 연결, 확인 가능한 최신 자료와 알려진 반대 근거, ADR의 보통주 기초 권리는 계속 확인하며 불확실하면 제외합니다. 이름·티커·모델 기억·검색 요약만으로 확정하지 않습니다.

호스팅된 웹 검색은 클라이언트에 원문 본문 전체를 제공하지 않습니다. `explanation`은 모델의 근거 설명이며 원문과 바이트 단위로 대조한 인용문이 아닙니다. 실제 출처 연결과 내용의 타당성은 구분하며 자료의 의미·증권 연결·현재 적용 가능성은 별도 점검이 필요합니다. 날짜가 없는 페이지도 다른 근거로 현재 적용 여부를 확인할 수 있지만 확인하지 못하면 제외합니다. 원문과 인용의 보관·공개는 출처의 허용 범위를 따르세요.

웹 열람 기록은 SDK의 클라이언트 도구 실행 전에 등록합니다. `store: false`에서는 성공한 웹 동작을 다음 모델 요청에 그대로 재구성하고, SDK가 재구성하지 못하는 개별 열람 실패 결과만 실패를 나타내는 고정 문장으로 전달합니다. 실패를 완료된 웹 동작이나 출처 ID로 바꾸지 않습니다. 출처 목록을 받는 후속 모델 요청도 같은 모델 요청 12회·전체 180초 한도를 공유합니다.

최종 판단이 `unknown`이 아닌데 근거 목록이 비었거나 인용 근거가 모두 원본 유형 코드 `01`만 관측된 해당 증권의 KIS 상품정보이면, 해당 종목의 유형 확정을 거부하고 `type: unknown`, `applicable: false`, `included: false`로 제외합니다. `typeRejection.submittedType`에 모델이 제출한 유형을, `typeRejection.reason`에 각각 `missing_type_evidence` 또는 `kis_broad_stock_only`를 남기고 `reason`으로 제외 사유를 설명합니다. 나머지 종목의 판단은 계속하며 모두 미확인이면 `analysis_insufficient`와 종료 코드 2를 반환합니다. 모델이 식별을 확정하지 못한 종목은 `identity: ambiguous`를 유지하고 `type: unknown`, `applicable: false`, `included: false`로 제외합니다. `typeRejection.reason: identity_unconfirmed`와 `submittedType`으로 원래 유형 주장과 식별 미확인 사유를 남깁니다. 원본 거래소·종목 코드·순위를 보존하고 미확인 수에 집계하며, 유형 미확인과 구분합니다. 개별 제외 전에 전체 입력 소속·누락·중복과 모든 제출 근거의 참조를 검증합니다. 미등록 출처 ID·다른 종목의 KIS 출처 참조·코드가 발견한 순위 식별자 충돌과 공통 실패는 계속 전체 실패이며 미확인 표시로 숨기지 않습니다.

`01`은 보통주·ETF 등 세부 유형을 입증하지 못하는 넓은 주식 코드이므로 상품명·상품분류명으로 이를 보충하지 않습니다. 식별이 확인된 종목의 명시적인 `unknown` 제외나 충분한 근거로 확정한 종목에는 `typeRejection`을 추가하지 않으며, 다른 KIS 코드나 독립적으로 열린 유형 근거를 일괄 허용·금지하는 규칙은 추가하지 않습니다. 이 검사를 통과해도 자료 내용과 현재 적용 가능성의 타당성이 입증된 것은 아닙니다. 개별 제외 정책은 [ADR 0010](adr/0010-incremental-security-type-validation.md)을 따르며, 과거 실제 실행의 전체 실패 기록은 당시 소스의 결과로 보존합니다. 이번 단일 흐름의 실제 점검과 남은 조건은 [현재 검증 상태](#현재-검증-상태)를 따릅니다.

코드는 근거가 실제 조회에 연결되고 필수 항목이 있는지 검사합니다. 자료의 의미, 유형과 현재 적용 가능성의 타당성은 LLM 판단과 별도 평가 대상입니다. 링크가 연결됐다는 사실만으로 판단이 맞다고 보장하지 않습니다.

## 결과와 실패 구분하기

stdout에는 완성된 결과 JSON 한 줄만 출력합니다. `securities`에서 원본 거래소·종목 코드·순위, 유형, 포함 여부, 판단 이유와 연결된 근거를 확인하세요. 각 종목의 `evidence`에는 `sourceId`·`source`·`explanation`이 담기며, 별도 `evidenceRecords`는 제공하지 않습니다. `lookups`에는 허용 필드로 제한된 KIS 종목 정보와 개별 조회 실패가, `webSources`에는 실제로 읽은 웹 URL이, `webFailures`에는 개별 웹 호출 실패가 담깁니다. 순위 관측에는 요청 경로·거래 ID·파라미터도 보존합니다. `coverage`에서 입력·포함·제외·미확인 수와 개별 조회 실패 수를 확인하세요.

| 결과 | 종료 코드 | 의미 |
| --- | --- | --- |
| `status: assessed` | 0 | 유형 확인 결과입니다. 모두 제외 대상일 수 있으며 매수 추천이나 실제 정확도 검증 완료가 아닙니다. |
| `status: analysis_insufficient` | 2 | 모든 종목이 식별 미확인·유형 미확인 또는 현재 적용 여부 미확인입니다. 정상적인 후보 없음과 구분합니다. |
| stderr의 안전한 오류 코드, stdout 없음 | 1 | 순위·인증·모델·공통 조회 실패, 입력 식별자 충돌, 형식·근거 오류 등으로 실행을 완료하지 못했습니다. |

정보 조회의 구조화된 `EGW00316`은 [공통 조회 정책](kis-probe-reference.md#요청과-제한)에 따라 기존 단계 마감 안에서 1초 뒤 최대 한 번 재시도합니다. 허용된 복구 뒤에도 실패하면 아래 전체 실패 경계를 유지합니다. 개별 정보 요청의 HTTP 404는 해당 종목의 조회 실패로 기록하고 나머지 분석을 계속합니다. 다른 허용 근거가 없다면 제외합니다. 인증·전송·응답 구조·정체를 알 수 없는 KIS 오류는 개별 종목의 부재로 단정하지 않고 전체 실패합니다. 모델이 정보 도구에 순위 밖 종목을 요청하거나 결과에서 종목을 추가·누락·중복하면 실패합니다.

개별 웹 페이지 조회 실패는 해당 호출의 실패로 기록하고 다른 근거가 없으면 그 종목을 제외합니다. 특정 URL의 `open_page`·`find_in_page` 실패만 개별 처리합니다. 검색 자체의 실패나 실패 범위를 특정할 수 없는 호출, OpenAI 요청의 인증·통신·서비스 오류와 스트림의 명시적 실패는 전체 실패입니다.

주요 오류는 `RANKING_FAILED`, `RANKING_INCOMPLETE`, `IDENTITY_AMBIGUOUS`, `AUTH_FAILED`, `QUERY_FAILED`, `SEARCH_FAILED`, `MODEL_FAILED`, `MODEL_INCOMPLETE`, `MODEL_OUTPUT`, `MODEL_LIMIT`입니다. 인증 파일 오류는 `siwc_`로 시작합니다. 모델의 중간 도구 단계와 최종 응답 모두 명시적인 `response.completed`를 받아야 하며 JSON이나 스트림 종료만으로 성공을 판정하지 않습니다.

구독 한도 소진의 명시적 오류는 `SUBSCRIPTION_LIMIT`로 구분합니다. 기존 유료 API 키가 있어도 이 도구의 서버 실행 웹 검색을 포함한 최대 과금액을 보장할 수 없으면 `PAID_BUDGET_UNPROVABLE`로 중단하고 유료 요청을 보내지 않습니다. 인증 실패·검색 미지원·일반적인 429·사용량 확인 불가에서는 유료 요청을 보내지 않습니다. 비용 상한을 보장할 수 있는 유료 경로는 후속 구현 대상입니다.

### 종목별 조사 경과 대조하기

`webResearch`는 코드가 관측한 웹 도구 완료 이벤트를 모델 요청 번호 `request`와 함께 남깁니다. `action`·`status`·`queries`·`url`을 통해 검색과 실제 페이지 열람·실패를 구분하세요. 검색문 목록이 없으면 단일 검색문을 사용하며 유효한 문자열이 아닌 값은 기록하지 않습니다. 알 수 없는 동작·상태는 `unknown`, 없는 URL은 `null`입니다. 자격정보가 포함됐거나 유효한 HTTPS 주소가 아닌 URL도 관측 기록과 `webFailures`에서 `null`로 남깁니다. 검색문·URL은 기존 민감값 검사를 통과한 값만 기록하며, 출처로 인정하는 조건은 기존 `webSources`와 같습니다. 실패 전에 관측한 기록은 stderr의 `diagnostic.typeAssessment.webResearch`에 남습니다. 이벤트가 없으면 이 진단 필드는 생략됩니다.

이 기록은 모델이 설명한 판단·중단 사유와 별개입니다. 종목별 `reason`·근거와 대조하되 검색문이나 URL을 특정 종목과 연결할 수 없으면 미확인으로 남기세요. 검색 결과나 성공 상태만으로 페이지 내용의 충분성·유형의 정확성을 인정하지 않으며, 기록이 없다고 검색 미수행이나 자료 부재를 단정하지 마세요. 검색 횟수·페이지 수를 정상 완료의 새 조건으로 강제하지 않습니다. 조사 미수행이 확인된 종목은 미확인으로 제외하고 다른 유효 결과는 유지하며, 품질 평가는 [#277 설계](security-type-evaluation-samples.md#277-종목별-조사-경과의-평가)를 따릅니다.

### 기본 실패 진단 읽기

실패 시 기존 stderr JSON의 `diagnostic`에 `stage`·`reason`·`location`을 제공합니다. 기존 `error`·인증 재시도 시각·로그인 안내와 종료 코드는 유지합니다. 성공 결과와 정상적인 분석 불충분에는 진단을 추가하지 않습니다. 독립된 인증·KIS 관측 CLI의 출력 계약도 유지합니다.

인수·평가 파일 검사 실패와 이 범위의 예상하지 못한 예외는 `stage: input`, `reason: unknown`, `location: null`입니다. 초기 SIWC 인증 준비와 동적 import 실패는 `authentication`, 순위 요청·응답 검사·입력 종목 구성 실패는 `ranking`입니다. 하나로 합친 모델 흐름의 준비·조회·판단·결과 검증 실패는 `assessment`, 완성된 결과 구성·민감값 검사·직렬화 실패는 `output`입니다. 예상하지 못한 예외도 확인한 단계를 유지합니다. 더 이상 `retrieval`·`judgment` 단계를 출력하지 않습니다.

필수 필드 누락은 `missing_required_field`, 등록되지 않은 출처 ID는 `unobserved_source`, 다른 종목의 KIS 출처 참조는 `cross_security_evidence`입니다. 기존 `error: MODEL_OUTPUT`과 종료 코드 1, 빈 stdout은 유지합니다. 그 밖의 값·형식 오류나 미확정 원인은 `unknown`입니다. 폐기한 중간 근거 ID의 `unknown_evidence_id` 진단은 제거했습니다.

`location`은 `judgments[1].evidence[0].sourceId`처럼 코드가 아는 응답 배열·필드명과 0부터 시작하는 번호만 담습니다. 입력 순서와 다른 응답 위치일 수 있으며 위치를 특정할 수 없으면 `null`입니다. 예상하지 못한 필드의 이름과 값은 노출하지 않습니다. 최초 검증 실패 한 건을 보고하며 추가 조회·모델 호출·재시도를 하지 않습니다.

진단의 원인은 코드가 직접 확인한 경우에만 확정합니다. KIS·모델 인증 실패는 `AUTH_FAILED`, 한도 도달·불완전 완료·검색 장애·구독 소진 등은 해당 내부 오류의 고정 사유로 구분합니다. 순위 중 인증 실패는 `error: RANKING_FAILED`와 `stage: ranking`, `reason: AUTH_FAILED`를 제공합니다. 외부 예외 메시지가 알려진 식별자를 흉내 내도 원인을 확정하지 않습니다. 비밀 값·모델 원문·개인 경로는 진단에 넣지 않습니다. 정적 모듈 로딩 실패·강제 종료·진단 출력 자체의 실패는 JSON 진단 보장 범위 밖입니다.

`assessment` 실패의 `diagnostic.statistics`와 정상 결과의 `statistics`는 모델 흐름 전체의 통계입니다. `status`는 `completed` 또는 `failed`, `elapsedMs`는 준비·검증을 포함해 완료 또는 중단까지 단조 시계로 측정한 밀리초입니다. 두 단계 통계와 미시작 단계 출력은 제거했습니다. 다른 단계의 실패에는 모델 통계를 추가하지 않습니다. `coverage.inclusionRate`는 포함 수를 입력 수로 나눈 값입니다.

`modelRequests`는 전송을 시도한 모델 HTTP 요청 수로 실패한 시도도 포함하며, 전송 전 한도로 차단한 요청은 포함하지 않습니다. `infoToolCalls`는 KIS 정보 도구 실행 횟수로 한도로 거부된 실행도 포함합니다. 인증·재발급 등 내부 HTTP 요청 수와는 다릅니다. `observedWebToolCalls`는 실행 중 관측한 서로 다른 웹 도구 호출 ID 수이며 같은 ID가 반복돼도 한 번만 셉니다. 공급자 내부 HTTP 요청 수는 아닙니다. 세 종류를 합산하지 않으며 ID 원문은 진단에 넣지 않습니다.

### 유형 판단의 요청별 진단 읽기

실패의 `diagnostic.elapsedMs`는 입력 검사·인증을 포함한 CLI 전체 경과 시간입니다. `diagnostic.typeAssessment`는 후보군·매수 후보·유형 검증 CLI가 함께 사용하는 유형 판단 관측 결과입니다. 기존 `diagnostic.reason`·`location`과 `diagnostic.statistics`의 의미, 성공 출력과 종료 코드는 유지합니다.

| 필드 | 확인할 내용 |
| --- | --- |
| `statistics` | 유형 판단 상태·경과 시간과 기존 모델·정보 도구·관측 웹 도구 호출 집계 |
| `cause` | 코드가 직접 관측한 중단 사유. 기한 초과, 완료 누락·중복, 공급자 실패·불완전 응답, 통신 오류 등을 구분하며 미확정 원인은 `unknown` |
| `lastProgress` | 코드가 확인한 마지막 진행 위치의 고정 식별자 |
| `requests` | 각 유형 모델 요청의 순번·경과 시간·확인한 HTTP 상태·완료 이벤트 수·종료 상태와 사유 |

요청 시간은 HTTP 응답 헤더를 받은 시점이 아니라 스트림 종료 또는 중단까지 측정합니다. 도구 왕복으로 여러 모델 요청이 발생해도 각 요청의 기록을 구분합니다. 완료 이벤트를 받은 뒤 오류가 발생하면 그 응답을 정상 완료로 해석하지 마세요. 기한으로 중단된 스트림은 완료 이벤트 없는 자연 EOF와 구분하며, 먼저 관측한 실패 사유를 후속 취소로 덮어쓰지 않습니다. 관측하지 못한 HTTP 상태·완료 여부는 `null` 또는 `unknown`으로 남깁니다.

유형 판단을 시작하지 않았으면 `statistics.status`는 `not_started`, 시간은 `null`, 호출 수는 0이며 `requests`는 비어 있습니다. 이미 유형 판단을 완료한 뒤 다른 단계에서 실패했다면 완료한 유형 판단의 기록을 보존합니다. 모델 요청 집계는 전송 시도 수이며 성공한 응답 수가 아닙니다. 공급자가 불완전 응답을 보냈다는 관측만으로 공급자 내부 원인까지 판단하지 마세요.

새 진단에는 원문 오류 메시지·인증값·프롬프트·모델 응답·웹 원문·헤더·개인 경로를 넣지 않습니다. 진단 수집 때문에 외부 요청·재시도·시간 또는 호출 상한을 늘리지 않습니다. 이 정보는 다음 실행에서 원인을 구분하기 위한 것이며 과거에 수집하지 않은 모델 이벤트를 복구하거나 실제 유형 판단의 정확성을 입증하지 않습니다.

공개 CLI 회귀 검사는 `node --test tests/llm-security-probe.test.mjs`로 실행하세요. 입력·인증·순위·모델·출력 실패, 출처 연결, 제한 도달과 비밀 비노출을 외부 HTTP·시각을 모의 처리해 확인합니다. 모의 검사로 실제 서비스 동작이나 유형 정확도를 입증하지는 않습니다.

### 공통 실행 기록으로 요청 관계 확인하기

상세 기록이 잘려도 `observation.summaries.stages`와 `modelRequests`에는 완료한 단계와 모델 요청 요약이 남습니다. 각 요청의 시작 시 `stageRemainingMs`로 공유하는 유형 단계 예산이 줄어드는지 확인하세요. `inputBytes`는 실제 전송 본문 크기이며 내용은 기록하지 않습니다. 독립 유형 CLI의 `executionRemainingMs`는 `null`이고, 통합 경로에서는 전체 마감도 적용합니다. 필드와 미관측 값의 의미는 [공통 요약 계약](rca-observability-design.md#2026-10-31-시간예산-요약-보강)을 따릅니다. [2026-10-31 고정 6종목 실행](buy-candidate-history.md#첫-실행-고정-6종목-유형-판단)은 유형 단계 제한으로 중단된 사례이며 정확도 평가나 최종 보고서 성공이 아닙니다.

세 CLI의 실패 JSON에는 기존 상세 진단과 별도로 최상위 `observation`을 제공합니다. 유형 모델의 `types.model.http`, 정보 조회·출처 목록 도구의 `types.info_tool`, 관측 웹 도구의 `types.web_tool`, 근거·결과 검증의 `types.validation`을 같은 실행 기록에서 확인하세요. 도구의 `parentId`는 호출을 낸 모델 요청에 연결되고, 모델 요청은 `types.model`에 연결됩니다. 유형 검증 CLI의 초기 SIWC 인증·KIS 순위 조회·최종 직렬화에도 같은 관측 소유자를 전달합니다. KIS 내부 작업의 상세 기록은 KIS 관측 구현 범위에 따릅니다.

요청의 `headersAt`은 상태 코드를 받은 시점이며 완료 시점이 아닙니다. `firstEventAt`·`lastEventAt`, `completionEvents`·`errorEvents`, `streamEnd`로 이벤트 수신과 자연 EOF·읽기 오류·취소를 구분하세요. 결과 검증에 실패해도 이미 정상 EOF를 확인한 전송을 통신 실패로 바꾸지 않습니다. `cancellationSource`의 `stage_limit`은 연결한 유형 판단 제한이 실제로 취소된 경우입니다. 통합 실행의 공통 마감이나 개장 경계는 해당 제한의 출처로 남기며, 출처가 확인되지 않으면 `unknown`입니다. 모델 요청 전 대기, 헤더 뒤 스트림 대기, 정보 도구 대기는 각각 해당 작업과 요청 기록으로 구분하세요.

`firstFailure`는 처음 관측한 실패이지 확정한 근본 원인이 아닙니다. 뒤따른 취소가 이 기록을 덮지 않으며 `finalError`는 기존 공개 오류와 연결된 작업을 가리킵니다. `coverage`는 실제 관측을 시작한 영역만 나타냅니다. 공통 작업 수·직렬화 크기 상한, 생략 계수와 `degraded`의 의미는 [공통 관측 계약](rca-observability-design.md#273의-공통-구현-계약)을 따릅니다. 관측을 위해 추가 요청·재시도·유료 전환을 하지 않으며, 독립 CLI의 기존 예산과 통합 CLI의 공통 예산은 각각 유지합니다.

#259 재개 보완으로 초기 인증 뒤 실패한 실행의 `diagnostic.inputSnapshot`에는 입력 모드·모델·순위 N, 원본 거래소·종목 코드·식별자·순위와 수집을 마친 순위의 관측 내역을 남깁니다. 빈 순위도 보존하며 순위 도중 실패하면 완료한 부분까지만 담습니다. 인증 값과 일치하는 내용이 있으면 스냅샷 전체를 생략합니다. 인증 경로와 모델 응답 원문은 담지 않습니다. 오류 코드·빈 stdout·종료 코드는 유지합니다. 프로세스 강제 종료까지의 영속 보관을 보장하지 않으므로 실행 전 명령·소스 해시·설정과 종료 결과·stdout·stderr는 접근을 제한한 저장소 밖 기록으로 보존하세요.

```sh
node --test tests/llm-security-probe.test.mjs tests/siwc-auth.test.mjs tests/siwc-refresh.test.mjs
npm run check

```

테스트는 공개 CLI와 실제 로컬 callback 서버를 실행하되 OpenAI·KIS HTTP와 시각을 대체합니다. callback 리스너를 금지하는 실행 환경에서는 loopback 허용이 필요하며 외부 서비스 접근으로 대체하지 마세요.

`npm test`와 이를 호출하는 기존 푸시 검사는 전체 테스트 전에 루프백 바인딩을 확인합니다. 바인딩 실패는 환경 오류로 표시하고 테스트를 실행하지 않습니다. 직접 `node --test`로 실행하는 집중 검사는 이 사전 검사를 거치지 않으므로 필요한 루프백 사용이 가능한 환경에서 실행하세요. 사전 검사 통과만으로 이후 모든 테스트의 리스너 생성이 보장되지는 않습니다.

보통주·적격 ADR·우선주 ADR·워런트·ETF·ETN과 종류주, 유형 미확인·현재성 불확실·조회 실패, 식별 모호함, 모델 완료 누락과 근거 연결을 모의 검사합니다. 이 검사는 통제된 모델 응답을 처리하는 계약 검사이며 LLM의 실제 분류 정확도 평가는 아닙니다. 후속 #261 점검에서는 실행 전에 고른 작은 표본의 독립 정답과 실제 결과·제출 근거를 대조합니다. 잘못된 포함과 근거 없는 유형 확정을 우선 확인하고 적격 종목 누락은 이유와 함께 개선 대상으로 기록합니다. 첫 점검 전에 모든 유형의 실제 포함을 요구하지 않습니다.

모든 종목이 미확인이면 분석 불충분이며, 확인된 비적격 유형만 있어 전부 제외된 정상 결과와 구분합니다. 실제 호환성·유형·현재 적용 가능성을 확인하지 못한 조건은 미검증으로 남기며 #250과 장전 데이터·일정·운영값의 후속 차단을 자동으로 해제하지 않습니다.

### #252 구독 인증 갱신의 검증 범위

[#252](https://github.com/mochafreddo/stock-scout/issues/252)의 자동 갱신은 [ADR 0008](adr/0008-siwc-preflight-refresh.md)과 [확정 설계](siwc-refresh-design.md)를 따릅니다. CLI의 입력·stdout·stderr·종료 코드, 인증 파일 변화, 외부 인증·모델 요청을 검증 경계로 사용합니다. 합성 인증과 모의 HTTP·시각으로 갱신·별도 프로세스 재사용, 시간 경계, 권한·신원 검증, 동시 실행, 저장 실패, 무효화·일시 오류와 취소를 확인합니다. 이 검사는 실제 계정의 갱신 성공을 입증하지 않습니다.

실제 갱신과 다음 별도 프로세스의 재사용 결과는 [구독 인증 검증 기록](siwc-refresh-live-validation.md)에 있습니다. 이 결과의 범위는 인증과 모델 목록 조회까지입니다.

### 고정 표본을 같은 판단 경로로 평가하기

현재 실행 흐름·판단 품질 점검 기준은 [ADR 0010](adr/0010-incremental-security-type-validation.md)을 따릅니다. #261은 실제 순위의 유용한 유형 결과를 기다리지 않고 기존 평가 입력 경로로 작은 독립 표본을 점검할 수 있습니다. 포함률·처리 시간은 측정값으로 기록하며 전체 표본 3회·적격 종목 전부 포함은 필수 관문이 아닙니다.

[#260의 표본 조사와 입력 파일](security-type-evaluation-samples.md)에 2026-10-22 확인한 8개 사례·11개 증권의 독립 정답을 기록했습니다. 2026-10-22 후속 합의로 자료 부족·미해결 충돌의 실제 사례 확보를 필수 준비 조건에서 제외했습니다. 표본 버전 `2026-10-22.2`는 `sample_ready`이며 이 상태는 실제 모델 평가나 다른 실행 선행 조건의 충족을 뜻하지 않습니다. 모델용 JSON과 평가자용 정답을 분리했으며 이번 조사는 실제 모델 평가 통과가 아닙니다.

평가 전용 입력 파일에는 정답 없이 거래소·종목 코드만 넣으세요. 제품의 기본 실행은 계속 KIS 순위를 자동 수집합니다. 다음은 같은 회사의 서로 다른 ADR을 함께 확인하는 입력 예입니다.

```json
{"securities":[{"exchange":"NYS","symbol":"BBD"},{"exchange":"NYS","symbol":"BBDO"}]}
```

```sh
node --env-file=.env scripts/llm-security-probe.ts /absolute/private/stock-scout gpt-6-luna --evaluation-input /absolute/private/adr-case.json
```

이 모드는 순위 조회를 생략하고 같은 자료 조회·판단 경로를 실행합니다. 결과의 `inputMode: evaluation`을 확인하세요. 실제 순위에 포함됐다는 의미가 아니며 순위나 증권 식별자를 만들어 넣지 않습니다. 입력에 정답이나 임의 필드를 추가하지 마세요.

평가를 시작하기 전에 모델·구현·설정을 고정하고 공식 근거로 표본 정답을 별도로 확정하세요. 정답 파일과 참고 해설은 모델 요청에 넣지 않습니다. 기존 표본에서 점검 목적에 필요한 작은 부분집합을 먼저 고르세요. 모든 유형·반례를 첫 실행 전에 평가할 필요는 없습니다. 자료 부족·미해결 충돌의 안전한 결과 처리는 통제된 HTTP·모델 응답의 CLI 회귀 검사로 확인하고, 운영 중 발견하는 실제 사례를 추가하세요. 이 두 종류의 실제 표본 확보는 평가 시작의 필수 조건이 아닙니다. 기존 표본의 입력 연결과 현재 적용 가능성도 다시 확인해야 합니다. 예를 들어 KIS의 VXX 입력은 저장 관측상 `AMS/VXX`이며 외부 상장 시장의 명칭과 KIS 조회 코드를 혼동하지 마세요.

사례별로 실행하되 같은 회사의 별도 증권을 구분하는 사례는 관련 종목을 함께 넣으세요. 선택한 사례별 결과를 기록하고 각 실행은 기존 한도를 지키세요. 실제 열린 출처와 발췌문, 증권 연결, ADR 기초 권리, 후속 변경과 현재 적용 가능성을 독립 정답에 대조하세요. 유형 문자열의 일치만으로 근거의 타당성이 확인되지는 않습니다. 선택한 표본의 잘못된 포함과 근거 없는 유형 확정을 먼저 확인하세요. 적격 종목 누락은 제외 사유와 함께 개선 대상으로 기록하세요.

선택한 입력·모델·구현·설정과 실패한 실행도 보존하세요. 수정 후에는 영향받는 회귀 검사와 사례를 다시 확인하세요. 전체 3회 반복은 필수 조건이 아닙니다. 표본 정답이나 현재성을 확보하지 못한 사례는 미검증으로 남기며 실제 점검 범위를 넘는 정확도를 주장하지 마세요. 별도로 실제 KIS 상위 순위를 수집해 여러 종목을 함께 처리하는 실행도 확인하세요. 모의 검사, 실제 순위 실행, 고정 표본 평가의 결과와 한계는 각각 기록하세요.
