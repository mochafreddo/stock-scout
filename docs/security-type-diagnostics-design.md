# 종목 유형 판단 실패 진단 설계

[#258](https://github.com/mochafreddo/stock-scout/issues/258)의 설계 인터뷰 기록이다. 상위 요구사항은 #250·#237을 따른다. Q8에서 설계를 확정했으며 후속 `to-spec` 요청으로 #258 명세 게시와 `ready-for-agent` 라벨 적용을 승인받았다. 구현·실연동·커밋·푸시 착수를 뜻하지 않는다.

2026-10-29 [#240](https://github.com/mochafreddo/stock-scout/issues/240)의 실제 실패를 계기로 [공용 유형 판단 진단 보강](#2026-10-29-공용-유형-판단-진단-보강)을 추가로 확정했다. 아래 기존 인터뷰와 소스 관찰은 당시 기록으로 유지하며, 새 절은 현재의 통합 유형 판단 흐름에 적용할 후속 설계다. 설계 확정은 구현이나 추가 실연동 승인이 아니다.

## 진단의 기본 제공

Q1에서 별도 옵션 없이 모든 실패의 stderr JSON에 `diagnostic` 객체를 기본 제공하기로 합의했다. 기존 필드·오류 코드·종료 코드와 성공 출력은 유지한다. 코드가 정한 안전한 단계·거부 사유·항목 위치만 제공하며 모델 응답 원문이나 외부 오류 메시지는 넣지 않는다. 진단을 얻기 위한 재실행을 줄이는 것이 목적이다.

## 여러 오류의 처리

Q2에서 기존 검증 순서에서 처음 발견한 거부 조건 하나와 관련 위치를 보고하고 즉시 실패하기로 합의했다. 전체 오류를 수집하기 위한 추가 검증은 하지 않는다. 기존 실패 동작과 검증 순서를 유지하면서 최초 거부 원인을 드러낸다.

## 항목 위치

Q3에서 관련 항목 번호를 오류가 발생한 응답 배열과 필드의 경로로 표시하기로 합의했다. `evidence[2].source`처럼 배열 번호는 0부터 시작하며 입력 종목 순번과 구분한다. 코드가 아는 배열·필드명과 숫자만 사용하고 모델이 보낸 필드명이나 값을 그대로 넣지 않는다. 응답 전체의 오류 등 위치를 특정할 수 없는 경우는 `null`로 표시한다.

## 호출 집계

Q4에서 조회·최종 판단 단계마다 모델 요청 시도 수, KIS 정보 조회 도구 호출 수, 관측한 웹 도구 호출 수를 나누어 표시하기로 합의했다. 서로 다른 호출을 합산하지 않는다. 웹 도구 호출 수는 관측한 호출 ID 기준이며 공급자 내부 HTTP 요청 수를 뜻하지 않는다.

## 시간 제한 당시의 상태

Q5에서 시간 제한 실패의 단계별 경과 시간을 밀리초로 남기고 각 단계를 완료·실패·미시작으로 구분하기로 합의했다. 실패한 단계는 중단 시점까지의 시간을 표시한다. 미시작 단계는 시간 `null`과 호출 수 0을 표시하여 0밀리초 만에 완료한 단계와 구분한다.

## 실패 단계와 통계 범위

Q6에서 인수·평가 파일 검사, 인증, 순위 수집, 자료 조회, 최종 판단, 결과 출력 검사를 구분해 실패 단계를 표시하기로 합의했다. 근거 검증은 자료 조회 단계에, 판단 결과 검증은 최종 판단 단계에 포함한다. 시간·호출 통계는 자료 조회와 최종 판단에 한정하며 시간 제한뿐 아니라 해당 단계의 다른 실패에도 제공한다. 실제 실패한 단계를 표시하고 다른 단계의 실패로 추정해 바꾸지 않는다.

## 거부 사유

Q7에서 코드가 정한 고정 식별자를 `diagnostic.reason`에 제공하기로 합의했다. 기존 `error`는 유지하며 필수 필드 누락, 미열람 출처, 존재하지 않는 근거 ID, 다른 증권의 근거 참조를 구분한다. 정확한 원인을 확인할 수 없으면 `unknown`을 사용하고 원문 오류 메시지에서 원인을 추측하지 않는다.

## 최종 확정과 명세 게시 범위

Q8에서 Q1~Q7의 합의와 로컬 설계 문서 확정 범위를 수락했다. 이어 사용자가 `to-spec`으로 #258 명세 게시와 `ready-for-agent` 라벨 적용을 요청했다. 구현·실연동·커밋·푸시·이슈 종료는 포함하지 않는다. 향후 #258 구현의 공개 검증 경계는 CLI 입력·stdout·stderr·종료 코드와 외부 HTTP 요청이다. 이번 문서 검토 기준은 인터뷰 시작 HEAD `41a4188e0413a95dc6757658c1e4d99a492f8859`와 문서 생성 직전의 작업 트리이며, 이슈 요구사항은 이번에 확보한 #258·#250·#237 원문과 댓글을 기준으로 한다. #258에 명시된 구현 리뷰 기준점도 같은 HEAD다.

## 확인한 사실

인터뷰 시작 시 HEAD는 `41a4188e0413a95dc6757658c1e4d99a492f8859`다. 기존 미커밋 용어집·ADR·설계 문서는 이번 기록과 구분한다.

현재 코드는 조회와 최종 판단을 분리하며 판단 결과를 거래소·종목 코드로 입력과 연결한다. 판단 배열의 순서가 입력 순서와 같다고 보장하지 않는다. 근거 ID는 조회 결과 배열 순서로 부여한다. Responses 요청, KIS 정보 조회 도구 호출, 관측한 웹 도구 호출은 서로 다른 카운터이며 웹 도구 관측 수가 공급자 내부 HTTP 요청 수를 뜻하지 않는다. 이 사실은 인터뷰 시작 시 `scripts/security-type-assessment.ts`를 읽어 확인한 것이며 실제 서비스 실행 결과는 아니다.

## 2026-10-29 공용 유형 판단 진단 보강

### 확인한 실패와 증거의 한계

한국 시각 2026-10-29 12:01:52부터 12:06:55까지 소스 `dacd813ec5fc65cef730f7c01ddc20fbc9270f50`, 모델 `gpt-6.1-sol`로 실제 매수 후보 CLI를 1회 실행했다. 전체 소요 시간은 302.393초였고 `stage: assessment`, `error: MODEL_INCOMPLETE`, 종료 코드 1로 끝났다. stdout은 비어 있었다. 공식 일정 HTTP 50회는 모두 200이었으며 전송 집계는 KIS 13회·발급 1회·일정 모델 1회·유형 모델 6회·추천 모델 0회·SIWC 갱신 1회였다. 발급은 KIS 전송 집계에 포함되므로 두 값을 더하지 않는다.

이 결과는 유형 판단 단계의 실패를 확인한 것이며 실제 최종 보고서 완료나 유형 판단의 정확도를 입증하지 않는다. 모델 요청 집계는 전송 시도 수이며 완료한 응답 수가 아니다. 당시 관측기는 공식 일정 HTTP 상태만 기록했으므로, 전체 소요 시간으로 유형 판단의 180초 기한 초과를 확정하거나 어느 모델 요청이 중단됐는지 판단할 수 없다. 이전 실제 실행과 이번 실행은 [실행 안내](buy-candidates.md)의 검증 기록과 구분한다.

해당 소스의 공용 [유형 판단 코드](../scripts/security-type-assessment.ts)는 단계 기한 초과, 완료 이벤트 누락·중복, 공급자의 실패·불완전 응답 등을 `MODEL_INCOMPLETE`로 묶는다. [후보군 통합 호출부](../scripts/candidate-universe.ts)는 유형 판단 통계 콜백을 사용하지 않으며 실패 시 오류·단계·공통 요청 집계만 출력한다. [유형 검증 CLI](../scripts/llm-security-probe.ts)는 기존 통계를 보존하지만 모델 요청별 시간과 종료 상태는 제공하지 않는다. 이는 소스에서 확인한 동작이며 이번 실제 실패의 구체적 원인을 확정한 결과가 아니다.

### 합의한 범위와 유지 조건

사용자는 Q1에서 기존 시간·호출 한도와 실패 정책을 유지하면서 진단 보강부터 설계하는 방향을 수락했다. Q2에서 공용 유형 판단 코드와 이를 사용하는 후보군·매수 후보·유형 검증 CLI의 진단 보강 범위, 공개 검증 경계와 리뷰 기준을 확정했다.

기존 통계와 진단 오류 구조를 확장하고 세 CLI가 같은 유형 판단 관측 결과를 사용한다. 별도 로깅 시스템·실행기·의존성은 추가하지 않는다. 기존 stderr 필드·오류 코드·종료 코드·성공 stdout과 실패 시 부분 보고서 차단을 유지하며, 기본 제공하는 실패 stderr JSON에 진단 정보만 추가한다. 기존 `diagnostic.reason`과 응답 항목 위치의 의미를 시간·스트림 상태로 바꾸지 않는다.

유형 판단 180초, 통합 실행 600초·대상 개장 마감, 단계별 요청·도구 상한과 인증·비용 정책을 유지한다. 기한을 늘리거나 자동 대기·재시도·모델 대체·유료 전환을 추가하지 않는다. 이 설계의 진단 범위는 공용 유형 판단이며 일정·추천 단계까지 요청별 상세 진단을 확대하지 않는다.

### 남길 진단 정보

| 구분 | 확정한 내용 |
| --- | --- |
| 전체 경과 시간 | 각 CLI 실행에서 측정한 전체 경과 시간과 유형 판단 경과 시간을 구분한다. 시작하지 않은 유형 판단은 시간 `null`과 요청 수 0으로 나타내어 0밀리초 완료와 구분한다. |
| 유형 판단 통계 | 기존 단계 상태·경과 시간·모델 전송 시도·KIS 정보 도구 호출·관측한 웹 도구 호출 집계를 재사용한다. 서로 다른 호출 종류를 더하지 않는다. |
| 요청별 관측 | 실행 안의 모델 요청 순번, 경과 시간, 확인한 HTTP 상태, 완료 이벤트 수와 종료 상태를 남긴다. HTTP 응답 헤더를 받은 시점에 시간을 확정하지 않고 스트림 종료 또는 중단까지 측정한다. 요청별 기록은 기존 최대 12회 범위로 제한한다. |
| 중단 사유 | 코드가 직접 관측한 유형 판단 기한 초과, 완료 이벤트 누락·중복, 공급자의 실패·불완전 응답, 통신 오류를 구분한다. 실제로 확인하지 못한 사유는 `unknown`으로 남긴다. |
| 마지막 진행 단계 | 코드가 확인한 마지막 진행 위치를 고정된 단계 식별자로 남긴다. 모델의 자유 서술이나 외부 오류 메시지에서 단계를 추측하지 않는다. |

공급자 이벤트의 실패·불완전 상태와 로컬 기한 도달은 서로 다른 관측이다. 전체 실행 시간이나 포괄 오류 코드로 원인을 역산하지 않으며, 최초 실패 뒤에 일어난 취소가 최초 실패를 덮어쓰지 않는다. 기존 실패 판정과 검증 순서를 유지한다. 진단을 위해 응답을 더 검증하거나 외부 요청을 추가하지 않는다.

중간 도구 요청을 포함해 각 모델 요청의 기록을 해당 요청에 연결한다. 완료 이벤트 뒤 오류나 중복 완료가 오면 앞선 완료 이벤트만으로 정상 응답이라고 기록하지 않는다. 관측하지 못한 HTTP 상태·완료 여부는 확인되지 않은 상태로 표현하며 성공을 추정하지 않는다. 완료 이벤트 누락은 스트림이 끝난 뒤에만 확정하고, 기한으로 중단된 스트림을 자연 종료로 취급하지 않는다.

새 진단에는 코드가 정한 식별자·숫자·상태만 사용한다. 인증값·개인 인증 경로·프롬프트·모델 응답 본문·웹 원문·외부 오류 메시지·요청 및 응답 헤더는 기록하지 않는다. 기존 입력 스냅샷이나 원자료를 새 진단에 복제하지 않으며, 허용한 필드만 구성한 뒤 기존 민감값 검사와 함께 확인한다.

### 구현 대상과 검증 경계

공용 유형 판단의 관측은 `scripts/security-type-assessment.ts`에 둔다. 기존 `scripts/diagnostic-error.ts`의 오류 전달과 통계를 재사용하고, `scripts/candidate-universe.ts`의 통합 CLI와 `scripts/llm-security-probe.ts`가 실패 출력에 전달한다. `scripts/buy-candidates.ts`는 기존 공용 통합 경로를 계속 사용한다. 전체 경과 시간은 각 실행의 시작점에서 측정하며 유형 판단 시간과 같은 값으로 대체하지 않는다. 구체적인 보조 함수 배치보다 공용 동작의 일관성과 최소 변경을 우선한다.

공개 검증 경계는 세 CLI의 입력·stdout·stderr·종료 코드와 외부 HTTP 목업이다. 기존 `tests/candidate-cli-helper.mjs`와 각 CLI의 HTTP 목업을 재사용한다. 단계 시간·응답 상태·완료 이벤트는 외부 시간과 통신 경계에서 대체하며 내부 함수 배치나 문서 문구를 테스트하지 않는다.

검증은 다음 조건을 포함한다.

- 모델 스트림 대기와 정보 도구 대기 중의 단계 기한 초과를 관측하고 전체 시간·유형 판단 시간·요청별 시간을 구분한다.
- 완료 이벤트 없는 EOF, 중복 완료, `response.failed`, `response.incomplete`, 정상 JSON 뒤 오류와 통신 오류가 관측된 사유와 일치한다. 앞선 실패가 후속 취소에 가려지지 않는다.
- HTTP 헤더를 먼저 받은 뒤 본문이 지연되는 경우에도 요청별 시간이 본문 종료·중단까지 포함한다. 여러 모델 요청의 시간과 종료 상태가 다른 요청에 붙지 않는다.
- 기존 오류 코드·종료 코드·빈 실패 stdout·성공 출력과 외부 요청 인자를 보존한다. 진단 추가 때문에 외부 호출·재시도·한도 확대가 생기지 않는다.
- 인증값과 원문에 합성 비밀값을 넣어도 진단에 노출되지 않는다. 관측하지 못한 원인은 `unknown`으로 남는다.
- 새 검사에서 진단 누락·잘못된 사유·헤더 시점의 조기 시간 확정을 탐지하는 음성 대조를 수행한다. 소스 변이가 필요하면 공용 변이 검사 절차를 사용한다.

구현 시 해당 CLI 회귀 검사·형식·린트·타입 검사와 최종 전체 테스트를 수행하고, 고정한 변경본을 Standards·Spec 두 축으로 검토한다. 리뷰 기준은 `stock-scout`의 `dacd813ec5fc65cef730f7c01ddc20fbc9270f50` 이후 이번 설계·구현 변경이다. 모의 검증은 실제 실패 원인 확인이나 최종 보고서 실연동 성공을 대신하지 않는다.

### 승인 범위와 후속 작업

이번 승인은 합의한 설계를 로컬 문서에 기록하는 범위다. 런타임 코드·테스트 구현, 추가 실제 호출, 커밋·푸시, 원격 이슈 수정·종료와 새 예약 작업은 포함하지 않는다. 진단 구현과 검증을 마친 뒤 실제 실행 횟수·시각·모델·기존 한도를 별도로 합의해야 새로운 실제 실패를 관측할 수 있다. 과거 실행에서 수집하지 않은 정보를 이번 설계로 복구할 수 있다고 주장하지 않는다.

이번 결정은 기존 진단을 확장하는 가역적인 구현 범위이며 새 도메인 용어나 되돌리기 어려운 구조 선택을 추가하지 않는다. 따라서 용어집과 별도 ADR은 추가하지 않는다.

후속 `implement` 요청은 위 설계를 공용 코드와 세 CLI·회귀 검사에 구현하고 검토·검증한 뒤 현재 브랜치에 로컬 커밋하는 범위를 승인한다. 추가 실연동·푸시·원격 이슈 변경은 이 후속 요청에도 포함하지 않는다. 위의 문서 전용 승인은 당시 범위로 보존한다.
