# 종목 유형 판단 실패 진단 설계

[#258](https://github.com/mochafreddo/stock-scout/issues/258)의 설계 인터뷰 기록이다. 상위 요구사항은 #250·#237을 따른다. Q8에서 설계를 확정했으며 후속 `to-spec` 요청으로 #258 명세 게시와 `ready-for-agent` 라벨 적용을 승인받았다. 구현·실연동·커밋·푸시 착수를 뜻하지 않는다.

## 진단의 기본 제공

Q1에서 별도 옵션 없이 모든 실패의 stderr JSON에 `diagnostic` 객체를 기본 제공하기로 합의했다. 기존 필드·오류 코드·종료 코드와 성공 출력은 유지한다. 코드가 정한 안전한 단계·거부 사유·항목 위치만 제공하며 모델 응답 원문이나 외부 오류 메시지는 넣지 않는다. 진단을 얻기 위한 재실행을 줄이는 것이 목적이다.

## 여러 오류의 처리

Q2에서 기존 검증 순서에서 처음 발견한 거부 조건 하나와 관련 위치를 보고하고 즉시 실패하기로 합의했다. 전체 오류를 수집하기 위한 추가 검증은 하지 않는다. 기존 실패 동작과 검증 순서를 유지하면서 최초 거부 원인을 드러낸다.

## 항목 위치

Q3에서 관련 항목 번호를 오류가 발생한 응답 배열과 필드의 경로로 표시하기로 합의했다. `evidence[2].source`처럼 배열 번호는 0부터 시작하며 입력 종목 순번과 구분한다. 코드가 아는 배열·필드명과 숫자만 사용하고 모델이 보낸 필드명이나 값을 그대로 넣지 않는다. 응답 전체의 오류 등 위치를 특정할 수 없는 경우는 `null`로 표시한다.

## 호출 집계

Q4에서 조회·최종 판단 단계마다 모델 요청 시도 수, KIS 정보 조회 도구 호출 수, 관측한 웹 도구 호출 수를 나누어 표시하기로 합의했다. 서로 다른 호출을 합산하지 않는다. 웹 도구 호출 수는 관측한 호출 ID 기준이며 공급자 내부 HTTP 요청 수를 뜻하지 않는다.

## 시간 제한 당시의 상태

Q5에서 시간 제한 실패의 단계별 경과 시간을 밀리초로 남기고 각 단계를 완료·실패·미시작으로 구분하기로 합의했다. 실패한 단계는 중단 시점까지의 시간을 표시한다. 미시작 단계는 시간 `null`과 호출 수 0을 표시하여 0밀리초 만에 완료한 단계와 구분한다.

## 실패 단계와 통계 범위

Q6에서 인수·평가 파일 검사, 인증, 순위 수집, 자료 조회, 최종 판단, 결과 출력 검사를 구분해 실패 단계를 표시하기로 합의했다. 근거 검증은 자료 조회 단계에, 판단 결과 검증은 최종 판단 단계에 포함한다. 시간·호출 통계는 자료 조회와 최종 판단에 한정하며 시간 제한뿐 아니라 해당 단계의 다른 실패에도 제공한다. 실제 실패한 단계를 표시하고 다른 단계의 실패로 추정해 바꾸지 않는다.

## 거부 사유

Q7에서 코드가 정한 고정 식별자를 `diagnostic.reason`에 제공하기로 합의했다. 기존 `error`는 유지하며 필수 필드 누락, 미열람 출처, 존재하지 않는 근거 ID, 다른 증권의 근거 참조를 구분한다. 정확한 원인을 확인할 수 없으면 `unknown`을 사용하고 원문 오류 메시지에서 원인을 추측하지 않는다.

## 최종 확정과 명세 게시 범위

Q8에서 Q1~Q7의 합의와 로컬 설계 문서 확정 범위를 수락했다. 이어 사용자가 `to-spec`으로 #258 명세 게시와 `ready-for-agent` 라벨 적용을 요청했다. 구현·실연동·커밋·푸시·이슈 종료는 포함하지 않는다. 향후 #258 구현의 공개 검증 경계는 CLI 입력·stdout·stderr·종료 코드와 외부 HTTP 요청이다. 이번 문서 검토 기준은 인터뷰 시작 HEAD `41a4188e0413a95dc6757658c1e4d99a492f8859`와 문서 생성 직전의 작업 트리이며, 이슈 요구사항은 이번에 확보한 #258·#250·#237 원문과 댓글을 기준으로 한다. #258에 명시된 구현 리뷰 기준점도 같은 HEAD다.

## 확인한 사실

인터뷰 시작 시 HEAD는 `41a4188e0413a95dc6757658c1e4d99a492f8859`다. 기존 미커밋 용어집·ADR·설계 문서는 이번 기록과 구분한다.

현재 코드는 조회와 최종 판단을 분리하며 판단 결과를 거래소·종목 코드로 입력과 연결한다. 판단 배열의 순서가 입력 순서와 같다고 보장하지 않는다. 근거 ID는 조회 결과 배열 순서로 부여한다. Responses 요청, KIS 정보 조회 도구 호출, 관측한 웹 도구 호출은 서로 다른 카운터이며 웹 도구 관측 수가 공급자 내부 HTTP 요청 수를 뜻하지 않는다. 이 사실은 인터뷰 시작 시 `scripts/security-type-assessment.ts`를 읽어 확인한 것이며 실제 서비스 실행 결과는 아니다.
