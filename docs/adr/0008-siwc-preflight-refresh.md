# 구독 인증은 API 실행 전에 자동 갱신한다

2026-10-20 구독 인증 갱신 설계 인터뷰에서 CLI의 API 요청 전에 액세스 토큰을 확인하고, 만료했거나 남은 시간이 5분 이하면 저장된 갱신 토큰으로 자동 갱신하기로 합의했다. 유효기간이 충분하면 기존 토큰을 사용하며 서버의 갱신 가능 시점을 준수한다. 정상적인 갱신마다 브라우저 로그인을 요구하는 불편을 줄이는 대신 CLI가 승인된 보관소의 인증 상태를 갱신하도록 한다. 응답 필드와 실패 처리의 세부 계약은 [확정한 설계](../siwc-refresh-design.md)를 따른다.

이번 범위는 실행 전 갱신이다. 모델 실행 중 인증 오류가 발생하면 기존 전체 실패 계약을 유지하고 모델·도구 호출을 자동으로 다시 실행하지 않는다. 이미 수행한 분석과 조회를 반복하지 않는 쪽을 선택한다. 이 결정은 갱신 구현·실연동 완료나 기존 유형 판단·장전 데이터 검증의 차단 해제를 뜻하지 않는다.

2026-10-21 후속 합의에서 로그인과 갱신은 같은 잠금으로 직렬화하고 최대 30초 기다린 뒤 저장 상태를 다시 확인하기로 했다. 회전된 갱신 토큰을 여러 프로세스가 동시에 사용하는 일을 막으며 남은 잠금은 자동 삭제하지 않는다. 통신·시간 초과·서버 장애에는 기존 인증을 보존하고 같은 실행에서 재시도하지 않는다. 공식 오류로 갱신 토큰 무효화가 확인되면 토큰을 정리하되 계정·client ID·호스트 등록은 보존하고 명시적 재로그인을 안내한다. 응답을 받지 못한 갱신을 성공으로 추정하거나 브라우저 로그인을 자동 시작하지 않는다.

Q5·Q6의 합의로 공식 예제를 참고해 `earliest_refresh_at`의 숫자는 Unix 초로 해석하며 시간대를 명확히 해석할 수 있는 날짜 문자열도 허용한다. 값이 없으면 만료 5분 전 기준을 적용하고, 잘못된 값이나 아직 허용되지 않은 갱신 시각에서는 요청하지 않는다. 응답에서 scope나 ID 토큰이 생략되면 기존 검증 정보를 유지하며 새 값이 있으면 권한과 신원을 검증한 뒤 적용한다. 액세스 토큰·교체 갱신 토큰·유효기간은 필수로 검사하고 인증 상태를 원자적으로 저장하며, 실패하면 모델 요청을 시작하지 않는다. 공식 예제의 선택을 채택한 것과 서버 계약의 실연동 검증은 구분한다.

Q8~Q10에서 검증된 갱신 응답은 취소가 들어와도 원자적 저장과 잠금 해제를 마친 뒤 종료하기로 확정했다. 취소를 즉시 처리하는 대신 서버가 이미 교체한 갱신 토큰을 잃지 않는 쪽을 선택하며 이후 데이터·모델 요청은 시작하지 않는다. 갱신 요청과 원격 신원 검증의 시간 제한은 설계를 따른다. 강제 종료나 저장 실패에도 저장 완료를 보장한다는 뜻은 아니다.
